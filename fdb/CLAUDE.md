# nos-fdb — Forwarding-database (EVPN/VXLAN) component

`nos-fdbd` is the MAC counterpart of `nos-ribd`: one process per `BroadcastDomain` that has a `vni` (spawned by `nos-watchdogd` through `instances::manage`, `claim_label: "vni"` — the opt-in mechanism `nos-restd` uses on `rest-api`). It owns the kernel side of the domain's EVPN: a VXLAN device enslaved into the domain's bridge, and the bridge FDB behind it, in both directions.

| `nos-ribd` (per `RoutingTable`) | `nos-fdbd` (per `BroadcastDomain`) |
|---|---|
| owns the kernel VRF + routes, deletes them on shutdown | owns the kernel VXLAN device + FDB entries, deletes the device on shutdown |
| `nos-bgpd` pushes learned routes in (`PushBgpRoutes`) | `nos-bgpd` pushes received EVPN routes in (`FdbRequest::PushEvpnRoutes`) |
| pushes redistributed routes to `nos-bgpd` (`RedistributeRoutes`) | pushes local MACs to `nos-bgpd` (`BgpRequest::RedistributeMacs`) |
| `show route <table>` | `show fdb <domain>` (`GET /v1/fdb/{domain}`) |

## Config (`BroadcastDomain`, see `proto/CLAUDE.md`)

`vni`, `rd`, `route_targets_import`/`route_targets_export`, `vtep_source` (a `SourceAddress`: `interface <if> [label <l>]` or `loopback [label <l>]`) and `mac_redistribute` (`redistribute from mac to bgp <instance>` — the BGP instance is named on that command, not on the domain). Two optional siblings add Type-2 routes *with an IP*: `arp_redistribute` (`redistribute from arp to bgp <instance>` — local ARP/IPv6 ND bindings on the bridge) and `connected_redistribute` (`redistribute from connected to bgp <instance>` — the domain's own SVI `addresses`, originated with the bridge's MAC). Both must name the same instance as `mac_redistribute` (validated) — one EVPN target per domain. Link-local/loopback/multicast addresses are never advertised (`is_advertisable_ip`). The daemon is only *ready* (`fdb::Ready`) when all of `rd`, `vtep_source`, `mac_redistribute`, the domain's bridge (asked of `nos-interfaced`, `GetBroadcastDomain` → `bridge_name`) and the VTEP address (`GetInterface`) resolve; until then it idles and the 10s tick retries — a bridge or address that isn't there *yet* is the normal case.

## Kernel side (`driver/`)

`FdbDriver` (`--driver linux|noop`, like `RibDriver`). The Linux driver, over `rtnetlink`:
- `vx<vni>` (a VNI is unique per netns, so no registry file) with `local <vtep>`, dstport 4789, `nolearning`, **and `dev <underlay>`** — the device carrying the VTEP address (`eth0` for an interface source, `lo<table-id>` for a loopback, via `RibRequest::GetTableId`). This is not cosmetic: when the address lives inside a VRF the kernel can only bind the tunnel's UDP socket through that device. A device whose VNI/address/underlay drifted is recreated; VNI can't change in place.
- Remote MAC: `RTM_NEWNEIGH` AF_BRIDGE on the VXLAN device, `NTF_SELF|NTF_MASTER|NTF_EXT_LEARNED` (files it in the bridge table too; the bridge neither ages nor relearns it), `dst`=remote VTEP, `vni`, state permanent.
- Flood list: one all-zero-MAC entry per remote VTEP (head-end replication), which needs `NLM_F_APPEND` — `NeighbourAddRequest` hardcodes its flags, so every FDB write is a raw message via `Handle::request`.
- Remote IP: a Type-2 with an IP (`EvpnKey::MacIp`) is also an IP neighbour on the *bridge* (`RTM_NEWNEIGH` AF_INET/INET6, permanent + `NTF_EXT_LEARNED`, so the SVI resolves the host without ARP and the kernel neither ages nor probes it) next to its FDB entry. `desired` returns both; `installed` holds a list per route and an item is only removed when no other route still names it (a MAC-only and a MAC+IP route for one MAC share the FDB entry).
- Local MACs: `local_macs` dumps the bridge FDB and keeps entries that are *not* `permanent` (the ports' own addresses), not `extern_learn` (fdbd's own writes — this is the loop guard), not on the VXLAN port, and not group/all-zero addresses. An `RTNLGRP_NEIGH` subscription (`watch_neigh`, which also wakes on IPv4/IPv6 neighbour events) only signals "look again"; a debounced (200ms) dump is the source of truth, and the 10s tick covers a dropped notification. Note `bridge fdb add` defaults to *permanent* — pin a test MAC with `static`.

## IPC

- `--listen-socket` (`/run/nos/fdb-<domain>.sock`, `ServiceRef::FdbDomain`). `allowed`: `PushEvpnRoutes` is `bgpd`'s, `GetMacs` is `user`/`restd`.
- `bgp_client.rs` originates this domain's routes into `ServiceRef::BgpInstance(mac_redistribute)`: one Type-3 (inclusive multicast, origin = VTEP), one Type-2 per local MAC and, with `arp`/`connected`, one Type-2 (MAC+IP) per local neighbour (`local_neighbours`: the bridge's ARP/ND dump, not `extern_learn` — the loop guard — *and only for MACs behind a local port*, so a binding the SVI learned over the VXLAN port isn't re-originated) and per SVI address (`bridge_mac` from netlink), carrying the export Route Targets and the VXLAN encapsulation community, next-hop = VTEP. `Full` on every (re)connect; the otherwise write-only connection is also read for EOF so a `nos-bgpd` restart is answered at once (unlike `nos-bgpd`'s `rib_push_client`, which doesn't notice).
- `nos-bgpd`'s `fdb_push_client` pushes *every* received EVPN route to each domain that redistributes into it; **Route-Target filtering is fdbd's** (`fdb::desired`): a route is installed only if it carries an import RT, names this VNI (a Type-3's VNI comes from its PMSI attribute, absent = matches) and isn't our own VTEP.

## Ethernet Segments (ESI) and the Designated Forwarder

A `PortAggregate` with an `esi` (config: `set port-aggregate <n> esi <10 hex bytes>`) that is a member of this domain's bridge — through its switching profile, untagged (the bond is the bridge port) or `Dot1q(n)` (its `<bond>.<n>` sub-link is) — is an **Ethernet Segment port** (`Ready.es_ports`, resolved in `reconcile::es_ports`, the bond's real `bond<id>` name coming from `nos-interfaced`'s `GetPortAggregate`). What that does:

- **Type-2 ESI.** `FdbDriver::local_macs` now returns each MAC with the bridge port it sits behind; `local_routes` puts that port's ESI on the MAC's Type-2 (and on a MAC+IP for a neighbour behind it). `EvpnRoute.esi` is in the route *value*, not `EvpnKey`; the ESI is part of a Type-2's wire identity though, so `nos-bgpd`'s `apply_evpn_local` withdraws the old NLRI when a MAC moves onto/off a segment.
- **Type-4.** One `EvpnKey::EthernetSegment { rd, esi, origin = VTEP }` per distinct ESI, carrying only its ES-Import Route Target (`nos_proto::evpn_id::es_import_rt`). Originated by *every domain's* fdbd that attaches the segment, each with its own RD, so the same segment appears once per domain; receivers dedupe by origin.
- **DF election** (`df.rs`, pure): RFC 7432 §8.5 default carving — the segment's PEs (our VTEP plus every received Type-4 origin for that ESI, matched on the exact ESI, not the ES-Import RT, and — RFC 8584 §2.1 — further restricted by `plan_df` to those with a held per-EVI Ethernet A-D for this domain's own VNI, so a PE on the segment that never joined this EVI is not a candidate for it) ordered by ascending address; the DF for the domain is `pes[vni % n]` (RFC 8365 §8.3.1: the VNI is the Ethernet tag), so two domains on one segment spread over the PEs. `Fdb::sync_df` re-runs it on every received Type-4/per-EVI-A-D change and on each resync.
- **Applied to the kernel:** `FdbDriver::set_port_flood` (an `RTM_NEWLINK` with `IFLA_INFO_PORT_DATA` = `IFLA_BRPORT_{UNICAST,MCAST,BCAST}_FLOOD`, the same as `ip link set … type bridge_slave flood …`; via netlink, not sysfs, since fdbd is the unprivileged `nos` user) — off on the non-DF's segment port, on for the DF and for a port that left the segment (or on shutdown). The block is re-asserted every resync so a recreated port is healed. Log anchors: `df elected … role=df|non-df pes=…`, `segment port flooding set … flood=…`.
- **`desired`** skips a remote Type-2 whose ESI is one of our local segments: that MAC is reachable through our own bond, a VXLAN entry to the peer PE would win over it.
- `show fdb` lists each segment (`FdbTable.segments`: ESI, port, DF role, ranked PEs) and the ESI of a local MAC.

- **DF wait timer** (§8.5 step 3, `--df-wait`, default 3s): a segment port is held blocked (`segments[].waiting`, reported non-DF in `show fdb`) for the wait after it *first appears* in the plan — fdbd start, ESI newly set, port newly attached, fdbd back from not-ready — and only then is the election applied, so a PE that has just come up doesn't double-deliver BUM. A peer's Type-4 arriving later does not restart it (the joining PE waits, the incumbent doesn't). `run_local` sleeps to the earliest deadline (`df_deadline`) since the 10s tick is too coarse. Log anchors: `df wait started … seconds=`, then `df elected …` only once it ends. Tunable through `--fdbd-arg=--df-wait=N` (e2e `evpn-esi` uses 12s so the kernel state can be read while blocked).

- **Type-1 Ethernet A-D routes** (`EvpnKey::EthernetAd { rd, esi, tag, origin }`; `tag == AD_TAG_ES` is per-ES, otherwise per-EVI). For every attached segment whose port has carrier, `local_routes` originates, next to the Type-4, a **per-ES A-D** (MAX-ET, this domain's export RTs, encapsulation and an **ESI Label** community — `nos_proto::evpn_id::esi_label_ext`, no label with VXLAN (RFC 8365 §8.3.1), only the flags octet whose bit 0 is Single-Active) and a **per-EVI A-D** (tag 0, the VNI in the label field, the domain's RTs). `origin` is not on the wire (the NLRI has no originator): it is the BGP next hop on a received route and our VTEP on a local one, and is only there so two PEs' routes stay apart in `evpn_push_snapshot` (which otherwise collapses one key from two peers). `nos-bgpd` renders the community as `esi-label:single-active|all-active`.
- **Mass withdrawal** (RFC 7432 §8.2.1, receiver side): `Ads` (`ad_index`) records, per segment, the PEs whose per-ES A-D we hold (import RT only, never our own). `desired` installs a remote Type-2/MAC+IP with a non-zero ESI only while *its* PE is in that set, so withdrawing one route removes every MAC (and neighbour) of that PE on the segment at once, and they come back with it. `apply_push` re-syncs every Type-2 of the segments whose set changed (`segment per-es a-d changed` in the log). A MAC on a segment we are attached to is still skipped (reachable through our own bond).
- **ES down** (the trigger that makes mass withdrawal real): `FdbDriver::port_up` (`IFF_LOWER_UP`) is read by `refresh_local` on every link/neighbour event (`watch_neigh` also subscribes to `RTNLGRP_LINK`) and on the tick. A segment whose port has no carrier withdraws its Type-4 and both Type-1, is never the DF, and restarts its DF wait when carrier returns (`segment port carrier changed … up=`). A failed read counts as up. Local MACs behind the dead port are not withdrawn (the bridge ages them).
- **Single-active** (`PortAggregate.redundancy_mode`, `set port-aggregate <n> redundancy-mode single-active`, needs an `esi`): the election is unchanged (RFC 7432 §8.5, `df.rs`), what differs is what it is applied to. A single-active non-DF (or one still in its wait, or down) has its bridge port put in the STP state **disabled** (`FdbDriver::set_port_forwarding`: an `RTM_SETLINK` in the `AF_BRIDGE` family with `IFLA_PROTINFO` — what `bridge link set … state` sends; **not** the `RTM_NEWLINK` + `IFLA_INFO_SLAVE_DATA` path `set_port_flood` uses, which accepts `IFLA_BRPORT_STATE` and silently ignores it), which drops unicast as well as BUM in both directions; its flood flags stay on. It is *disabled*, not *blocking*: with the bridge's STP off (the only mode here) the kernel's `br_port_state_selection` turns a BLOCKING port straight back to forwarding — the write succeeds and does nothing, which the first e2e run found — but skips disabled ones. The DF's port forwards. Forwarding is the kernel default, so it is only asserted after the port was blocked; a block is re-asserted every resync. Switching the mode swaps the mechanism and undoes the old one (`segment port forwarding set …`). The per-ES A-D carries the Single-Active flag; `show fdb` lists `single_active`. **Ceiling:** the blocked port keeps its carrier, so a customer device needs end-to-end failure detection (an ARP-monitored active-backup bond, as `evpn-single-active` uses) to move over — dropping the carrier would mean touching a link `nos-interfaced` owns.
- **Backup path** (§8.4.1.2, receiver side): `SegmentAds` also records the PEs with a per-EVI A-D for *this domain's VNI* and whether any per-ES A-D carried the Single-Active flag. When a MAC's PE has lost its per-ES A-D and the segment is single-active, `desired` re-points the MAC at the lowest-address PE that still advertises both the segment and the EVI, ahead of the new Type-2. (`ponytail:` ideally the current DF, which is not visible for a remote segment.) An all-active segment has no backup: that is the mass withdrawal above.

- **Aliasing** (§8.4.1.1, receiver side, all-active only): a remote MAC on a segment we are *not* attached to is reached through every PE that advertises **both** the segment (per-ES A-D) and this domain's EVI (per-EVI A-D), provided there are at least two, the MAC's own PE is one of them and they are all IPv4 (`alias_group`). Those PEs become an **FDB nexthop group** (`ip nexthop add id N via <vtep> fdb`, `… group A/B fdb`, then the FDB entry with `NDA_NH_ID`) and the kernel balances flows over it; otherwise the plain single-PE entry is used. The group shrinks when a PE's per-ES or per-EVI A-D goes (`remote mac group installed|removed … vteps=`, `show fdb` lists all `vteps` of a MAC, `(aliased)` in the CLI). Two Type-2 routes for one MAC from two PEs want the *same* group item, so they neither reinstall nor flap each other. The FDB entry has to be **deleted before it changes form** (the kernel keeps the old form on a `replace`), which `set_remote_mac_group` and `sync_key`'s uninstall-then-install order both do. No `netlink-packet-route`/`rtnetlink` support exists for nexthops, so `driver/nexthop.rs` hand-encodes `RTM_NEWNEXTHOP`/`RTM_DELNEXTHOP` (a unit test pins the byte layout) and sends them on a plain `netlink-sys` socket from `spawn_blocking`. Ids are `vni << 8 | slot` so the per-domain `nos-fdbd` processes sharing a netns never collide; `ponytail:` 255 nexthops + groups per domain, deleted only with the domain (`remove_vxlan`), and IPv6 VTEPs are not aliased. **Spike (2026-09-21, kernel 7.2):** an FDB nexthop group forwards through a VXLAN whose underlay device is in a VRF — the `via`/`NDA_IFINDEX` problem does not recur, since the nexthop path takes the VXLAN device's underlay — so no operator prerequisite beyond the existing `udp_l3mdev_accept`.

Ceilings (`ponytail:`): **no local bias** (see below); the non-DF of an all-active segment also stops delivering *locally sourced* BUM to that port; no ES-Import filtering. `nos-e2e evpn-esi` proves the control plane, the Type-1/mass-withdrawal behaviour and the kernel port flags, `evpn-single-active` the single-active state machine and failover with real traffic, `evpn-dataplane` all-active forwarding (below).

### Local bias / split horizon — not implemented, and why

BUM a CE sends on its link to the non-DF PE is head-end-replicated to the other PE on the segment, which — if it is the DF — forwards it back to the CE. RFC 8365 §8.3.1 has the receiving PE drop BUM whose source VTEP shares the segment. The bridge cannot: it sees only the inner frame, never the outer source address. **Spike (2026-09-21):** the mechanics do work in the kernel with only netlink — a tc `flower` filter on the *underlay's* ingress matching outer `ip_src` + UDP 4789 with `skbedit mark`, and a `fw` filter with `gact drop` on the segment port's egress; the mark survives VXLAN decapsulation into the bridge, and a filter naming another source drops nothing. (`netlink-packet-route` types flower/matchall but not `skbedit`, `fw` or `gact`, so those would be raw attributes.)

It is **not built** because it is unsafe on its own. Today the non-DF refuses *all* BUM to the segment port (flood off), so BUM from a host attached only to the non-DF PE reaches the CE through the DF — exactly the copy a same-ES-peer drop would kill, leaving the CE without it. Correct local bias needs the DF filtering to change with it: the non-DF must deliver *locally sourced* BUM to its segment port and refuse only BUM arriving from the core, i.e. tc has to classify core-origin BUM (mark every VXLAN packet at the underlay ingress, and BUM by the inner destination MAC's multicast bit at a fixed offset of the outer packet, and combine that with the same-ES-peer mark) instead of the flood flag doing the DF's job. Also limits: the underlay ingress hook only sees a VTEP that is an *interface* address (`vtep-source interface`), not a loopback's; the mark space would be IPv4 addresses.

## Explicit ceilings (`ponytail:` in the code)

MAC mobility / duplicate-MAC selection is now resolved in `nos-bgpd`, not here — see `bgp/CLAUDE.md`'s "MAC mobility" section: `nos-fdbd`'s own `received` table only ever gets the RFC 7432 §15 winner for a given `(VNI, MAC)` per push, so `desired`/`sync_key` need no cross-key MAC awareness. ARP suppression itself (the entries are installed but `neigh_suppress` isn't set on the VXLAN port), the IP-VRF label / Type-5 / router-MAC extended community; RPL policy on EVPN (bypassed in `nos-bgpd`); re-advertising received EVPN routes; a `Lookup` query. An SVI's own Type-2 (`redistribute from connected`) carries the RFC 7432 §7.8 Default Gateway extended community (`nos_proto::evpn_id::DEFAULT_GATEWAY`, `local_routes` tagging only `r.connected`-sourced neighbours, never a real ARP/ND-learned host); `bgp::evpn::format_ext_community` renders it `default-gw`. There is no separate proxy-ARP path to gate behind it — any Type-2 with an IP already installs an unconditional kernel neighbour (`Installed::Neigh`), which is already this RFC's actual mechanism. `nos-e2e evpn-fdb` proves the control plane and the kernel FDB programming against GoBGP; `nos-e2e evpn-dataplane` proves **forwarding** between two nos PEs and a dual-homed CE (unicast across the VXLAN both ways, a broadcast delivered to the segment once through the DF and never through the non-DF, local bridging on the non-DF) — the run that found every remote FDB entry must name its underlay (`via`/`NDA_IFINDEX`, the driver's `underlay` map), else with the underlay in a VRF the kernel looks the remote VTEP up in the main table and drops every frame (`tx_carrier_errors`). **Operator prerequisite nothing in nos sets:** with the underlay in a VRF, receiving VXLAN needs `net.ipv4.udp_l3mdev_accept=1` (the daemons are unprivileged and `/proc/sys` is read-only in the container); the e2e phase sets it through its privileged helper. Not observed by the e2e: a remote MAC behind a segment we share is *skipped* (`desired`) rather than pinned to our own segment port, so a PE that hasn't learned it locally has no FDB entry for it and would flood its unicast (the phase's pings pass either way).

## Modules

| Module | Role |
|---|---|
| `main.rs` | flags, PKI identity from stdin, tracing + `ForwardingLayer`, spawns reconcile / local-MAC loop / bgp push / server; SIGINT deletes the VXLAN device |
| `fdb.rs` | `Fdb`: the MAC table (`received`, `installed`, `local` with each MAC's port, `ads`, `es_down`), `desired`/`local_routes`/`plan_df`/`ad_index` (pure), `set_ready`/`apply_push`/`sync_df`/`refresh_local`/`run_local`/`table` |
| `df.rs` | pure DF election (`candidates`/`elect`) |
| `reconcile.rs` | config diff + tick → `Ready` → `Fdb::set_ready` |
| `driver/` | `FdbDriver`, `linux.rs`, `noop.rs`, `nexthop.rs` (hand-encoded FDB nexthops/groups), `is_local_mac` (pure) |
| `bgp_client.rs` | pushes local routes to `nos-bgpd` |
| `interface_client.rs` | bridge name, VTEP address + underlay device, a port aggregate's `bond<id>` name |
| `server.rs` | `GetMacs` / `PushEvpnRoutes` |
| `config_client.rs`, `watchdog_client.rs` | reimplemented per crate, per the star dependency graph |

`nos-e2e evpn-fdb` (GoBGP as the remote VTEP; a helper container pins a MAC and an `ip neigh ... nud permanent` on the bridge from inside router-a's netns) is the end-to-end proof, including Type-2-with-IP in both directions.
