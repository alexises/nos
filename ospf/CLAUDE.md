# nos-ospf — OSPF Component

OSPF daemon for NOS (binary `nos-ospfd`, one process per `OspfInstance`, dynamically spawned by `nos-watchdog` — see root `CLAUDE.md`'s "Process supervision" section).

## Scope

`nos-ospfd` resolves its own configured instance/areas/profiles from `nos-configd`, and runs a real RFC 2328 Hello protocol on every `Subinterface.ospf_profile` (point-to-point) and `BroadcastDomain.ospf_profile` (multi-access, with RFC 2328 §9.4 DR/BDR election) attach point — a real raw protocol-89 socket, VRF-scoped, joined to the AllSPFRouters (224.0.0.5) multicast group. Adjacency formation now reaches real `Full` state with real LSAs, matching how `nos-bgp` grew from OPEN/KEEPALIVE-only into real route exchange:

- **Neighbor FSM depth**: `Down` → `Init` → `TwoWay` → `ExStart` → `Exchange` → `Loading` → `Full` (`ospf::neighbor::NeighborState`), on both network types — the full RFC 2328 §10.5 ladder. `TwoWay` only advances to `ExStart` once RFC 2328 §7.5/§10.4's adjacency-eligibility rule holds (`link::should_form_adjacency`): unconditionally true on point-to-point; on a broadcast link, only for a DR/BDR-involving pair (a `DrOther`-`DrOther` pair stays at `TwoWay` forever). From `ExStart` onward, `ospf::exchange` drives RFC 2328 §10.6-10.8's DBD master/slave negotiation and summary-list exchange, then real LSR/LSU/LSAck against a per-area `ospf::lsdb::Lsdb` (see below) — no SPF/route computation is done with what lands in it yet.
- **Network type**: `Subinterface.ospf_profile` attach points (a VLAN sub-interface modeling one link to one peer) run point-to-point — at most one neighbor, no election, `link::InterfaceState` fixed at `PointToPoint`. `BroadcastDomain.ospf_profile` (multi-access SVI) attach points run broadcast — potentially many neighbors keyed by router-id, a `Waiting` interface state on start (wait-timer = dead-interval), then a real DR/BDR election (`ospf::election::elect`) settling into `Dr`/`Backup`/`DrOther`. A loopback (`Interface.ospf_profile`) attach point still has no peer to Hello with and stays **log-only**, resolved purely from the already-fetched `Config` (`reconcile::attach_points_for`). Hello stays multicast 224.0.0.5 on both real network types (RFC 2328 has no unicast Hello); DBD/LSR/LSU/LSAck are unicast to the specific neighbor's IP (captured from the source address of its last Hello).
- `OspfProfile.network_type: Option<NetworkType>` overrides the type an attach point gets when set; left `None`, it defaults per attach-point kind (`Subinterface` → `PointToPoint`, `BroadcastDomain` → `Broadcast`) — resolved in `reconcile.rs`, not the schema, since one profile can be referenced by attach points of different kinds at once. Never validated against the attach point's actual kind (real OSPF allows forcing either behavior on either kind of link).

`OspfProfile` carries `hello_interval`/`dead_interval`/`priority: Option<u16|u8>` (`None` defaults to `HELLO_INTERVAL_DEFAULT`/`DEAD_INTERVAL_DEFAULT`/`PRIORITY_DEFAULT` — 10s/40s/1, RFC 2328 Appendix C.3), `hello_interval`/`dead_interval` validated (`dead_interval` must exceed `hello_interval` when both are set) the same way `BgpPeerGroup.hold_time`/`keepalive_interval` are, one level up on `OspfArea.profiles` (`ospf_profile::valid_profile_timers`). `priority` governs DR/BDR election eligibility on a `Broadcast` link (`0` means "never eligible") and is sent on the wire (functionally inert) on a `PointToPoint` one too. `cost: Option<u16>` (range `1..=65535`) is stored/validated/rendered only — this NOS has no SPF yet, so it has no behavioral consumer, a forward-declared placeholder for a future SPF phase. All five fields are `nos-cli`-editable (`set hello-interval|dead-interval|cost|priority|network-type ...` while navigated into an `OspfProfile`, or the fully-qualified form from anywhere — mirrors `BgpPeerGroup.hold_time`'s exact CLI precedent). RFC 2328 Appendix C.3's `RxmtInterval` (how often an unacknowledged LSR/LSU is resent) is a fixed 5s constant (`link::RXMT_INTERVAL`), not yet a sixth `OspfProfile` field — see `link.rs`'s own `ponytail:` note on why.

### LSA exchange and the LSDB

Once a neighbor reaches `ExStart`, `ospf::exchange` (pure, no I/O, mirroring `bgp::fsm::step`'s transition-returns-actions shape) drives:

- **`ExStart`**: RFC 2328 §10.6 master/slave negotiation — the higher router-id wins master. `ponytail:` this crate sends its *entire* local LSDB summary in one DBD (`more: false`) per direction rather than paginating across many polls, since this NOS's LSDB is lab-scale and always fits one packet — see `exchange.rs`'s own note for the upgrade path. The two sides' Hello-driven `ExStart` entry is never synchronized (each side reaches it independently, off its own Hello timing), so the would-be master's `on_dbd_in_exstart` accepts *either* the neighbor's own negotiation attempt (I=1,M=1,MS=1) *or* its reply (MS=0) as the trigger — a real, common case where the master never gets to see the neighbor's original attempt (sent before the master itself reached `ExStart`) but does see its reply almost immediately after. Since that reply is also the only copy of the neighbor's summary the master will ever see (the neighbor, already past its own `ExStart`, never resends the original attempt), receiving it this way processes its content immediately too (`ExchangeDone` fires in the same step as `NegotiationDone`) rather than waiting for a second message that isn't coming.
- **`Exchange`**: compares the neighbor's summary list against the local LSDB (`lsa::is_newer`) to build a request list; empty request list goes straight to `Full`, non-empty goes to `Loading`. A negotiation-shaped duplicate arriving here (the peer's own view hasn't caught up to the fact that negotiation already succeeded) is silently ignored, not treated as a restart signal — treating it as `SeqNumberMismatch` would force both sides to keep re-picking fresh random sequence numbers and restarting in lockstep, an unrecoverable live ping-pong. A genuine peer restart is instead caught via Hello: losing 2-way already clears `adjacency` (`link::handle_hello`).
- **`Loading`**: LSR/LSU/LSAck against the neighbor, via `ospf::lsdb::Lsdb` — one per OSPF area (`LinkManager` holds `HashMap<Ipv4Addr, Arc<Mutex<Lsdb>>>`, never a single flat map, since `OspfArea` is already multi-valued in this schema and a flat LSDB would leak LSAs across areas). `Lsdb::install` only accepts a strictly-newer instance (RFC 2328 §13.1: sequence number, then checksum, then `MaxAge`-is-always-newer). An unrequestable LSA (`BadLSReq`) or an out-of-sequence packet at any point restarts negotiation from `ExStart` (`SeqNumberMismatch`).
- **Self-origination** (`LinkManager::originate_router_lsas`, on a 2s tick, independent of the 10s config-reapply tick): recomputes and reinstalls this router's own Router-LSA per area (one link entry per currently-known link with a neighbor/resolved DR) and a Network-LSA on any broadcast link where this router is DR with ≥1 `Full` neighbor — only reinstalling (and bumping the sequence number) when the content actually changed.
- **Flooding**: `ponytail:` no real RFC 2328 §13 event-driven flooding yet (on origination, or on receipt, reaching every adjacent link) — instead, each link periodically (every `RXMT_INTERVAL`) resends its *entire* local-area LSDB to every `Full` neighbor on that link (`link::flood_full_neighbors`). Safe (a non-newer duplicate is cheaply rejected and still acked) and simple, at the cost of a little wasted bandwidth on a lab-scale LSDB; it does mean an LSA can validly be first observed as "installed" via either of a router's links when it has more than one in the same area — see `lsa.rs` for what Router/Network-LSA bodies this NOS parses/originates and what's deliberately deferred (LSA aging/refresh, AS-external/Summary LSAs, multi-area ABR behavior, authentication).
- **Reporting**: `nos_proto::OspfNeighborState`/`NeighborSummary` (`show ospf neigh`) don't yet have `ExStart`/`Exchange`/`Loading`/`Full` variants of their own — every one of those internal states currently reports as `TwoWay` on the wire (`link::to_neighbor_state`), since all of them are supersets of it; a future phase grows the wire enum to match.

## Modules

| Module | Role |
|--------|------|
| `main.rs` | Arg parsing (`--instance`, `--watchdog-socket`, `--listen-socket`, `--log-socket`), resolves `nos-configd`'s address via the watchdog broker before starting, SIGINT+SIGTERM shutdown wait, spawns `reconcile::run` and `server::start` sharing one `Arc<link::LinkManager>` |
| `config_client.rs` | Own `fetch_config` (`Request::Get`) / `subscribe_diff` (`Request::SubscribeDiff`) — reimplemented rather than shared with the other component crates, per the root `CLAUDE.md`'s star dependency graph |
| `watchdog_client.rs` | `resolve_with_retry` (used once at startup for `ServiceRef::Config`) and `resolve_once` (used every resync for `ServiceRef::RibTable`/`ServiceRef::Interfaces`, where "not available" must return quickly rather than block) |
| `rib_client.rs` | One-shot `get_vrf_name` — the client side of `RibRequest::GetVrfName`, reimplemented from `nos-bgp`'s own copy per the star dependency rule |
| `interface_client.rs` | One-shot `get_interface`/`get_broadcast_domain` — the client side of `InterfaceRequest::GetInterface`/`GetBroadcastDomain`, likewise reimplemented from `nos-bgp`'s own `get_interface` (the broadcast-domain query is new to `nos-interfaced` itself — see `interface/CLAUDE.md`) |
| `packet.rs` | RFC 2328 Appendix A.3's common packet header (shared `encode`/`decode` dispatch by type byte, mirroring `bgp::message::BgpCodec`'s per-type-byte dispatch) plus each type's own body: Hello (A.3.2), DBD (A.3.3), LSR (A.3.4), LSU (A.3.5), LSAck (A.3.6). Pure, no I/O. Checksum is the standard RFC 1071 ones-complement-of-ones-complement-sum (same as IP/TCP/ICMP), **not** OSPFv3's Fletcher checksum or the LSA checksum (RFC 905 Annex B, see `lsa.rs`) — this covers only the common header, never an LSA's own. `router_priority`/`designated_router`/`backup_designated_router` are real Hello fields (used by broadcast-link election; sent but functionally inert on point-to-point); network mask stays always-zero/ignored on both (RFC 2328 §10.5 exempts point-to-point, and this NOS never implements the address-mask subnet check broadcast links would otherwise want) |
| `lsa.rs` | RFC 2328 Appendix A.4's LSA types: the common 20-byte header (`LsaHeader`, keyed by `LsaKey` — type/link-state-id/advertising-router) plus Router-LSA (A.4.2) and Network-LSA (A.4.3) bodies, fully parsed (not opaque bytes) since both are small/fixed-width and a future SPF phase would need real link data anyway — link **metric** round-trips but nothing computes/consumes a real one yet. `is_newer` implements RFC 2328 §13.1's instance-freshness tie-break (sequence number, then checksum, then `MaxAge`-is-always-newer). AS-external/Summary LSAs (types 3/4/5), multi-area ABR behavior, LSA aging/refresh, and authentication are all out of scope, matching this crate's single-backbone-area/no-auth ceiling elsewhere |
| `lsdb.rs` | `Lsdb` — the per-area installed-LSA store (`HashMap<LsaKey, Arc<Lsa>>`), `install`/`get`/`headers`/`all`, pure with respect to I/O. One `Lsdb` per area, held by `LinkManager` behind `Arc<tokio::sync::Mutex<_>>` and shared by every link in that area |
| `exchange.rs` | RFC 2328 §10.6-10.8's DBD/LSR/LSU/LSAck exchange logic — `on_dbd_received`/`on_lsr_received`/`on_lsu_received`/`on_lsack_received`, each pure (no I/O), returning `Action`s (`SendDbd`/`SendLsr`/`SendLsu`/`SendLsAck`/`NeighborEvent`) for `link.rs` to carry out — the RFC-2328-specific counterpart to `bgp::fsm::step`'s pure-transition-returns-actions shape. `AdjacencyData` (request list, retransmission list, master/slave role) lives alongside `NeighborInfo` rather than inside a `NeighborState` variant's payload, unlike `bgp::fsm::State::Established(RemoteInfo)` — this data mutates on nearly every packet for a `Full` adjacency's whole lifetime, unlike `RemoteInfo`'s set-once shape |
| `neighbor.rs` | `step(NeighborState, Event) -> NeighborState` — the pure RFC 2328 §10.5 neighbor transition table, covering the full `Down`/`Init`/`TwoWay`/`ExStart`/`Exchange`/`Loading`/`Full` ladder, unit-tested directly with no I/O. Applied once per neighbor — unchanged by network type, `link.rs` just calls it once (point-to-point) or per-neighbor-in-a-map (broadcast) |
| `election.rs` | `elect(Candidate, &[Candidate]) -> ElectionResult` — the pure RFC 2328 §9.4 DR/BDR election algorithm (priority/router-id tie-break, incumbent-DR stickiness, priority-0 exclusion), unit-tested directly with no I/O. `link.rs`'s `run_election` re-runs it after every Hello-driven neighbor-state change and dead-sweep once a broadcast link is out of `Waiting` — a `ponytail:`-flagged single-pass simplification of RFC 2328's "recompute twice if self's own role changed" refinement, harmless even now that adjacency eligibility depends on DR/BDR-ness (see `election.rs`'s own updated note). `run_election`'s own candidate-pool filter matters here: it includes every neighbor at `TwoWay` *or later* (`ExStart`/`Exchange`/`Loading`/`Full`), not just exactly `TwoWay` — a neighbor that's progressed into DBD/LSR/LSU exchange is still on the segment and must stay eligible, or this router would wrongly conclude it's alone and re-elect itself DR the moment its only neighbor advances past `TwoWay` |
| `socket.rs` | `OspfSocket` — a raw protocol-89 socket bound via `socket2::Socket::bind_device` (`SO_BINDTODEVICE`) to this link's own specific L3 interface (`link::LinkConfig.kernel_interface`) — **not** the VRF device, unlike `bgp/src/tcp.rs`'s TCP socket. A raw socket has no port/connection concept to demultiplex by, so binding to the VRF would make every OSPF link in that VRF also receive every *other* link's traffic; binding to the interface still sends/receives correctly within its VRF (Linux's VRF driver applies L3 rules per-device) while actually scoping reception to this one link — see `socket.rs`'s own doc comment for the full incident this fixed (a live DBD sequence-number mismatch storm once two links shared a VRF). Joined to 224.0.0.5 on the link's own local address (`join_multicast_v4`), with multicast loopback explicitly disabled (`set_multicast_loop_v4(false)`) so a router never treats its own Hello as a neighbor. `send_multicast`/`send_unicast` send an already-encoded packet; `recv_packet` strips the IP header raw sockets always deliver on receive (even without `IP_HDRINCL`) using the IHL nibble and also returns the sender's IP (needed for DBD/LSR/LSU/LSAck's unicast replies, unlike Hello which never needed it) |
| `link.rs` | `LinkConfig` (gains `network_type`/`priority`/`kernel_interface` — the real Linux device `socket.rs` binds to: the subinterface itself for a point-to-point attach point (computed purely from config, `reconcile::subinterface_kernel_interface`), or the `BroadcastDomain`'s own bridge/SVI for a broadcast one (queried from `nos-interfaced`, `reconcile::resolve_broadcast_domain`) — part of the wholesale-diffed struct) / `LinkStatus` (an `InterfaceState` — `PointToPoint`/`Waiting`/`Dr`/`Backup`/`DrOther` — plus a `HashMap<Ipv4Addr, NeighborInfo>`, at most one entry on point-to-point; `NeighborInfo` gains `address` and `adjacency: Option<exchange::AdjacencyData>`) / `run` — one link's Hello send ticker, dead-interval tracking (a single `sleep_until` on point-to-point; a `ponytail:`-flagged 1s periodic sweep on broadcast, not N precise per-neighbor timers), (broadcast only) the `Waiting`-state wait-timer plus election triggering, DBD/LSR/LSU/LSAck dispatch (`handle_dbd`/`handle_lsr`/`handle_lsu`/`handle_lsack`, sharing a `finish_neighbor_event` tail that applies `exchange::Action::NeighborEvent`s and restarts negotiation from scratch on a `SeqNumberMismatch`-driven return to `ExStart`), a `RXMT_INTERVAL` retransmit sweep (`retransmit_pending`), and the periodic full-LSDB-to-`Full`-neighbors resend (`flood_full_neighbors`, see the LSA-exchange section above). `LinkManager`, the OSPF analogue of `bgp::session::SessionManager` (much smaller: no shared listener, no auth, no collision resolution), also owns the per-area `Lsdb`s and a background task (started in `new`, running for the process's lifetime) that recomputes self-originated LSAs every 2s (`originate_router_lsas`). `LinkManager::reconcile` diffs desired links by attach-point (restart on any resolved-field change, exactly like `bgp::session::diff_peers`) and treats a link whose driver task ended on its own (e.g. socket-open failure) as "not currently running" so the next resync/re-apply tick respawns it. `neighbor_summaries` emits exactly one row per point-to-point link (even with no neighbor yet) and one row per currently-known neighbor on a broadcast link (zero if none yet) |
| `reconcile.rs` | Steady-state loop: subscribes to `OspfInstances` diffs purely as a resync trigger, always re-fetching the whole config, plus a fixed 10s re-apply tick (same justification as `nos-bgp`'s own `REAPPLY_INTERVAL` — VRF/interface readiness is an external condition no config diff signals). Logs this instance's `router_id`/`routing_table`/areas/profiles, each profile's `cost` (observability only, no behavioral use), and each profile's attached interfaces (`attach_points_for`, unchanged); resolves each `Subinterface.ospf_profile` attach point's VRF/local address (`resolve_vrf`/`resolve_local_address`, mirroring `nos-bgp`'s `resolve_source_address`) plus its `kernel_interface` (`subinterface_kernel_interface`, pure — the physical interface name at `tag == 0`, else `<interface>.<tag>`) and each `BroadcastDomain.ospf_profile` attach point's VRF/local-address/`kernel_interface` (`resolve_vrf`/`resolve_broadcast_domain`, the latter asking `nos-interfaced`'s `GetBroadcastDomain` query for both the SVI address and the domain's real bridge device name in one round trip, rather than reading `Config.broadcast_domains[].addresses` directly, for the same "ask the owning daemon" reasoning `resolve_local_address` already follows — an unresolved bridge name, same as an unresolved VRF/address, is treated as "not ready yet" and retried), and hands the resulting `LinkConfig`s to `LinkManager::reconcile` |
| `server.rs` | Binds `--listen-socket` and serves `OspfRequest::GetNeighbors` from `LinkManager::neighbor_summaries` (backs `nos-cli`'s `show ospf neigh`) — resolved via the watchdog broker's `ServiceRef::OspfInstance`, the same pattern `nos-bgpd`/`nos-ribd`/`nos-interfaced`'s query listeners use |

## Watchdog/broker wiring

`nos-watchdogd` gives every `nos-ospfd` instance a real `--listen-socket` (`/run/nos/ospf-<name>.sock`) and registers it in `EndpointRegistry` under `EndpointKind::OspfInstance` — the `ServiceRef`/registry plumbing that already existed generically (see root `CLAUDE.md`'s "Endpoint broker") is now actually wired up, not just present.
