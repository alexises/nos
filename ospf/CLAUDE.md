# nos-ospf — OSPF Component

OSPF daemon for NOS (binary `nos-ospfd`, one process per `OspfInstance`, dynamically spawned by `nos-watchdog` — see root `CLAUDE.md`'s "Process supervision" section).

## Scope

`nos-ospfd` resolves its own configured instance/areas/profiles from `nos-configd`, and runs a real RFC 2328 Hello protocol on every `Subinterface.ospf_profile` (point-to-point) and `BroadcastDomain.ospf_profile` (multi-access, with RFC 2328 §9.4 DR/BDR election) attach point — a real raw protocol-89 socket, VRF-scoped, joined to the AllSPFRouters (224.0.0.5) multicast group. Adjacency formation now reaches real `Full` state with real LSAs, matching how `nos-bgp` grew from OPEN/KEEPALIVE-only into real route exchange:

- **Neighbor FSM depth**: `Down` → `Init` → `TwoWay` → `ExStart` → `Exchange` → `Loading` → `Full` (`ospf::neighbor::NeighborState`), on both network types — the full RFC 2328 §10.5 ladder. `TwoWay` only advances to `ExStart` once RFC 2328 §7.5/§10.4's adjacency-eligibility rule holds (`link::should_form_adjacency`): unconditionally true on point-to-point; on a broadcast link, only for a DR/BDR-involving pair (a `DrOther`-`DrOther` pair stays at `TwoWay` forever). From `ExStart` onward, `ospf::exchange` drives RFC 2328 §10.6-10.8's DBD master/slave negotiation and summary-list exchange, then real LSR/LSU/LSAck against a per-area `ospf::lsdb::Lsdb` (see below) — now with real RFC 2328 §16.1/§16.2 SPF route computation over what lands in it (`ospf::spf`, see "SPF and route installation" below).
- **Network type**: `Subinterface.ospf_profile` attach points (a VLAN sub-interface modeling one link to one peer) run point-to-point — at most one neighbor, no election, `link::InterfaceState` fixed at `PointToPoint`. `BroadcastDomain.ospf_profile` (multi-access SVI) attach points run broadcast — potentially many neighbors keyed by router-id, a `Waiting` interface state on start (wait-timer = dead-interval), then a real DR/BDR election (`ospf::election::elect`) settling into `Dr`/`Backup`/`DrOther`. A loopback (`Interface.ospf_profile`) attach point still has no peer to Hello with and stays **log-only**, resolved purely from the already-fetched `Config` (`reconcile::attach_points_for`). Hello stays multicast 224.0.0.5 on both real network types (RFC 2328 has no unicast Hello); DBD/LSR/LSU/LSAck are unicast to the specific neighbor's IP (captured from the source address of its last Hello).
- `OspfProfile.network_type: Option<NetworkType>` overrides the type an attach point gets when set; left `None`, it defaults per attach-point kind (`Subinterface` → `PointToPoint`, `BroadcastDomain` → `Broadcast`) — resolved in `reconcile.rs`, not the schema, since one profile can be referenced by attach points of different kinds at once. Never validated against the attach point's actual kind (real OSPF allows forcing either behavior on either kind of link).

`OspfProfile` carries `hello_interval`/`dead_interval`/`priority: Option<u16|u8>` (`None` defaults to `HELLO_INTERVAL_DEFAULT`/`DEAD_INTERVAL_DEFAULT`/`PRIORITY_DEFAULT` — 10s/40s/1, RFC 2328 Appendix C.3), `hello_interval`/`dead_interval` validated (`dead_interval` must exceed `hello_interval` when both are set) the same way `BgpPeerGroup.hold_time`/`keepalive_interval` are, one level up on `OspfArea.profiles` (`ospf_profile::valid_profile_timers`). `priority` governs DR/BDR election eligibility on a `Broadcast` link (`0` means "never eligible") and is sent on the wire (functionally inert) on a `PointToPoint` one too. `cost: Option<u16>` (range `1..=65535`, `None` defaults to `1`) is a real RFC 2328 §16 SPF metric: `link::router_lsa_links`/`originate_router_lsas` use it as this link's (or loopback stub's) Router-LSA link metric, summed along the Dijkstra path by `ospf::spf::compute`. All five fields plus `auth` (see "Authentication" below) are `nos-cli`-editable (`set hello-interval|dead-interval|cost|priority|network-type|simple-password|crypto-key ...` while navigated into an `OspfProfile`, or the fully-qualified form from anywhere — mirrors `BgpPeerGroup.hold_time`'s exact CLI precedent). RFC 2328 Appendix C.3's `RxmtInterval` (how often an unacknowledged LSR/LSU is resent) is a fixed 5s constant (`link::RXMT_INTERVAL`), not yet a sixth `OspfProfile` field — see `link.rs`'s own `ponytail:` note on why.

### Authentication

`OspfProfile.auth: Option<OspfAuth>` is RFC 2328 Appendix D authentication, mirroring `BgpPeerGroup.auth: Option<BgpAuth>`'s exact shape (`OspfAuth::Simple { password }` / `OspfAuth::Crypto { keys: Vec<OspfCryptoKey> }`, `None` == AuType 0/Null) — stored clear-text like every other field. `OspfCryptoKey.algorithm: OspfCryptoAlgorithm` covers both RFC 2328 Appendix D.3's original plain-MD5 scheme (`Md5`, `MD5(packet || key)`, 16-byte digest, no real HMAC construction) and RFC 5709's HMAC-SHA extension (`HmacSha1`/`HmacSha256`/`HmacSha384`/`HmacSha512`, real HMAC per RFC 2104, 20/32/48/64-byte digests) — the wire's AuType is `2` for all five; there's no separate algorithm field on the wire, so a packet's Key ID alone must unambiguously determine which algorithm a receiver uses, exactly like `BgpAoKey`'s key-rotation model (`is_current` marks the key that signs outgoing packets; every configured key is still accepted on receive, looked up by the wire's own Key ID — this is what allows graceful key rollover with no dropped adjacency).

`ospf::packet` (see the Modules table) owns the wire-level mechanics, kept dependency-free of `nos-proto` like the rest of that "pure, no I/O" module — `packet::CryptoAlgorithm` is its own mirror of `nos_proto::OspfCryptoAlgorithm`, converted at the config boundary in `link::LinkAuthConfig` (`reconcile.rs`'s `resolve_auth`). `packet::checksum` now correctly excludes the 8-byte Authentication field (bytes 16..24) from its RFC 1071 sum for Null/Simple auth — a no-op for Null (those bytes are already zero) but load-bearing for Simple, whose password occupies that field on the wire; Crypto auth skips the checksum entirely (RFC 2328 D.4.3: not calculated for that AuType) and instead appends a real digest (`CryptoAlgorithm::digest`, using the `md-5`/`sha1`/`sha2`/`hmac` crates) after the packet, outside the packet's own `length` field's count — `verify_auth` is the shared decode-side counterpart, rejecting an AuType that doesn't match the link's configured policy (`PacketError::AuthTypeMismatch`) or a bad password/digest/unknown Key ID (`PacketError::AuthFailed`).

RFC 2328 D.4.3's anti-replay crypto sequence number is deliberately **not** tracked in `packet.rs` (which stays fully stateless) — `link.rs` owns it instead, since it already owns all other per-neighbor state: `NeighborInfo.last_crypto_seq` records the last-accepted value per neighbor, checked/updated once in `run()`'s single inbound decode call site (`accept_crypto_sequence`, generic across all five packet types via `packet::router_id`) before any `handle_*` dispatch — a non-increasing sequence number is silently dropped and logged (`"ospf packet crypto sequence number not increasing, dropping"`), never treated as a fatal error. The outgoing counter (`next_crypto_seq`, threaded as `&mut u64` through every send path) is seeded from wall-clock unix-seconds at link startup (`crypto_seq_floor`) and bumped by one per packet sent — floored at the current wall-clock value on every bump, so it never regresses even across a link restart (an auth/key change is just another `LinkConfig` field change, so it restarts the link task exactly like any other — the peer rejects the new auth until it's updated too, which is the desired match/mismatch behavior; auth failures log distinctly as `"ospf packet authentication failed"` so `nos-e2e ospf-auth` can assert on them).

**RFC 7474 extended sequence numbers** (`OspfProfile.extended_sequence_numbers`, `set … profile <p> extended-sequence-numbers enable|disable`, provision `--ospf-extended-seq`): `AuType` 3 — 32-bit Key ID, a 64-bit (boot count : counter) number in the 8 octets after the packet (outside the OSPF length, covered by the digest) and `Apad` = IP source address + `0x878FE1F3…` (`packet::ext_digest_input`; the packet's source is threaded in via `OutgoingAuth::Crypto.extended`/`AuthPolicy::Crypto.extended`). It does **not** use an LLS block (issue #43 said so; RFC 7474 doesn't) — RFC 5613 LLS is still unimplemented. Commit-time validation (`valid_profile_timers`) requires crypto auth with HMAC-SHA keys only. The boot count comes from `boot::BootCounter` (`--state-dir`, default `/var/lib/nos/ospf`, file `<instance>.boot`, atomic write) and is taken fresh on **every link (re)start**, not just process start, so a config-driven link restart can't send a lower sequence than before; the low 32 bits carry into it on wrap. Replay check is per neighbor **per packet type** (`NeighborInfo.last_crypto_seq: HashMap<u8, u64>`; the classic `AuType` 2 keeps its single slot). Types 2 and 3 don't interoperate (`AuthTypeMismatch`, logged as an auth failure). Verified by `nos-e2e ospf-auth` (mismatch, both-ends Full, `nos-ospfd` kill/restart with no replay drops). The classic `AuType` 2 HMAC-SHA digests are `HMAC(K, packet || Apad)` per RFC 5709 §3.3 (`packet::classic_digest`/`apad`, pinned by a test that recomputes the HMAC independently; #82) — plain MD5 is `MD5(packet || key)` with the key zero-padded/truncated to 16 bytes (RFC 2328 D.4.3 (a)).

Only MD5 and the RFC 5709 HMAC-SHA family are implemented — no other cryptographic algorithm, and (like the rest of this crate) no multi-area/ABR scope creep alongside it.

### LSA exchange and the LSDB

Once a neighbor reaches `ExStart`, `ospf::exchange` (pure, no I/O, mirroring `bgp::fsm::step`'s transition-returns-actions shape) drives:

- **`ExStart`**: RFC 2328 §10.6 master/slave negotiation — the higher router-id wins master. The two sides' Hello-driven `ExStart` entry is never synchronized (each side reaches it independently, off its own Hello timing), so `on_dbd_in_exstart` accepts *either* a genuine negotiation attempt (I=1,M=1,MS=1) *or* the other side's one reply/poll as the trigger, on **both** sides of the negotiation (would-be master accepting the slave's reply, and would-be slave accepting the master's poll — the latter's own detection no longer requires `more: false`, since a paginated first poll can legitimately still have data left) — a real, common case (on either side) where a peer's original attempt was sent, and lost, before the local side even had adjacency data to receive it into (`handle_dbd` drops a DBD for a neighbor with no adjacency yet), so the only packet ever seen back is that peer's reply/poll to our own (later) attempt. Since that packet is also the only copy of the peer's summary either side will ever see for that specific chunk (a peer already past its own `ExStart` never resends the original attempt), receiving it this way processes that chunk's content immediately too (only `NegotiationDone` fires here, though — never `ExchangeDone`, since with pagination a single chunk is never assumed to be the whole summary; termination is always decided in `Exchange`, see below). The slave-side half of this (accepting the master's poll, not just its attempt) was only added once a real three-router Docker scenario (`ospf-dr`, see root `CLAUDE.md`) exposed it — a newly-joining router's own attempt to a segment's already-converged DR/BDR would otherwise be the only exchange either side ever completed, leaving the third router's other adjacency permanently stuck at `ExStart`.
- **`Exchange`**: real RFC 2328 §10.8 pagination — each side's local LSDB summary (`AdjacencyData.summary_remaining`, seeded once at `ExStart` exit) is chunked into `max_headers`-sized pieces (`exchange::pop_chunk`; the per-process budget is `link::LinkManager`'s `dbd_max_headers`, defaulting to `exchange::DEFAULT_DBD_MAX_HEADERS` — see `main.rs`'s `--dbd-max-headers`), one chunk per DD sequence number: the master increments the sequence number and polls again as long as either side still has data (even sending an empty chunk purely to let the slave keep replying), the slave always replies at the master's latest sequence number with its own next chunk, and the request list accumulates across every chunk from both sides (`compute_request_list`, extended not overwritten). The exchange terminates once both sides have declared `more: false` in the same round. `ponytail:` `max_headers` is a fixed conservative constant sized off a generic Ethernet MTU assumption (`exchange.rs`'s own doc comment), not derived from a live query of the link's real interface MTU — this NOS never enforces `DbdPacket.interface_mtu` on send or receive at all. Empty request list goes straight to `Full`, non-empty goes to `Loading`. A negotiation-shaped duplicate arriving here (the peer's own view hasn't caught up to the fact that negotiation already succeeded) is silently ignored, not treated as a restart signal — treating it as `SeqNumberMismatch` would force both sides to keep re-picking fresh random sequence numbers and restarting in lockstep, an unrecoverable live ping-pong. A genuine peer restart is instead caught via Hello: losing 2-way already clears `adjacency` (`link::handle_hello`).
- **`Loading`**: LSR/LSU/LSAck against the neighbor, via `ospf::lsdb::Lsdb` — one per OSPF area (`LinkManager` holds `HashMap<Ipv4Addr, Arc<Mutex<Lsdb>>>`, never a single flat map, since `OspfArea` is already multi-valued in this schema and a flat LSDB would leak LSAs across areas). `Lsdb::install` only accepts a strictly-newer instance (RFC 2328 §13.1: sequence number, then checksum, then `MaxAge`-is-always-newer). An unrequestable LSA (`BadLSReq`) or an out-of-sequence packet at any point restarts negotiation from `ExStart` (`SeqNumberMismatch`).
- **Self-origination** (`LinkManager::originate_router_lsas`, on a 2s tick, independent of the 10s config-reapply tick): recomputes and reinstalls this router's own Router-LSA per area (one link entry per currently-known link with a neighbor/resolved DR) and a Network-LSA on any broadcast link where this router is DR with ≥1 `Full` neighbor — reinstalling (and bumping the sequence number) either when the content changed, or when the held instance's age has reached RFC 2328 §14's `LSRefreshTime` (1800s) even with unchanged content (see "Aging/refresh/flush" below).
- **Aging/refresh/flush** (RFC 2328 §14): a second per-process background tick in `LinkManager::new` (`AGE_TICK_INTERVAL`, real 1s, independent of `ORIGINATION_INTERVAL`) ages every installed LSA in every area's `Lsdb` by one second — scaled by `age_multiplier` (`LinkManager::new`'s argument, wired from `nos-ospfd`'s `--lsa-age-multiplier`, default `1` — test/debug only, reachable purely via `nos-watchdogd`'s `--ospfd-arg` pass-through, never `OspfProfile`/`nos-cli`) — and evicts (`Lsdb::age_and_evict`) anything that reaches `MAX_AGE` (3600s), logging `"ospf lsa maxage flushed"`. No explicit "premature aging" reflood: this crate has no LSA-withdrawal path (self-origination only ever reinstalls, never removes), so a stale received LSA simply expires on the receiving router's own clock once its originator stops refreshing it — `flood_full_neighbors`'s existing periodic resend already propagates a freshly-refreshed low-age instance. `MinLSArrival`/`MinLSInterval`/`CheckAge` are out of scope: this crate floods on a periodic full-resend, not event-driven, so there's no reflood storm to rate-limit, and every LSA's checksum is already verified once on wire admission.
- **Flooding**: `ponytail:` no real RFC 2328 §13 event-driven flooding (on origination, or on receipt, reaching every adjacent link) — instead, each link periodically (every `RXMT_INTERVAL`) resends its *entire* local-area LSDB to every `Full` neighbor on that link (`link::flood_full_neighbors`). Safe (a non-newer duplicate is cheaply rejected and still acked) and simple, at the cost of up to one `RXMT_INTERVAL` of propagation delay and a little wasted bandwidth on a lab-scale LSDB; it does mean an LSA can validly be first observed as "installed" via either of a router's links when it has more than one in the same area. This remains the permanent design even now that SPF exists (see below): `rib_push_client`'s own fixed 2s poll doesn't need tighter propagation than `RXMT_INTERVAL` already provides, so real event-driven flooding (`exchange::Action::InstallAndFlood`, kept unused as the extension point) still isn't worth the complexity of threading a fan-out channel through every link task. See `lsa.rs` for what Router/Network-LSA bodies this NOS parses/originates and what's deliberately deferred (AS-external/Summary LSAs, multi-area ABR behavior, authentication).
- **Reporting**: `nos_proto::OspfNeighborState`/`NeighborSummary` (`show ospf neigh`) report the full `Down`/`Init`/`TwoWay`/`ExStart`/`Exchange`/`Loading`/`Full` ladder 1:1 (`link::to_neighbor_state`). `show ospf database` (`OspfRequest::GetDatabase`/`OspfEvent::Database`, `LinkManager::database_summaries`) reports every installed LSA's header — type, link-state-id, advertising router, sequence number, age, checksum — across every area, never the full LSA body (SPF reads bodies internally; there's just no operator-facing rendering of one yet).

### SPF and route installation

`ospf::spf::compute(root, lsas)` is a pure RFC 2328 §16.1/§16.2 Dijkstra over one area's LSDB snapshot: vertices are routers (keyed by router-id) and transit networks (keyed by a Network-LSA's `link_state_id`), edges come from Router-LSA type-1/type-2 links (type-3 stub links are leaves, handled in a post-pass) and Network-LSA `attached_routers` (cost 0, per RFC). Next-hop derivation is entirely LSDB-based — no live neighbor-table dependency: a point-to-point/transit-network link's `link_data` is always the *originating* router's own address on that link (RFC 2328 §12.4.1.1), so a neighbor `w`'s address is learned by reading *`w`'s own* LSA for its link back to us, not ours. Every vertex beyond the first hop simply inherits its parent's next-hop unchanged. Destinations directly attached to the root (root's own stub links, or a transit network root itself sits on) are filtered out by `(link_id, link_data)` key, not by reachability — necessary because a point-to-point link's *far end* independently advertises the identical subnet (see below), which Dijkstra will otherwise happily reach through the neighbor.

To give SPF real destination prefixes to compute against — the LSDB otherwise carries pure router-to-router/transit-network topology, zero leaf prefixes — `link::router_lsa_links` now emits a type-3 stub-network link for every point-to-point link's own subnet *unconditionally* (RFC 2328 §12.4.1.1: independent of neighbor state), and `originate_router_lsas` fills in a real `NetworkLsaBody.network_mask` (previously always `UNSPECIFIED`) for a broadcast link's Network-LSA. A loopback (`Interface.ospf_profile`) attach point stays log-only for Hello/adjacency purposes (see above) but now feeds `LinkManager.stub_networks: HashMap<area, Vec<(subnet, cost)>>` (populated by `reconcile.rs`'s `loopback_attach_points`/`resolve_loopback_prefix`), so its own subnet is still advertised as a type-3 stub — the cleanest destination with zero neighbors, and what `nos-e2e ospf-spf` exercises end to end. `LinkConfig` carries the real `local_prefix_len`/`cost` needed for all of this (`OspfProfile.cost`, `None` → `1`).

`LinkManager::compute_routes` runs `spf::compute` per area and merges into one route set — a router attached to 2+ areas (an ABR, see "ABR and Summary-LSA origination" below) can legitimately compute the same prefix from more than one area's own LSDB, so the merge keeps whichever is cheaper rather than a plain overwrite. `rib_push_client.rs` (mirroring `bgp::rib_push_client`'s shape exactly, including its fixed-poll `ponytail:` rationale — `Lsdb` mutates from too many call sites for a single edge-triggered hook) pushes the result to the owning `nos-ribd` instance over `RibRequest::PushOspfRoutes` (`Full` on connect, diffed `Add`/`Remove` every 2s poll after), landing as `RouteSource::Ospf` (admin-distance-style preference `110` — Cisco-convention, beaten by `Static`/`Bgp`) in `nos-rib`'s multi-source `Rib`.

### Loop-free alternates (backup routes)

`spf::compute` also fills `RouteEntry.backup_next_hop` with an RFC 5286 basic loop-free alternate. `spf::alternates` runs one extra `run_dijkstra` rooted at each router adjacent to root (p2p neighbor, or another router on a transit network root sits on); `pick_backup` accepts a candidate whose address differs from the primary next hop and that satisfies `dist(N,E) < dist(N,root) + dist(root,E)` for the route's *egress vertex* `E` (`RouteEntry.egress`, the router/network the metric was built from — the leaf/summary/external metric cancels out of the inequality), choosing the cheapest, ties by address. `ospf::rib_push_client` carries it in `OspfRoute.backup_next_hop`; `nos-ribd` installs it as a second kernel route at `BACKUP_METRIC` (see `rib/CLAUDE.md`), so failover needs no netlink call. `ponytail:` link protection only (no node protection, no remote LFA), one Dijkstra per neighbor per area on every SPF run; `nos-ospfv3d` has its own port (see `ospfv3/CLAUDE.md`). Verified by `nos-e2e ospf-lfa`.

### ASBR and AS-external-LSA origination

`RoutingTable.redistribute` now also accepts `to: Ospf` (alongside the pre-existing `to: Bgp`) — `redistribute from static to ospf` makes this router a real RFC 2328 ASBR. The mechanism mirrors BGP's own redistribution exactly, mirrored end to end: `nos-ribd`'s `ospf_client.rs` (a near line-for-line copy of `bgp_client.rs`) pushes this table's `RouteSource::Static` entries to the owning `nos-ospfd` instance over a persistent connection (`OspfRequest::RedistributeRoutes(RedistributeUpdate)`, fire-and-forget, `Full` on connect then diffed `Add`/`Remove`); `link.rs`'s `LinkManager` holds the raw set (`redistribute_raw`) and a policy-filtered set (`redistribute_filtered`, re-derived by `set_redistribute_policy` on every `reconcile.rs` resync — no `PolicyCache` unlike BGP's, since `OspfInstance.redistribute_policy` is exactly one policy per instance, so compiling fresh every resync tick needs no cache-invalidation logic); `originate_as_external_lsas` (run from the same 2s tick as `originate_router_lsas`) installs a real Type-5 AS-external-LSA (`lsa::AsExternalLsaBody`, RFC 2328 Appendix A.4.5) per redistributed prefix.

**The one new cross-area mechanism in this crate**: since a real AS-external-LSA is domain-wide, not area-scoped like Router-/Network-LSAs, `originate_as_external_lsas` installs each redistributed prefix's Type-5 into *every* area this router is itself attached to (`self.lsdbs`'s full key set) — this is this router replicating its own origination into its own areas, **not** real ABR translation of another router's externally-learned LSA across areas (which remains out of scope, see "Explicitly out of scope" below). No new flooding code was needed: `flood_full_neighbors`'s existing periodic per-link full-LSDB resend already picks up whatever lands in that link's own area's `Lsdb`.

`ospf::spf::compute` gained a third destination-collection pass, `collect_external_routes`, parallel to the existing stub/network passes: for each installed AS-external-LSA, it looks up the advertising ASBR's already-computed intra-area distance/next-hop and adds `EXTERNAL_METRIC_CONSTANT` (a fixed `20`) to it — `spf::insert_best`'s existing tie-break then picks the cheaper of an external route and a stub/network route to the same prefix for free. A guard skips `advertising_router == root` — this router's own Type-5, once installed into its own area, would otherwise compute a spurious route to its own prefix via itself.

Deliberate simplifications (all `ponytail:`-flagged at their point in the code), scoped to keep this a real, correct, appropriately-sized ASBR without pulling in NSSA/ABR work:
- **Redistribution source**: `Static` only, mirroring BGP's own redistribution (which also only supports `Static` today). BGP→OSPF redistribution is unimplemented.
- **Metric semantics**: always Type-1 (ASBR's own intra-area distance + the fixed constant above) — no RFC 2328 §16.4 Type-1/Type-2 metric-type selection, no per-route configurable metric, no Type-1-beats-Type-2 tie-break. This NOS never produces a Type-2 route, so there's nothing to compare against.
- **Forwarding address**: `AsExternalLsaBody.forwarding_address` is always `0.0.0.0` on origination and decoded faithfully on receipt (so a foreign/corrupt LSA never fails to parse), but SPF never resolves a non-zero one to an alternate next-hop — every external route's next-hop is always the advertising ASBR's own next-hop.
- **Router-LSA E-bit**: still hardcoded `0`, unchanged — nothing downstream (no stub-area/ABR logic) reads it yet, so wiring it has zero functional effect right now. (The separate Hello-packet Options-byte E-bit is now real — see `link::handle_hello`'s RFC 2328 §10.5 packet-validity check — but with no stub-area concept on either side it's a comparison against our own constant `OPTION_E`, not yet a meaningful per-area setting.)
- **LSA withdrawal**: none, consistent with this crate's existing LSA model for Router-/Network-LSAs — when a redistributed prefix disappears, this router simply stops re-originating its Type-5; it ages out over up to `MAX_AGE` (3600s) like every other LSA type already does.

`nos-e2e asbr` (requires `ospf` to have already run) exercises this end to end: a static route + `redistribute from static to ospf` on router-a, confirming a real Type-5 origination, router-b installing it into its own LSDB over the real adjacency, and router-b's own SPF pushing a real kernel route for it via `nos-ribd`.

### ABR and Summary-LSA origination

A router attached to 2+ `OspfArea`s at once (already fully supported by the config/reconcile layers — `LinkManager.lsdbs` is already keyed per area) is a real RFC 2328 Area Border Router by this NOS's purely-derived definition: `LinkManager::originate_summary_lsas` checks `self.lsdbs.keys().len() >= 2` on every 2s origination tick, no config flag, mirroring how this crate already derives DR-ness/ASBR-ness from live state rather than a schema field. When true, it computes each area's own **intra-area-only** view (`spf::intra_area_routes` — Dijkstra plus only the stub/network collector passes, explicitly excluding external/summary-derived routes: RFC 2328 forbids re-summarizing an already inter-area or already-external route, which is what prevents trivial two-area routing loops) and, for every *other* area the router touches, installs a fresh Type-3 network-summary LSA (`lsa::SummaryLsaBody`, RFC 2328 Appendix A.4.4) per intra-area prefix and a Type-4 ASBR-summary LSA per genuinely-in-that-area ASBR (any router-id with an installed Type-5 that's actually reachable via that area's own Dijkstra) — both freshly self-originated (advertising router is always this router's own id), not a raw copy of another router's LSA. No new flooding code was needed, exactly like Type-5 needed none: `flood_full_neighbors`'s existing periodic per-link full-area-LSDB resend already picks up whatever lands in that area's `Lsdb`.

`ospf::spf::compute` gained a fourth destination-collection pass, `collect_summary_routes`, parallel to `collect_external_routes`: for each installed Type-3 in this area, it looks up the advertising ABR's already-computed intra-area distance/next-hop and adds the summary's own metric — `insert_best`'s existing min-metric tie-break then competes it against stub/network/external routes to the same prefix for free, the same precedent `collect_external_routes` already established (no strict RFC 2328 §16.4 intra→inter→external class preference, just raw metric competition). `collect_external_routes` itself gained a Type-4 proxy fallback (`spf::asbr_distance`): if an AS-external-LSA's advertising ASBR has no direct intra-area Router-LSA vertex in this area (it's genuinely attached in another area), it falls back to an installed Type-4 for that ASBR in this area — distance is that Type-4's advertising ABR's own intra-area distance plus the Type-4's metric, next-hop is the ABR's own next-hop (packets to a foreign ASBR go via the ABR proxying reachability to it); multiple Type-4s for the same ASBR take the cheapest. A guard skips `advertising_router == root` in `collect_summary_routes`, mirroring `collect_external_routes`'s own `asbr == root` guard — this router's own self-installed Type-3 must never route to its own summarized prefix via itself.

Deliberate simplifications (all `ponytail:`-flagged at their point in the code), scoped the same way the ASBR feature was — a real, correct, appropriately-sized 2-area ABR mechanism without pulling in NSSA/full-mesh-loop-prevention work:
- **No stub/NSSA areas, no virtual links, no area-range/route-summarization aggregation config** — every intra-area prefix is summarized as-is, one Type-3 per prefix, never aggregated into a covering range.
- **No RFC 2328 up/down-bit loop-prevention machinery** — correct for the 2-area topology this is designed/tested against (one non-backbone area behind a single ABR); a 3+-area topology with multiple ABRs could in theory re-summarize an already-inter-area route back across a third area, since `intra_area_routes` only excludes *this router's own* external/summary-derived routes, not another ABR's.
- **`intra_area_routes` doesn't summarize root's own directly-attached transit networks** (only stub networks) — a router won't advertise reachability to a broadcast segment it's itself sitting on into its other areas. This NOS's concrete ABR scenarios (a loopback stub, a redistributed prefix) never need it.
- **No strict intra→inter→external route-class precedence** beyond raw metric competition — matches the existing external-route precedent (`insert_best`).
- **No LSA withdrawal** — consistent with this crate's existing LSA model: when a prefix stops being intra-area to some area, this router simply stops re-summarizing it; it ages out over up to `MAX_AGE` (3600s) like every other LSA type already does.

`nos-e2e abr` (requires `ospf-spf` to have already run — it reassigns that scenario's own loopback into a second area, at a distinct address, since `nos-ribd`'s route diffing needs a genuinely new prefix to log a fresh kernel-install event) exercises this end to end: router-b's loopback moves from the backbone into a real second area, making router-b a genuine ABR; router-b originates a real Type-3 for it; router-a (backbone-only) learns and installs that Type-3 into its own LSDB over the real adjacency; and router-a's own SPF computes and pushes a real kernel route for a prefix that isn't in its own area at all, purely via router-b's summary.

## Watchdog/broker wiring

`nos-watchdogd` gives every `nos-ospfd` instance a real `--listen-socket` (`/run/nos/ospf-<name>.sock`) and registers it in `EndpointRegistry` under `EndpointKind::OspfInstance` — the `ServiceRef`/registry plumbing that already existed generically (see root `CLAUDE.md`'s "Endpoint broker") is now actually wired up, not just present.
