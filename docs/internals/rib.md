# RIB internals

How `nos-rib` is built, moved from `rib/CLAUDE.md` (#264) so the always-loaded file keeps only rules and pitfalls. The rules to respect when editing the crate are in [`rib/CLAUDE.md`](../../rib/CLAUDE.md).

## Scope

The internal `Rib` (`src/rib.rs`) is multi-source (`RouteSource::Static` / `RouteSource::Bgp` / `RouteSource::Ospf` / `RouteSource::Connected` / `RouteSource::Evpn`, the last described in "EVPN IP-VRF" below), each populated by its own independent writer: `reconcile::resync` rebuilds the whole `Static` side from config on every resync — and the whole `Connected` side (preference 0, below `Static`) from what `nos-interfaced` applied, via `interface_client.rs` (`InterfaceRequest::GetInterfaces` for every `Interface`/`Subinterface` address in this table, `GetPortAggregates` for aggregate subinterfaces — only when the config puts one in this table — plus `GetBroadcastDomain` per SVI-carrying domain of this table, resolved through `ServiceRef::Interfaces`; a failed call keeps the previous set, like `nos-bgpd`'s `igp_client`) — and `server::apply_bgp_route_update`/`apply_ospf_route_update` apply `RibRequest::PushBgpRoutes`/`PushOspfRoutes` — sent by the owning `nos-bgpd`/`nos-ospfd` instance over a persistent connection, `Full` on connect then incremental `Add`/`Remove` (`bgp::rib_push_client`/`ospf::rib_push_client`, mirroring this crate's own `bgp_client.rs` for the reverse direction) — incrementally. `Rib::replace_source`/`upsert`/`remove` are all scoped to one `RouteSource`, so no writer can clobber another's candidates; `best_routes_for_kernel()` merges them for `driver.apply` — every prefix's winner, except a prefix whose winner is `Connected`, which is left to the kernel whole: a `Static`/`Bgp`/`Ospf` candidate for a connected prefix is listed but never installed (#139 — for IPv4 it would only collide with the kernel's own route, `EEXIST`, on every reapply), the same view the delta path's `best_route` takes. A connected prefix is never installed by this daemon: the kernel adds its own on-link route the instant `nos-interfaced` applies the address (a `Connected` entry's one next hop is that local address, display only), and `driver::linux::extract_route` already skips gateway-less kernel routes as unmanaged, so it never shows up on either side of the dump-diff. The source exists for `igp_costs()` (cost 0, like `Static`), which is how `nos-bgpd` tells a directly-connected next hop from an unresolvable one (RFC 4271 §9.1.2, `bgp-internals.md`'s "Next-hop feasibility"); `best_routes()` (every source) still serves `show route`, where it renders as `connected`.

This crate also **redistributes the other direction**: `reconcile::compute_redistribute_target`/`compute_redistribute_target_ospf` filter this table's `RouteSource::Static` candidates against `RoutingTable.redistribute` (a list of rules, one per `to`: each of `Bgp`/`Ospf`/`Ospfv3` is evaluated independently, so one table can feed several; `Ospfv3` is IPv6 only) and publish the result to `bgp_client.rs`/`ospf_client.rs` (near-identical, each mirroring the opposite-direction push above), which forward it over a persistent `BgpRequest::RedistributeRoutes`/`OspfRequest::RedistributeRoutes` connection to the owning `nos-bgpd`/`nos-ospfd` instance — the mechanism that makes `redistribute ospf` a real RFC 2328 ASBR (see `ospf-internals.md`'s "ASBR and AS-external-LSA origination").

**OS application is now real**, via a swappable `driver` (`src/driver/`, see below) — `--driver linux` (the default on Linux) creates an actual Linux VRF device + kernel routing table per routing table and installs the winning route per prefix into it; `--driver noop` (the default off-Linux) keeps the old log-only behavior for tests/dev. Only the *best* route per prefix is ever installed to the kernel — `Rib`'s multi-candidate view stays a query-serving concern.

There is an external query API: `server.rs` serves `nos_proto::rib::{RibRequest, RibEvent}` for `nos-cli`'s `show route` command (see `docs/architecture/endpoint-broker.md` for how a client finds this instance's socket), plus `GetVrfName` — the first direct daemon-to-daemon IPC link in this codebase, letting `nos-interfaced` ask this instance for its Linux VRF interface name so it can enslave interfaces into it by name — and `GetTableId`, symmetric to `GetVrfName`, letting `nos-interfaced` learn this table's raw numeric kernel table id so it can name a loopback interface's kernel device (`lo<table_id>`). `PushBgpRoutes` is fire-and-forget (no reply), from the one `nos-bgpd` instance the config schema allows to claim this table (`bgp_instance_reference_valid` enforces at most one `RoutingTable` per `BgpInstance`) — `server.rs` no longer trusts whatever arrives: the socket is mutually authenticated TLS, and `allowed(role, &request)` restricts `PushBgpRoutes` to the `bgpd` role and `PushOspfRoutes` to `ospfd`/`ospfv3d` (both OSPF daemon families push OSPF-sourced routes), queries to `user`/`restd`, and `GetVrfName`/`GetTableId` to the daemons that resolve a VRF through this instance. It is role-level only — a `bgpd` for another instance could still push into this table (`ponytail:` in `server.rs`). A refused request is logged with the peer's role and name and the connection closed. `bgp_client.rs`/`ospf_client.rs` dial the owning daemons with the name-checked `nos_pki::connect(.., Role::Bgpd/Ospfd, &name)`.

## L3VPN VRF import (#579)

- `RouteSource::Vpn` (preference 200, like `Evpn`) is written only by `server::apply_vpn_route_update` from `RibRequest::PushVpnRoutes`, the underlay `nos-bgpd`'s `vpn_push_client`. `Full` is `replace_source(Vpn)`, so a CE-facing `PushBgpRoutes` and the VPN feed never wipe each other.
- `RibEntry.mpls_labels` holds the label stack (part of equality). The PE and RD sit beside `entries` in `Rib.vpn_info` (display only), rendered by `show route` as `via <gw> pe <pe> rd <rd> label <n> [vpn]`.
- Not installed yet: `kernel_visible` drops a `Vpn` winner from `best_routes_for_kernel` and from `diff_best` (a `Bgp` winner falling back to a `Vpn` one is a kernel `Removed`). `ponytail:` #581 installs it as an MPLS route and drops the filter.
- `Rib::resolve(addr)` answers `RibRequest::ResolveNextHop`: the best non-`Bgp`/`Evpn`/`Vpn`, non-discard candidate of the longest covering prefix (`resolving_best`, shared with `igp_costs`), its first next hop, or `addr` itself with no ifindex for `Connected`.

## L3VPN VRF export (#580)

- Config (`vpn::resolve`, from `reconcile::vpn_export` each resync): RD, export RTs and `vpn.bgp_instance` (never `table.bgp_instance`); idle without RD and instance.
- Label: an explicit `vpn.label` wins and is not persisted. Otherwise `driver::table_registry::ensure_label`: the `labels` map of the table-id registry file, same `fs2` lock, smallest of 1000..=1048575 that no other table holds and no table configures explicitly (a persisted label that became someone's explicit one is replaced). Never freed. `info!` `vpn label allocated table=… label=…` once. A failed allocation keeps the previous export. Kept in `Rib.vpn_label` for `RibRequest::GetVpnLabel` (`user`/`restd`, `show route`'s `VPN label:` header).
- Export (`vpn::originated`): one `VpnPrefix` per best route (`best_routes`, connected included) except `Vpn` (the loop guard) and `Evpn` ones, with `[label]` and the export RTs.
- Push (`vpn_client.rs`): `BgpRequest::RedistributeVpnPrefixes { table, update }` to the underlay `nos-bgpd`. The connection loop is `push_client.rs`, shared with `evpn_client.rs` (a `Feed` per kind): `Full` on connect, diffed `Add`/`Remove` after, `Full([])` when the instance changes or `vpn` goes, the connection read for EOF. Log `sent initial vpn snapshot to nos-bgpd table=… bgp_instance=… routes=…`.
- `ponytail:` refreshed on resync (config diff or 10s tick), not on each `PushBgpRoutes`/`PushOspfRoutes`, like the Type-5 export; no RPL on export (#582).

## EVPN IP-VRF (L3 VNI)

A table with `RoutingTable.evpn.l3_vni` set is an RFC 9136/9135 §4.4.1 "interface-less" IP-VRF, and this daemon owns all of it — it is the only one allowed to put gateway routes in the VRF, already knows every route to originate, and has `CAP_NET_ADMIN`. No new daemon, no watchdog change.

- **Config** (`reconcile::resolve_l3vni`): the parsed RD/RTs plus the VTEP from `vtep_source` (`interface_client::resolve_vtep`, duplicates `nos-fdbd`'s; `loopback` is `lo<id>` of the table owning `evpn.bgp_instance`, asked of *that* table's `nos-ribd` with `GetTableId` — `ribd`/`fdbd` are now allowed it). An unresolvable VTEP keeps the previous `EvpnState.local`, so a transient `nos-interfaced` failure doesn't tear the devices down.
- **Devices** (`RibDriver::sync_l3vni`, `LinuxRibDriver::build_l3vni`): a bridge `brv<vni>` enslaved to the VRF, `vx<vni>` on it (`local <vtep> dev <underlay> dstport 4789 nolearning`, `nos-fdbd`'s reopen-on-underlay-VRF-change rule copied). The bridge's MAC, read back after enslaving, is our Router's MAC. Per remote VTEP: a permanent `extern_learn` neighbour `<vtep> lladdr <rmac>` on the bridge and an FDB entry `<rmac> dst <vtep> via <underlay>` (`self master extern_learn`) on the VXLAN device, re-asserted every pass and removed when no installed route uses that VTEP any more. `l3_vni` gone (or changed) deletes both devices; so does `teardown`. Log anchors: `created l3 vni vxlan device`, `evpn remote vtep installed|removed`, `deleted l3 vni devices`.
- **Received** (`RibRequest::PushEvpnRoutes`, `bgpd` only, from the underlay instance's `fdb_push_client` `Feed::Tables`): kept raw in `EvpnState.received`; `evpn::desired` keeps a route only with an import RT, our VNI, a Router's MAC, a next hop that isn't our VTEP and the VTEP's address family, one PE per prefix (lowest VTEP), and `Rib::refresh_evpn` makes them `RouteSource::Evpn` candidates (preference 200, below `Ospf`; excluded from `igp_costs`). `LinuxRibDriver::add_route` installs an `Evpn` slot `via <vtep> dev brv<vni> onlink`. `server::apply_evpn_route_update` and `reconcile::resync` both end in `reconcile::apply_to_kernel`: `sync_l3vni` first (the routes leave through its bridge), then `apply`.
- **Symmetric IRB** (RFC 9135, #188): a received Type-2 MAC+IP whose Label2 (`EvpnRoute.l3_vni`) is our L3 VNI goes through the same `evpn::desired` filters and becomes a `/32`/`/128` `Evpn` host route in the same `best` map (so a Type-5 /32 and a host route for one address dedupe on lowest VTEP). `nos-bgpd`'s `Feed::Tables` sends these next to the Type-5s. The other half: `RibRequest::GetEvpnIrb` (`fdbd` only) answers `EvpnState::irb()` — L3 VNI, Router's MAC, export RTs, `None` until both `local` and `rmac` are set — which a domain's `nos-fdbd` asks when its SVI is in this table, to stamp its MAC+IP routes.
- **Originated** (`evpn::originated` → `evpn_client.rs`): one Type-5 per best route that isn't `Evpn`-sourced (the loop guard), connected subnets included, with the RD, export RTs, `ENCAP_VXLAN` and `router_mac_ext(rmac)`, next hop = VTEP, sent as `BgpRequest::RedistributeEvpnPrefixes { table, update }` to `evpn.bgp_instance` (`Full` on connect, diffed after, the connection read for EOF). Idle until the driver gave a Router's MAC (never with `--driver noop`).
- `show route` renders an `Evpn` candidate `via <vtep> rmac <mac> vni <n> [evpn]` (`RouteEntry.evpn`). Verified by `nos-e2e evpn-l3` (two PEs, hosts ping across the L3 VNI; its symmetric IRB stage routes to a host of a stretched domain over the L3 VNI) and `evpn` (GoBGP's Type-5 and symmetric MAC+IP installed).
- **Ceilings** (`ponytail:` in `evpn.rs`): same-family prefix (or host) and VTEP only; no ECMP across PEs advertising one prefix, and a host's ESI is ignored (no aliasing for host routes); no gateway-IP/ESI overlay index (`nos-bgpd` drops those); no RPL on origination; the server's push and the 10s resync can both run `sync_l3vni` at once (a racing create is an error the next tick fixes).

## Failed route ops

`LinuxRibDriver` runs every add/remove of a pass to completion (`drain`, bounded by `MAX_CONCURRENT_ROUTE_OPS`) and only then returns the first error: one failed route no longer cancels the rest, a failed remove no longer skips the add phase, and `installed` keeps the kernel's slot for each failed op (`apply_delta` updates it per op as each succeeds). Each failure is still logged once (`failed to add route`/`failed to remove route`).

## Backup routes

`RibEntry.backup` (from `BgpRoute`/`OspfRoute.backup_next_hop`) is part of the entry's equality, so a backup-only change re-installs the winner. Only the winning entry's backup is installed. `LinuxRibDriver` treats each prefix as two kernel *slots* — `(prefix, false)` the primary at the default priority, `(prefix, true)` the backup at the family's backup metric (`BACKUP_METRIC_V4` 1000, `BACKUP_METRIC_V6` 2000 — an IPv6 primary is 1024, so 1000 would beat it), with `RibEntry.backup_interface_id` as its `RTA_OIF` (a link-local IPv6 backup needs one, and it may differ from the primary's) — through `slots()`, so `diff_routes`, `installed`, `apply_delta` and the dump (`extract_route` reads `RTA_PRIORITY`) all work per slot. The kernel keeps both routes in the FIB and falls to the backup the instant the primary is withdrawn or its link drops. `show route` renders `backup <gw>`. `ponytail:` metric-based failover only reacts to the primary *route* disappearing (link down, session/adjacency loss), not to an unreachable next hop behind a live link — that would need BFD or kernel nexthop groups.

## Tunnel backups (RFC 7490 remote LFA)

- `OspfRoute.backup_tunnel` (a PQ node's loopback) becomes `RibEntry.backup` with `backup_tunnel` set (`server::ospf_entry`); it is part of equality like `backup`. `show route` renders `backup tunnel <pq>`, REST `backup_tunnel: true`.
- **Device**: `RibDriver::sync_tunnel`, called on every resync with `reconcile::remote_lfa` (the table's OSPF instance has `remote_lfa`; the subscription includes `DiffScope::OspfInstances`). `LinuxRibDriver` keeps one `rlfa<table-id>` device per table: an NBMA ipip (no remote, no local) with `link` = the VRF device, enslaved in it, MTU 1480, address `192.0.0.8/32 scope host` (RFC 7600's dummy address: without any IPv4 address every `rp_filter` mode drops decapsulated packets). Deleted when the setting goes and on `teardown`. Logs `created|deleted remote lfa tunnel device`.
- **Route**: the backup slot is `via <pq> dev rlfa<id> onlink` at `BACKUP_METRIC_V4`: an NBMA tunnel takes the route's gateway as the outer destination, and its `link` makes the outer lookup use the VRF table. `add_route` gets a `tunnel` flag (deferred like an `Evpn` route until the device exists); the dump reads it back as an ordinary gateway backup slot. `added route … tunnel=true`.
- **Dump hygiene** (found by `nos-e2e ospf-remote-lfa`): `extract_route` skips `RTM_F_CLONED` entries (the PMTU exception a tunnel creates is dumped beside its route and used to look like a stale primary), and `reconcile_routes` clears `RTNH_F_ONLINK` from a dumped message before deleting it (the kernel answers ESRCH otherwise; `Evpn` routes are onlink too).
- Why not `ipip external` + `encap ip dst`: collect_md looks the outer packet up in main, never in the VRF (#187's kernel spike), and allows one device per netns.
- `ponytail:`s: the device decapsulates IP-in-IP from any source (no filtering); strict `rp_filter` on a PQ node still drops; with two rLFA tables on one router, decapsulation picks the first device's VRF.

## Discard routes

- An `OspfRoute` with `discard` set (an OSPF ABR's active advertised area range, see `ospf-internals.md`) becomes a `RibEntry` with **no next hop** (`server::ospf_entry`, `RibEntry::is_discard`) and no backup. Best-path selection is unchanged.
- `LinuxRibDriver::build_route` installs an empty-hop primary slot as `RTN_BLACKHOLE` (no gateway, no `RTA_OIF`); `extract_route` reads a dumped blackhole back as a managed slot with no gateway only when it carries `RTPROT_STATIC` (every route this driver builds does) — an operator's `ip route add blackhole` (`proto boot`) or a VRF recipe's `unreachable default` is left alone. A prefix switching between discard and real is a del+add, like a changed gateway. `added route`/`removed route` log `discard=true`.
- `igp_costs` skips discard entries: a BGP next hop that only resolves through a range's blackhole is unresolvable (RFC 4271 §9.1.2), not selectable-then-dropped.
- `show route`/`RouteEntry.discard` render `discard` instead of `via <gw>`. Verified by `nos-e2e ospf-stub`.

## Equal-cost multipath

`RibEntry.next_hops` (from `OspfRoute.next_hops`/`BgpRoute.next_hops`; one element for `Static`/`Connected`) is the primary slot's value: `LinuxRibDriver::build_route` emits `RTA_GATEWAY` (+`RTA_OIF`) for one hop and `RTA_MULTIPATH` for two or more, and `extract_route` reads the gateways back from either — a multipath route has no top-level `RTA_GATEWAY`, and without that it would look unmanaged (re-added with EEXIST every `apply`, never deleted). Slots compare by their sorted gateway list (a dump has no `interface_id` of ours), so a changed set is a del+add like a changed gateway; the `added route` log line carries `gateway=<a>,<b>` and `next_hops=<n>`. Best-path selection is unchanged — one source wins per prefix with its own set (OSPF's equal-cost SPF, or BGP multipath, `bgp-internals.md`). The set is part of equality, so a flapping equal-cost sibling re-installs the prefix, like `backup`. `ponytail:` a set change is a del+add of the primary slot (a brief gap; `NLM_F_REPLACE` would make it hitless), more visible with BGP churn than with OSPF; a next hop whose link goes down stays in the multipath route until SPF reconverges (the kernel keeps linkdown nexthops unless `ignore_routes_with_linkdown` is set) — the same class of limitation as metric-based failover below. IPv6 multipath round-trips through `RTA_MULTIPATH` (`ipv6_ecmp_route_round_trips_through_multipath`); old kernels that dump IPv6 ECMP as sibling routes instead are not supported.

## Modules

| Module | Role |
|--------|------|
| `main.rs` | Arg parsing (`--table`, `--watchdog-socket`, `--listen-socket`, `--driver`, `--table-registry-path`), resolves `nos-configd`'s address via the watchdog broker before starting, SIGINT+SIGTERM shutdown wait, spawns `reconcile::run` and `server::start` sharing one `Arc<RwLock<Rib>>` and the driver |
| `evpn.rs` | The EVPN IP-VRF's pure part: `L3Vni` (resolved config), `EvpnState` (on `Rib.evpn`), `desired` (received Type-5 → `Evpn` candidates + remote VTEPs), `originated` (best routes → Type-5) — see "EVPN IP-VRF" |
| `evpn_client.rs` | Pushes `originated`'s Type-5 routes to the underlay `nos-bgpd` (`RedistributeEvpnPrefixes`) over `push_client` |
| `vpn.rs`, `vpn_client.rs` | L3VPN VRF export: `VrfExport`/`resolve`/`originated`, and its push (`RedistributeVpnPrefixes`) over `push_client` |
| `push_client.rs` | The origination push loop shared by `evpn_client` and `vpn_client` (`Feed`, `Target`, `diff`) |
| `rib.rs` | `RouteSource`, `RibEntry`, `Rib` (best-path selection: `best_route`/`best_routes` for the winner only, `all_routes`/`lookup` for every candidate per prefix — the latter used to serve `RibRequest`), `build_from_config` |
| `driver/mod.rs` | `RibDriver` trait (`apply`, `teardown`, `vrf_name`, `table_id`, `sync_l3vni`, `sync_tunnel`) and `DriverError` — the swappable OS backend, so a future non-Linux/hardware driver can be added without touching `reconcile.rs` |
| `driver/noop.rs` | `NoopRibDriver` — today's original log-only behavior |
| `driver/linux.rs` | `LinuxRibDriver` — real `rtnetlink` calls: creates/ups the VRF link, diffs live kernel routes in that table against the desired best-path set and adds/removes the difference |
| `driver/table_registry.rs` | `nos-ribd`'s **own private** persisted state (`--table-registry-path`, default `/var/lib/nos/ribd/table-ids.yaml`): allocates a kernel table id (100–252, avoiding Linux's reserved 0/253/254/255) for this table's name on first use and remembers it across restarts, so a crash/restart recreates the same VRF name. Exclusively locked (via `fs2`) around the allocate-and-persist sequence since multiple `nos-ribd` instances share this one file. **No other process ever reads this file** — see `GetVrfName` above for how `nos-interfaced` learns the name instead. |
| `bgp_client.rs` | Owns the redistribution-push connection to this table's `nos-bgpd` instance (`RedistributeTarget`, `spawn`, full/incremental diffing); reads the connection for EOF so a restarted `nos-bgpd` gets a fresh `Full` at once (#12 — it used to get nothing until the next route change) — see the Scope section's "redistributes the other direction" |
| `ospf_client.rs` | The OSPF-redistribution analogue of `bgp_client.rs`, near line-for-line — one task per family (`Peer`: `OSPFV2` → `nos-ospfd`, `OspfRequest::RedistributeRoutes`; `OSPFV3` → `nos-ospfv3d`, `Ospfv3Request::RedistributeRoutes`, IPv6 routes only — `reconcile::compute_redistribute_target_ospf`'s `to`) |
| `interface_client.rs` | One-shot `get_interfaces`/`get_port_aggregates`/`get_broadcast_domain` — the client side of `InterfaceRequest::GetInterfaces`/`GetPortAggregates`/`GetBroadcastDomain` (mirroring `nos-bgp`'s `interface_client.rs`), from which `reconcile::connected_entries` derives this table's `Connected` candidates on every resync |
| `reconcile.rs` | Steady-state loop: subscribes to `RoutingTables`/`StaticRoutingInstances` diffs purely as a resync trigger, always re-fetching the whole config and rebuilding this table's `Static` candidates from scratch via `Rib::replace_source` (never touching any `Bgp`/`Ospf`-sourced candidate) rather than applying diffs incrementally (diffs carry only display strings, not structured route data), and its `Connected` candidates the same way from `interface_client` (`connected_entries`, pure and unit-tested — so a new address is visible within one `REAPPLY_INTERVAL` at worst); calls `driver.apply` with the recomputed best routes (`best_routes_for_kernel`), and publishes `bgp_client`/`ospf_client`'s `RedistributeTarget`s via `compute_redistribute_target`/`compute_redistribute_target_ospf`. Also re-applies on a fixed 10s timer even without a new diff — a config commit is not the only thing that can require re-applying (e.g. the VRF just didn't exist yet on an earlier attempt, or kernel state drifted out of band); this also re-affirms `Bgp`/`Ospf`-sourced routes against kernel drift for free. On exit, calls `driver.teardown` to delete the kernel VRF + its routes — this runs on **every** SIGINT nos-watchdog sends (both an ordinary restart and a real table removal look identical to this process), which is why `teardown` never touches the table-id registry: the next `apply` must recreate the exact same VRF name. |
| `server.rs` | Binds `--listen-socket` and serves `RibRequest::GetRoutes`/`Lookup`/`GetVrfName`/`GetTableId` from the shared `Arc<RwLock<Rib>>` (read-locked per request) and driver (`driver.vrf_name`/`driver.table_id`), `BgpRouteCount` (`bgpd` only — how many `Bgp` candidates the table holds, `Rib::count_source`; a restarted `nos-bgpd` asks it once to tell whether its forwarding state survived, RFC 4724 §4.1, `bgp-internals.md`'s "Graceful restart"), plus the fire-and-forget `PushBgpRoutes`/`PushOspfRoutes` (`apply_bgp_route_update`/`apply_ospf_route_update`): applies the update to the `Bgp`/`Ospf` side of the shared `Rib` and calls `driver.apply` itself, independent of `reconcile.rs`'s own periodic apply — safe since `apply` is an idempotent dump-diff-converge operation and every writer only ever touches its own disjoint `RouteSource` candidates. |

`table.bgp_instance` is deliberately never read by `build_from_config` — `Bgp`-sourced entries only ever arrive via `PushBgpRoutes`, never from config.
