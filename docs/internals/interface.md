# Interface reconciliation internals

How `nos-interface` is built, moved from `interface/CLAUDE.md` (#264) so the always-loaded file keeps only rules and pitfalls. The rules to respect when editing the crate are in [`interface/CLAUDE.md`](../../interface/CLAUDE.md).

## Scope

Applies configured interface state (addresses, admin-up, VRF enslavement) to the OS through a swappable **driver** (`driver::InterfaceDriver`), selected via `--driver` (default `linux` on Linux, `noop` elsewhere/for tests):
- `driver::noop::NoopInterfaceDriver` — logs the state that would be applied; no OS effect. Today's original placeholder behavior, kept as the portable default.
- `driver::linux::LinuxInterfaceDriver` — the real implementation, via the `rtnetlink` crate. Only ever *configures* an ordinary interface already present in the netns (see "Why one process for all interfaces" below) — it never creates one. The two deliberate, narrow exceptions are a **loopback interface** and **broadcast-domain bridges/802.1q sub-interfaces**, both described below. Diffs live kernel state (addresses, current master) against desired state on every call rather than trusting any cached record of what it applied last, which makes it self-healing against out-of-band kernel drift. MTU: `desired.mtu.unwrap_or(DEFAULT_MTU)` (1500, `driver/mod.rs`) is enforced on every link and bond, set (and logged, `applied interface mtu`) only when the link's `IFLA_MTU` differs — except a bond member with no `mtu`, whose MTU the bonding driver sets from its bond. Address reconciliation never touches a kernel-reported address at scope `Link` (e.g. IPv6 link-local) — NOS only owns addresses it put there itself. `Interface.addresses`' per-address `label` (`nos_proto::InterfaceAddress`) is stored but not yet applied to the kernel (no `ip addr ... label` call) — future work. Requires `NET_ADMIN`/`NET_RAW`; see the `Dockerfile`/`docker-compose.yml`.

  A loopback interface: an `Interface` whose config `name` starts with `loopback-` (`nos_proto::LOOPBACK_PREFIX`/`loopback_table_name` — the routing table it's for is the rest of the name, e.g. `loopback-rt1` is for table `rt1`; there is no separate "kind" field). For that one case, the driver creates (and later deletes) a `dummy` kernel device named `lo<table_id>` — never the interface's own config name, mirroring how `nos-ribd`'s VRF kernel name (`vrf<table_id>`) is independent of `RoutingTable.name` — since Linux only ever has one real `lo` per network namespace.

  **L2 switching (bridges/802.1q) and L3 routed subinterfaces, unified per tag.** `Interface.switching_profile` names a `SwitchingProfile` (a trunk-style list of `(broadcast_domain, tag)` memberships — see `nos_proto::schema::switching_profile`) — L2 config, unchanged, still a physical-interface-level field. `Interface.subinterfaces: Vec<Subinterface>` is L3 config instead: `tag == 0` is the untagged/native case, applied directly to the physical (or loopback) link exactly like the old flat `Interface.addresses`/`routing_table` fields it replaced; `tag` in `1..=4094` is a real 802.1q VLAN, realized the same way a `Dot1q` switching-profile member is — its own `<interface>.<tag>` kernel sub-interface. Because a `BroadcastDomain` is one L2 domain but two different interfaces can tag it with two *different* local dot1q values (the tag is locally significant per interface, not a global property of the domain), the driver creates **one Linux bridge device per configured `BroadcastDomain`** — never a single shared 802.1Q-aware bridge with one global VID→domain mapping.

  **The domain's own SVI.** `BroadcastDomain.addresses`/`routing_table` (same flat shape as a loopback `Interface`'s L3 config — a domain's bridge has no VLAN/tag concept of its own) make the bridge device itself an SVI (switch virtual interface), a routed L3 attachment point for the domain as a whole. `ensure_broadcast_domain` reconciles these directly onto the bridge with the identical `reconcile_addresses`/`reconcile_master` calls `apply` already makes for a physical/loopback link — a `BroadcastDomainState` (mirroring `nos_proto::BroadcastDomain`) carries them from `state::build_from_config` alongside the domain's name. The bridge and whatever interfaces are enslaved into it as L2 members are separate Linux links, so there is no conflict between a domain's own VRF assignment and any member's.

  **Port aggregates (static and LACP bonding).** `PortAggregate` is a named Linux bonding device. Structurally it has the identical config surface as a *physical* `Interface` (`switching_profile`/`mtu`/`subinterfaces` — never `addresses`/`routing_table` flat, since a bond is never a loopback), so `ensure_port_aggregate` reuses `apply`'s own post-link-resolution body verbatim via a shared helper, `reconcile_physical_link` (find-or-create the bond device itself, `LinkBond::new(&ifname).mode(...)`, then the identical addresses/master/tagged-subinterface reconciliation `apply` already does). Bond naming mirrors bridge naming exactly: `bond<id>`, allocated on first use and persisted to `driver::port_aggregate_registry` (`--port-aggregate-registry-path`, same `linux-driver/` directory as `bridge-ids.yaml`/`table-ids.yaml`). Aggregates are created/removed eagerly from every configured `PortAggregate` — same "create eagerly from config" pattern as broadcast-domain bridges — reconciled after every bridge (an aggregate's own `switching_profile` may enslave its bond device into a bridge that must already exist) and before any interface's own `apply` (a member interface enslaves into the bond by name). A member interface enslaves via `Interface.port_aggregate: Option<String>`, resolved to the bond's real device name the same way `routing_table`/`switching_profile` resolve to a VRF/bridge name; commit-time validation (`valid_port_aggregate_membership`) guarantees a member interface's `switching_profile`/`subinterfaces` are empty, so `apply`'s three-way VRF/bond/bridge master resolution never actually has to arbitrate a real conflict.

  `PortAggregateMode` is `Xor` (static — every member is enslaved unconditionally, no negotiation) or `Lacp` (dynamic — real IEEE 802.1AX LACPDU exchange, implemented from scratch by the separate `nos-lacpd` daemon, see `lacp/CLAUDE.md`). **Both modes create the underlying kernel bond as `BondMode::BalanceXor`** (`bond_mode_of`) — never the kernel's own `Ieee8023Ad` mode, which would intercept every slow-protocol frame via its own `rx_handler` before `nos-lacpd`'s raw sockets ever saw it, silently starving the from-scratch implementation of its own protocol traffic. The two modes differ only in which control plane decides *membership*: `InterfaceState.port_aggregate_active` gates whether a member interface is actually enslaved right now — always `true` for `Xor`, and for `Lacp` only once `nos-lacpd` has pushed it into `Interfaces.lacp_active_members` (`InterfaceRequest::PushLacpMembers`, a fire-and-forget full-resend push handled by `server.rs`'s `apply_lacp_push`, applied **immediately** via `driver.apply` rather than waiting for the periodic re-apply tick — the same immediate-apply precedent as `nos-ribd`'s BGP route push). `PushBfdMembers` (from `nos-bfdd`, aggregates with `bfd`) fills `Interfaces.bfd_up_members` the same way, and `port_aggregate_active` is `lacp_ok && bfd_ok` (`member_active`): both setters recompute from both maps, and no BFD push means not Up. `lacp_active_members` is deliberately *not* rebuilt by `build_from_config` — it's carried forward unchanged from the previous resync on every ordinary config change, so an unrelated commit never reverts a negotiated bond back to "nothing enslaved"; a fresh `Interfaces::new()` starts with an empty map, which is the fail-safe default (nothing enslaved into a `Lacp`-mode bond until `nos-lacpd`'s first real push arrives).

  `LinuxInterfaceDriver::apply` reconciles all of this per interface in one pass: the physical (or loopback) link itself gets `subinterfaces`' tag-0 addresses and is enslaved into the resolved VRF (from that tag-0 subinterface's `routing_table`), the resolved bond (from `port_aggregate`), or the resolved bridge (from an `Untagged` switching-profile member) — at most one of the three, since commit-time validation (`valid_subinterface_and_switching_profile_tags`, `valid_port_aggregate_membership`) guarantees they never collide. Every tag>0 sub-link — whether an L2 `Dot1q` switching-profile member or an L3 `tag>0` `Subinterface` — is reconciled by one shared function, `reconcile_tagged_subinterfaces`, over the *union* of both kinds' tags (never scanned separately, or one kind's live sub-link would be mistaken for the other's stale one and deleted): it creates/deletes each `<interface>.<tag>` VLAN sub-interface as needed, then enslaves it per a `TaggedMaster::{Bridge(domain), Vrf{routing_table, addresses}}` — `Bridge` enslaves into that domain's bridge (no addresses, as before); `Vrf` enslaves into the resolved routing table's VRF (or leaves the sub-link masterless if `routing_table` is unset) and applies that `Subinterface`'s own addresses, so two interfaces can use different tags for the same L2 domain and still land on the same bridge, while an L3 sub-interface gets its own independent addressing/VRF regardless of what other tags on the same physical interface are doing. Before creating a sub-link, an admin-down parent is raised (the kernel refuses to open a VLAN device over a down lower device with `ENETDOWN`), unless BPDU guard holds it err-disabled; then the sub-link `up` that fails with `ENETDOWN` is left for the next resync instead of failing `apply` every tick. Bridge naming mirrors the loopback/VRF pattern: `br<id>`, where `<id>` is allocated on first use and persisted to this driver's own private registry (`driver::bridge_registry`, `--bridge-registry-path`, default `/var/lib/nos/interfaced/bridge-ids.yaml` — same directory `nos-ribd`'s `table-ids.yaml` lives in, since every daemon here runs inside one watchdog container). Bridges are created/removed eagerly from every configured `BroadcastDomain`, independent of whether any interface currently references one — same pattern as `nos-ribd`'s VRF-per-`RoutingTable` — and are reconciled *before* any interface's own `apply` in the same resync, since enslavement resolves each bridge by name.

**Cross-daemon IPC to `nos-ribd`.** When an interface's `routing_table` is set (or, for a loopback interface, is implied by its name), `LinuxInterfaceDriver` needs the real Linux interface name of that table's VRF device — but VRF creation and table-id allocation are owned entirely by the *owning* `nos-ribd` instance's own driver (see `rib/CLAUDE.md`), not derivable independently. So the driver resolves that table's `nos-ribd` socket via the watchdog broker (`ServiceRef::RibTable(name)`) and asks it directly over IPC (`RibRequest::GetVrfName` → `RibEvent::VrfName(Option<String>)`, see `driver::rib_client`) — the first direct daemon-to-daemon link in this codebase (see root `CLAUDE.md`). A loopback interface additionally asks the same instance for its raw numeric table id (`RibRequest::GetTableId` → `RibEvent::TableId(Option<u32>)`, symmetric to `GetVrfName`) to compute its kernel device name. "Not resolvable yet" (broker doesn't know that table, connect failure, or rib hasn't created a VRF/table id yet) is a normal, expected, frequently-recurring condition, never an error — it's silently retried by the periodic re-apply tick (`reconcile::REAPPLY_INTERVAL`), not just on the next config diff, since the other daemon's readiness isn't itself a config change.

There is an external query API: `server.rs` serves `nos_proto::interface::{InterfaceRequest, InterfaceEvent}` for `nos-cli`'s `show interface` command (see `docs/architecture/endpoint-broker.md` for how a client finds this instance's socket — `ServiceRef::Interfaces`, resolved directly by the watchdog like `ServiceRef::Config`, since there's exactly one instance). A query reflects *desired* state (from the running config) — with the `linux` driver running, that's normally also what the kernel has, but the two can transiently diverge (e.g. right after a config change, or if the VRF isn't up yet).

`InterfaceRequest::GetBroadcastDomain { name }` → `InterfaceEvent::BroadcastDomain(BroadcastDomainStatus)`/`NotFound` is the same query shape for a `BroadcastDomain`'s own SVI (`state::Interfaces.by_domain`, populated in `build_from_config`'s existing broadcast-domain loop, mirroring `by_name`). Added for `nos-ospfd` to resolve a `BroadcastDomain.ospf_profile` attach point's local address the same way `resolve_local_address` already asks this daemon for a `Subinterface`'s — this is the second direct daemon-to-daemon IPC link that isn't `GetVrfName` (see root `CLAUDE.md`'s "Linux drivers"), and, like that one, exists because the answer isn't derivable from `nos-ospfd`'s own already-fetched `Config` alone (asking the owning daemon stays consistent even though today's answer happens to just mirror desired config, in case a future kernel-derived address ever isn't). `BroadcastDomainStatus.bridge_name: Option<String>` (`None` until the driver has actually allocated/created the bridge) carries the domain's real Linux bridge device name in the same reply — `InterfaceDriver::ensure_broadcast_domain` now returns it (`Ok(ifname)` on the `linux` driver, a synthesized `noop-br-<name>` placeholder on the `noop` one) rather than `Ok(())`, and `build_from_config` stores it onto the `BroadcastDomainState` it's already building. `nos-ospfd` needs this to bind its own raw OSPF socket to the domain's bridge (its SVI) rather than the shared VRF device — see `ospf-internals.md`'s `socket.rs` entry for why VRF-wide binding is wrong for a protocol with no port/connection concept to demultiplex by.

`nos-ribd` is the other daemon that reads both queries (`server.rs`'s `allowed` admits `Role::Ribd` to the status queries, never to `PushLacpMembers`): on every resync it asks for `GetInterfaces`, `GetPortAggregates` (when an aggregate subinterface is in its table) plus `GetBroadcastDomain` for each SVI-carrying domain of its table and derives its `RouteSource::Connected` routes from the addresses — the reverse of the `GetVrfName` link above (see [rib internals](rib.md)).

## Modules

| Module | Role |
|--------|------|
| `main.rs` | Arg parsing (`--watchdog-socket`, `--listen-socket` default `/run/nos/interface.sock`, `--driver` default platform-dependent, `--bridge-registry-path`, `--port-aggregate-registry-path`), resolves `nos-configd`'s address via the watchdog broker before starting, constructs the selected `InterfaceDriver`, SIGINT+SIGTERM shutdown wait, spawns `reconcile::run` and `server::start` sharing one `Arc<RwLock<Interfaces>>` |
| `state.rs` | `InterfaceState` (carrying `switching_profile`/`switching_profile_members`, the latter resolved from config — pure local lookup, no IPC needed — plus `port_aggregate: Option<String>` (the raw config name, for status display — resolved to a real bond device name by the driver itself), `port_aggregate_active: bool` (whether that enslavement should actually happen right now — see "Port aggregates" above), and `subinterfaces: Vec<SubinterfaceState>`, the wire twin of `nos_proto::Subinterface`; `addresses`/`routing_table` on `InterfaceState` itself are populated only for a loopback interface, empty otherwise — a loopback's `routing_table` is the table in its name (`loopback_table_name`), falling back to the field, since that is the VRF the driver enslaves it into), `BroadcastDomainState` (the wire twin of `nos_proto::BroadcastDomain` — name plus its own SVI `addresses`/`routing_table`, plus `bridge_name: Option<String>`, filled in from the driver's own return value, not desired config), `PortAggregateState` (the wire twin of `nos_proto::PortAggregate` — mode/switching_profile/mtu/subinterfaces, plus `bond_name`/`link_local_address` filled in the same way `BroadcastDomainState.bridge_name` is), `Interfaces` (name-keyed `by_name`/`by_domain`/`by_port_aggregate` collections, mirroring `nos-rib`'s `Rib`, plus each section's last-resync name set purely for diffing removals, plus `lacp_active_members: HashMap<String, Vec<String>>` — **not** rebuilt by `build_from_config`, carried forward unchanged from `previous` every resync — `get`/`get_domain`/`get_port_aggregate` back `server.rs`'s query kinds, `set_lacp_active_members` backs its `PushLacpMembers` handler), `build_from_config` (async — calls `driver.ensure_broadcast_domain`/`remove_broadcast_domain` per configured/removed domain, then `driver.ensure_port_aggregate`/`remove_port_aggregate` per configured/removed aggregate (after domains — an aggregate's own `switching_profile` may enslave it into a bridge that must already exist; before interfaces — a member enslaves into it by name), then `driver.apply` per interface (now also resolving `port_aggregate`/`port_aggregate_active`) and `driver.remove` for any interface dropped from config since the previous resync) |
| `driver/mod.rs` | `InterfaceDriver` trait (`apply`, `remove`, `ensure_broadcast_domain`/`remove_broadcast_domain`, `ensure_port_aggregate`/`remove_port_aggregate` — the latter pair mirrors the former exactly, for a `PortAggregate`'s bond device instead of a `BroadcastDomain`'s bridge), `DriverError` |
| `driver/noop.rs` | `NoopInterfaceDriver` |
| `driver/linux.rs` | `LinuxInterfaceDriver` — real `rtnetlink` implementation, including `reconcile_tagged_subinterfaces`/`TaggedMaster` (see above) and `reconcile_physical_link` (the shared post-link-resolution body — addresses, master enslavement, tagged subinterfaces — factored out of `apply`'s physical-interface case so `ensure_port_aggregate` can reuse it verbatim against a bond device's own kernel link, since a `PortAggregate` has the identical non-loopback config surface as a physical `Interface`). `MasterKind::Bond` is a third enslavement kind alongside `Vrf`/`Bridge` — same generic `IFLA_MASTER` operation, only the log wording differs (`"enslaved interface to bond"`) |
| `driver/bridge_registry.rs` | This driver's own private persisted state (`--bridge-registry-path`, default `/var/lib/nos/interfaced/bridge-ids.yaml`): allocates a bridge id (1, 2, 3, ... — just a short unique device-name suffix, never a real kernel table id, so no reserved range) for a `BroadcastDomain` name on first use and remembers it across restarts, mirroring `nos-ribd`'s `table_registry` exactly. **No other process ever reads this file.** |
| `driver/port_aggregate_registry.rs` | The `PortAggregate` counterpart of `driver/bridge_registry.rs` — identical shape, allocating a bond id (`--port-aggregate-registry-path`, default `/var/lib/nos/interfaced/port-aggregate-ids.yaml`, same directory) that names the real kernel device `bond<id>`. |
| `driver/rib_client.rs` | One-shot `get_vrf_name`/`get_table_id` — the client side of the cross-daemon `RibRequest::GetVrfName`/`GetTableId` IPC |
| `reconcile.rs` | Steady-state loop: subscribes to `Interfaces`/`BroadcastDomains`/`SwitchingProfiles`/`PortAggregates` diffs purely as a resync trigger, always re-fetching the whole config and rebuilding `Interfaces` from scratch rather than applying diffs incrementally (diffs carry only display strings, not structured data); also re-applies on a fixed `REAPPLY_INTERVAL` (10s) even without a new diff, since VRF/bridge/bond readiness is an external condition no config diff signals; writes the rebuilt `Interfaces` through the shared `Arc<RwLock<Interfaces>>` |
| `server.rs` | Binds `--listen-socket` and serves `InterfaceRequest::GetInterfaces`/`GetInterface`/`GetBroadcastDomain`/`GetPortAggregates`/`GetPortAggregate` from the shared `Arc<RwLock<Interfaces>>`, read-locked per request, plus `PushLacpMembers` (fire-and-forget, from `nos-lacpd`) — applies the pushed active-member set via `Interfaces::set_lacp_active_members` then immediately `driver.apply`s every affected interface, rather than waiting for `reconcile.rs`'s periodic tick |

## Link watcher

- **What.** `driver/links.rs`'s `LinkHub` is the kernel's link table (key: device name, value: `LinkState { name, ifindex, admin_up, carrier }`) plus a `broadcast` channel of `Changed`/`Removed`. `LinuxInterfaceDriver` starts `run_link_watcher` with the driver, so the table is warm before any subscriber.
- **Feeding it.** The watcher subscribes to `RTMGRP_LINK` first, dumps second, then applies each `RTM_NEWLINK`/`RTM_DELLINK`; a failed dump keeps the old table. A 30 s re-dump (`replace_all`) is the safety net for `ENOBUFS`; a dropped netlink stream reconnects after a fixed 1 s.
- **Dedupe.** An identical upsert emits nothing (counter-only `NEWLINK` noise). A rename arrives as `NEWLINK` only, so an `ifindex` reappearing under a new name emits `Removed(old)` first.
- **Semantics.** `admin_up` is `IFF_UP`; `carrier` is `IFF_LOWER_UP` with oper state up or unknown (dummy/bridge devices report unknown). `is_up()` needs both; `down_reason()` is `admin-down` or `no-carrier`, and a consumer adds `absent` for a name not in the table.
- **Serving it.** `server::stream_links` sends `LinkSnapshot { observed, links }`, then forwards events. On a lagged receiver it sends a new snapshot (never a silent gap). The connection lives until the client closes or writes anything; only `ospfd`/`ospfv3d` may subscribe.
- **`observed = false`** means the driver does not watch the kernel (noop): consumers must not gate on link state.
- **Consuming it.** Resolve `ServiceRef::Interfaces`, send `SubscribeLinks`, replace the whole table on every snapshot, and on disconnect reconnect after a fixed 1 s and take the new snapshot.
- **Log anchors** (debug): `link state changed name=… ifindex=… admin_up=… carrier=…`, `link removed name=…`.
