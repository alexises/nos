# Linux drivers

Contributor-facing; moved from the root `CLAUDE.md` (#260). Operator view: [docs/README.md](../README.md).


Both `nos-ribd` and `nos-interfaced` apply their reconciled desired state to the real Linux network stack via `rtnetlink`, behind a swappable `Driver` trait per crate (`interface::driver::InterfaceDriver`, `rib::driver::RibDriver`) selected with `--driver linux|noop` (default `linux` on Linux, `noop` elsewhere — the `noop` driver is today's original log-only placeholder behavior, kept as a portability/test fallback). This is deliberately in-process rather than a separate privileged process, so a future non-Linux/hardware backend only needs a new `Driver` impl, not new IPC or supervision wiring. Both binaries run as the unprivileged `nos` user; the kernel access their Linux drivers need comes from `CAP_NET_ADMIN`/`CAP_NET_RAW` file capabilities baked onto the two binaries at image build time plus a matching `cap_add` on the `watchdog` container (see `Dockerfile`/`docker-compose.yml`).

`no-new-privileges` must stay off: the kernel then ignores file capabilities on exec, so every `setcap` binary would lose its capabilities.

`nos-ribd`'s Linux driver owns creating a Linux VRF device + kernel routing table for its `RoutingTable`, allocating a kernel table id on first use and persisting the name→id mapping to a local file (`--table-registry-path`, default `/var/lib/nos/ribd/table-ids.yaml`) purely so a crash/restart reuses the same id and VRF name — this file is never read by any other process. On shutdown (the same SIGINT used for both "watchdog is stopping" and "this table was removed from config") it deletes the kernel VRF and its routes, but never the registry entry, so an ordinary restart recreates the identically-named VRF.

Because `nos-interfaced` needs to enslave an interface into the VRF device that backs its configured `routing_table`, but has no way to derive that VRF's real Linux interface name on its own (it's allocated entirely inside `nos-ribd`'s driver), `nos-ribd`'s per-table socket gains one more request: `RibRequest::GetVrfName` → `RibEvent::VrfName(Option<String>)`. `nos-interfaced`'s Linux driver resolves the owning `nos-ribd` instance via the broker (`ServiceRef::RibTable(name)`) and queries it directly — **this is the first direct daemon-to-daemon IPC link in the system** (every other component only ever talks to `nos-configd` or the watchdog broker). A `None` answer (table not running yet, or running but hasn't created its VRF yet) is treated as an ordinary transient condition, not an error, and retried automatically by both daemons' periodic re-apply tick (in addition to their existing config-diff-triggered resync) — needed here specifically because "the other daemon became ready" isn't a config change either daemon would otherwise be notified of. The link also runs the other way: `nos-ribd` derives its table's **connected routes** (`RouteSource::Connected`, preference 0 — below `Static`) from what `nos-interfaced` actually applied, asking it on every resync (`rib/src/interface_client.rs`, `ServiceRef::Interfaces` via the broker) for `GetInterfaces` (every `Interface`/`Subinterface` address whose `routing_table` is this table — a loopback's is always the table in its name, whatever the field says), `GetPortAggregates` when some aggregate subinterface is in this table, plus `GetBroadcastDomain` per SVI-carrying domain of this table (there is no "list every domain" request). They show up in `show route`/`GET /v1/routes/{table}` as `connected` and in `RibRequest::IgpCosts` at cost 0, but are **never installed** (`Rib::best_routes_for_kernel` leaves a prefix whose winner is `Connected` to the kernel, so a `Static`/`Bgp`/`Ospf` route for a connected prefix is listed but not installed either, #139): the kernel adds its own on-link route the moment the address is applied, and `LinuxRibDriver`'s dump already ignores gateway-less routes as unmanaged, so a connected prefix never appears on either side of its diff. Their purpose is RFC 4271 §9.1.2 in `nos-bgpd` — see `docs/protocols/bgp-internals.md`'s "Next-hop feasibility".

`nos-bgpd` resolves its VRF the same way: a `BgpInstance` carries a reflexive, read-only `routing_table` field (mirrored by `nos-config` from the owning `RoutingTable`'s `bgp_instance` reference on every commit — never independently editable, and never shown in `nos-cli`'s config rendering, since it exists purely for `nos-bgpd` to read over IPC), which it resolves to a VRF name via the same `ServiceRef::RibTable` + `GetVrfName` call `nos-interfaced` uses. A `BgpInstance` with no owning `RoutingTable` is treated as invalid operating state, not a "default VRF" fallback — `nos-bgpd` never opens a session for it, only logging an error and rechecking on every resync in case config is fixed. Once a VRF name is resolved, `nos-bgpd` opens raw, VRF-scoped TCP connectivity to its configured peers (both an active outbound connect per peer and a shared passive listener on port 179, scoped into the VRF via `SO_BINDTODEVICE` rather than `rtnetlink` since no interface/route is being programmed) — the foundation the BGP FSM (OPEN/KEEPALIVE message exchange) will be layered on top of later.

`nos-lacpd` (see `lacp/CLAUDE.md`) is a second, independent daemon-to-daemon link into `nos-interfaced`, but in the opposite direction from `GetVrfName`: instead of *querying* `nos-interfaced` for something only it knows, `nos-lacpd` *pushes* something only `nos-lacpd` knows — a `Lacp`-mode `PortAggregate`'s currently-negotiated active-member set (`InterfaceRequest::PushLacpMembers`, fire-and-forget, the same "data plane push" pattern as `nos-ribd`'s `RibRequest::PushBgpRoutes`) — over a persistent connection resolved via `ServiceRef::Interfaces`. `nos-interfaced`'s Linux driver still owns every actual `rtnetlink` call for the bond device (`ensure_port_aggregate`, member enslavement); `nos-lacpd` never touches rtnetlink at all, and the kernel bond is created identically for `Xor` and `Lacp` modes (`BondMode::BalanceXor` in both cases — **not** the kernel's own `Ieee8023Ad` bonding mode, which would silently steal every LACPDU from `nos-lacpd`'s own raw sockets before userspace ever saw them). The `PortAggregateMode` only changes which control plane decides *membership*: unconditional for `Xor`, gated on this push for `Lacp`.

`nos-interfaced` also *watches* the kernel: its Linux driver holds an `RTMGRP_LINK` netlink subscription (plus a 30 s re-dump) feeding an in-memory link table, and `InterfaceRequest::SubscribeLinks` streams it — `LinkSnapshot` first, then `LinkChanged`/`LinkRemoved`, a fresh snapshot after any lag — to `nos-ospfd`/`nos-ospfv3d`. See [interface internals](../internals/interface.md#link-watcher).

`nos-interfaced`'s Linux driver owns L2 switching the same way `nos-ribd`'s owns VRFs: one real Linux bridge device per configured `BroadcastDomain`, named from a bridge id allocated on first use and persisted to its own private registry (`--bridge-registry-path`, default `/var/lib/nos/interfaced/bridge-ids.yaml` — the same `linux-driver/` directory `nos-ribd`'s `table-ids.yaml` already lives in). Because a `BroadcastDomain` is one L2 domain but two different interfaces can tag it with two different local dot1q values (the tag is locally significant per interface, not global to the domain), there is deliberately no single shared 802.1Q-aware bridge with one global VID→domain mapping: an `Interface.switching_profile`'s `Untagged` member enslaves the physical link itself into its domain's bridge, and each `Dot1q(N)` member gets its own 802.1q sub-interface (`<interface>.<tag>`) enslaved into that domain's bridge instead — so two interfaces can use different tags for the same domain and still land on the same bridge. `routing_table` and an `Untagged` switching-profile member are mutually exclusive on the same interface (rejected at commit time), since the physical link has only one master; a `Dot1q` member never conflicts, since it lives on an independent sub-interface. `BroadcastDomain` itself also carries an optional `addresses`/`routing_table` — the same flat L3 shape as a loopback `Interface` — making the domain's own bridge device an SVI (switch virtual interface): `nos-interfaced` reconciles them directly onto the bridge with the identical `reconcile_addresses`/VRF-enslavement calls it already makes for an ordinary link, independent of whatever interfaces are enslaved into that bridge as L2 members (a separate Linux device, so no conflict with any member's own VRF assignment).

`nos-interfaced` also owns spanning-tree port safety (#326): while `spanning-tree mode` is not `disabled`, every bridge port is written DISABLED (the only blocking state a `BR_NO_STP` bridge keeps) and gets an ingress `flower`+`gact drop` BPDU trap, until `nos-stpd` pushes a state with `SetStpPortStates`. Details and kernel findings: [STP internals](../internals/stp.md#kernel-side-nos-interfaced-326).

## tc filters (`nos-tc`)

Several daemons put filters on the same device's `clsact` qdisc, all through the `nos-tc` crate (hand-encoded netlink: `netlink-packet-route` has no `gact`/`skbedit`/`fw`):

- Every owner ensures the qdisc (`Request::Clsact`, tolerating `EEXIST`) and never deletes it.
- Each owner keeps to its own priorities on chain 0 (table in `tc/CLAUDE.md`): `nos-fdbd` 1 and 2 (local bias), `nos-interfaced` 1 (BPDU trap, bridge-port ingress, never a VXLAN port; fdbd's prio 1 there is on egress), `nos-acld` 100 (#541). A lower priority runs first.
- Delete by priority (`DelFilter`, `handle` 0 for all of it) or by chain (`FlushChain`), never the whole hook.
- Calls block: run them on `spawn_blocking`.
- Check by hand in a throwaway namespace: `unshare -Urn`, then `tc filter show dev <dev> ingress` (add `chain <n>`, `-s` for counters).
