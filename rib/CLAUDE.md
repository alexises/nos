# nos-rib — RIB Component

Computes the best route per prefix for one routing table (binary `nos-ribd`, one process per `RoutingTable`, spawned by `nos-watchdog`).

## Scope

The internal `Rib` (`src/rib.rs`) is multi-source (`RouteSource::Static` / `RouteSource::Bgp` / `RouteSource::Ospf` / `RouteSource::Connected`), each populated by its own independent writer: `reconcile::resync` rebuilds the whole `Static` side from config on every resync — and the whole `Connected` side (preference 0, below `Static`) from what `nos-interfaced` applied, via `interface_client.rs` (`InterfaceRequest::GetInterfaces` for every `Interface`/`Subinterface` address in this table, `GetPortAggregates` for aggregate subinterfaces — only when the config puts one in this table — plus `GetBroadcastDomain` per SVI-carrying domain of this table, resolved through `ServiceRef::Interfaces`; a failed call keeps the previous set, like `nos-bgpd`'s `igp_client`) — and `server::apply_bgp_route_update`/`apply_ospf_route_update` apply `RibRequest::PushBgpRoutes`/`PushOspfRoutes` — sent by the owning `nos-bgpd`/`nos-ospfd` instance over a persistent connection, `Full` on connect then incremental `Add`/`Remove` (`bgp::rib_push_client`/`ospf::rib_push_client`, mirroring this crate's own `bgp_client.rs` for the reverse direction) — incrementally. `Rib::replace_source`/`upsert`/`remove` are all scoped to one `RouteSource`, so no writer can clobber another's candidates; `best_routes_for_kernel()` merges them for `driver.apply` — every source but `Connected`, dropped from each prefix's candidate pool *before* the winner is picked, so a `Static`/`Bgp`/`Ospf` candidate shadowed by a connected one is still installed. A connected prefix is never installed by this daemon: the kernel adds its own on-link route the instant `nos-interfaced` applies the address (a `Connected` entry's one next hop is that local address, display only), and `driver::linux::extract_route` already skips gateway-less kernel routes as unmanaged, so it never shows up on either side of the dump-diff. The source exists for `igp_costs()` (cost 0, like `Static`), which is how `nos-bgpd` tells a directly-connected next hop from an unresolvable one (RFC 4271 §9.1.2 — see `bgp/CLAUDE.md`'s "Next-hop feasibility"); `best_routes()` (every source) still serves `show route`, where it renders as `connected`.

This crate also **redistributes the other direction**: `reconcile::compute_redistribute_target`/`compute_redistribute_target_ospf` filter this table's `RouteSource::Static` candidates against `RoutingTable.redistribute` (`to: Bgp`/`to: Ospf` respectively) and publish the result to `bgp_client.rs`/`ospf_client.rs` (near-identical, each mirroring the opposite-direction push above), which forward it over a persistent `BgpRequest::RedistributeRoutes`/`OspfRequest::RedistributeRoutes` connection to the owning `nos-bgpd`/`nos-ospfd` instance — the mechanism that makes `redistribute from static to ospf` a real RFC 2328 ASBR (see `ospf/CLAUDE.md`'s "ASBR and AS-external-LSA origination").

**OS application is now real**, via a swappable `driver` (`src/driver/`, see below) — `--driver linux` (the default on Linux) creates an actual Linux VRF device + kernel routing table per routing table and installs the winning route per prefix into it; `--driver noop` (the default off-Linux) keeps the old log-only behavior for tests/dev. Only the *best* route per prefix is ever installed to the kernel — `Rib`'s multi-candidate view stays a query-serving concern.

There is an external query API: `server.rs` serves `nos_proto::rib::{RibRequest, RibEvent}` for `nos-cli`'s `show route` command (see root `CLAUDE.md`'s "Endpoint broker" section for how a client finds this instance's socket), plus `GetVrfName` — the first direct daemon-to-daemon IPC link in this codebase, letting `nos-interfaced` ask this instance for its Linux VRF interface name so it can enslave interfaces into it by name — and `GetTableId`, symmetric to `GetVrfName`, letting `nos-interfaced` learn this table's raw numeric kernel table id so it can name a loopback interface's kernel device (`lo<table_id>`). `PushBgpRoutes` is fire-and-forget (no reply), from the one `nos-bgpd` instance the config schema allows to claim this table (`bgp_instance_reference_valid` enforces at most one `RoutingTable` per `BgpInstance`) — `server.rs` no longer trusts whatever arrives: the socket is mutually authenticated TLS, and `allowed(role, &request)` restricts `PushBgpRoutes` to the `bgpd` role and `PushOspfRoutes` to `ospfd`/`ospfv3d` (both OSPF daemon families push OSPF-sourced routes), queries to `user`/`restd`, and `GetVrfName`/`GetTableId` to the daemons that resolve a VRF through this instance. It is role-level only — a `bgpd` for another instance could still push into this table (`ponytail:` in `server.rs`). A refused request is logged with the peer's role and name and the connection closed. `bgp_client.rs`/`ospf_client.rs` dial the owning daemons with the name-checked `nos_pki::connect(.., Role::Bgpd/Ospfd, &name)`.

## Backup routes

`RibEntry.backup` (from `BgpRoute`/`OspfRoute.backup_next_hop`) is part of the entry's equality, so a backup-only change re-installs the winner. Only the winning entry's backup is installed. `LinuxRibDriver` treats each prefix as two kernel *slots* — `(prefix, false)` the primary at the default priority, `(prefix, true)` the backup at the family's backup metric (`BACKUP_METRIC_V4` 1000, `BACKUP_METRIC_V6` 2000 — an IPv6 primary is 1024, so 1000 would beat it), with `RibEntry.backup_interface_id` as its `RTA_OIF` (a link-local IPv6 backup needs one, and it may differ from the primary's) — through `slots()`, so `diff_routes`, `installed`, `apply_delta` and the dump (`extract_route` reads `RTA_PRIORITY`) all work per slot. The kernel keeps both routes in the FIB and falls to the backup the instant the primary is withdrawn or its link drops. `show route` renders `backup <gw>`. `ponytail:` metric-based failover only reacts to the primary *route* disappearing (link down, session/adjacency loss), not to an unreachable next hop behind a live link — that would need BFD or kernel nexthop groups.

## Equal-cost multipath

`RibEntry.next_hops` (from `OspfRoute.next_hops`; one element for `Static`/`Bgp`/`Connected`) is the primary slot's value: `LinuxRibDriver::build_route` emits `RTA_GATEWAY` (+`RTA_OIF`) for one hop and `RTA_MULTIPATH` for two or more, and `extract_route` reads the gateways back from either — a multipath route has no top-level `RTA_GATEWAY`, and without that it would look unmanaged (re-added with EEXIST every `apply`, never deleted). Slots compare by their sorted gateway list (a dump has no `interface_id` of ours), so a changed set is a del+add like a changed gateway; the `added route` log line carries `gateway=<a>,<b>` and `next_hops=<n>`. Best-path selection is unchanged — one source wins per prefix with its own set (BGP multipath is #70). The set is part of equality, so a flapping equal-cost sibling re-installs the prefix, like `backup`. `ponytail:` a next hop whose link goes down stays in the multipath route until SPF reconverges (the kernel keeps linkdown nexthops unless `ignore_routes_with_linkdown` is set) — the same class of limitation as metric-based failover below; older kernels dump IPv6 ECMP as sibling routes, not one `RTA_MULTIPATH` (latent, `nos-ospfv3d` pushes one hop).

## Modules

| Module | Role |
|--------|------|
| `main.rs` | Arg parsing (`--table`, `--watchdog-socket`, `--listen-socket`, `--driver`, `--table-registry-path`), resolves `nos-configd`'s address via the watchdog broker before starting, SIGINT+SIGTERM shutdown wait, spawns `reconcile::run` and `server::start` sharing one `Arc<RwLock<Rib>>` and the driver |
| `rib.rs` | `RouteSource`, `RibEntry`, `Rib` (best-path selection: `best_route`/`best_routes` for the winner only, `all_routes`/`lookup` for every candidate per prefix — the latter used to serve `RibRequest`), `build_from_config` |
| `driver/mod.rs` | `RibDriver` trait (`apply`, `teardown`, `vrf_name`, `table_id`) and `DriverError` — the swappable OS backend, so a future non-Linux/hardware driver can be added without touching `reconcile.rs` |
| `driver/noop.rs` | `NoopRibDriver` — today's original log-only behavior |
| `driver/linux.rs` | `LinuxRibDriver` — real `rtnetlink` calls: creates/ups the VRF link, diffs live kernel routes in that table against the desired best-path set and adds/removes the difference |
| `driver/table_registry.rs` | `nos-ribd`'s **own private** persisted state (`--table-registry-path`, default `/var/lib/nos/linux-driver/table-ids.yaml`): allocates a kernel table id (100–252, avoiding Linux's reserved 0/253/254/255) for this table's name on first use and remembers it across restarts, so a crash/restart recreates the same VRF name. Exclusively locked (via `fs2`) around the allocate-and-persist sequence since multiple `nos-ribd` instances share this one file. **No other process ever reads this file** — see `GetVrfName` above for how `nos-interfaced` learns the name instead. |
| `config_client.rs` | Own `fetch_config` (`Request::Get`) / `subscribe_diff` (`Request::SubscribeDiff`) — reimplemented rather than shared with `nos-cli`/`nos-watchdog`, per the root `CLAUDE.md`'s star dependency graph |
| `watchdog_client.rs` | Own `resolve_with_retry` — resolves `nos-configd`'s address via the watchdog broker, retrying indefinitely (fixed 1s delay) until it succeeds or shutdown fires |
| `bgp_client.rs` | Owns the redistribution-push connection to this table's `nos-bgpd` instance (`RedistributeTarget`, `spawn`, full/incremental diffing) — see the Scope section's "redistributes the other direction" |
| `ospf_client.rs` | The OSPF-redistribution analogue of `bgp_client.rs`, near line-for-line — pushes to this table's `nos-ospfd` instance instead (`ServiceRef::OspfInstance`, `OspfRequest::RedistributeRoutes`) |
| `interface_client.rs` | One-shot `get_interfaces`/`get_port_aggregates`/`get_broadcast_domain` — the client side of `InterfaceRequest::GetInterfaces`/`GetPortAggregates`/`GetBroadcastDomain` (mirroring `nos-bgp`'s `interface_client.rs`), from which `reconcile::connected_entries` derives this table's `Connected` candidates on every resync |
| `reconcile.rs` | Steady-state loop: subscribes to `RoutingTables`/`StaticRoutingInstances` diffs purely as a resync trigger, always re-fetching the whole config and rebuilding this table's `Static` candidates from scratch via `Rib::replace_source` (never touching any `Bgp`/`Ospf`-sourced candidate) rather than applying diffs incrementally (diffs carry only display strings, not structured route data), and its `Connected` candidates the same way from `interface_client` (`connected_entries`, pure and unit-tested — so a new address is visible within one `REAPPLY_INTERVAL` at worst); calls `driver.apply` with the recomputed best routes (`best_routes_for_kernel`), and publishes `bgp_client`/`ospf_client`'s `RedistributeTarget`s via `compute_redistribute_target`/`compute_redistribute_target_ospf`. Also re-applies on a fixed 10s timer even without a new diff — a config commit is not the only thing that can require re-applying (e.g. the VRF just didn't exist yet on an earlier attempt, or kernel state drifted out of band); this also re-affirms `Bgp`/`Ospf`-sourced routes against kernel drift for free. On exit, calls `driver.teardown` to delete the kernel VRF + its routes — this runs on **every** SIGINT nos-watchdog sends (both an ordinary restart and a real table removal look identical to this process), which is why `teardown` never touches the table-id registry: the next `apply` must recreate the exact same VRF name. |
| `server.rs` | Binds `--listen-socket` and serves `RibRequest::GetRoutes`/`Lookup`/`GetVrfName`/`GetTableId` from the shared `Arc<RwLock<Rib>>` (read-locked per request) and driver (`driver.vrf_name`/`driver.table_id`), plus the fire-and-forget `PushBgpRoutes`/`PushOspfRoutes` (`apply_bgp_route_update`/`apply_ospf_route_update`): applies the update to the `Bgp`/`Ospf` side of the shared `Rib` and calls `driver.apply` itself, independent of `reconcile.rs`'s own periodic apply — safe since `apply` is an idempotent dump-diff-converge operation and every writer only ever touches its own disjoint `RouteSource` candidates. |

`table.bgp_instance` is deliberately never read by `build_from_config` — `Bgp`-sourced entries only ever arrive via `PushBgpRoutes`, never from config.
