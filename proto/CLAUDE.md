# nos-proto — Shared Protocol Types

Single source of truth for all inter-process wire contracts in NOS.

## Why this crate exists

Component processes (`nos-bgp`, `nos-rib`, …) must not depend on `nos-config` internals — only on the shared types they exchange. By owning all shared types here, we get:
- **Protocol sync at compile time**: change a type → compiler breaks every consumer immediately.
- **Clean dependency graph**: components depend on `nos-proto`, not on each other.

| `schema/` | Config tree types: `Config` (incl. the singleton `Config.lldp: LldpSettings` — system-wide LLDP timers/management address, diffed field-level via `ConfigDiff.lldp`/`DiffScope::Lldp` rather than as a keyed `SectionDiff` list, since there is only one; `Interface.lldp_destination: LldpDestination` is the per-interface half), `BgpInstance`, `BgpPeerGroup`, `BgpPeer`, `RoutingTable`, `StaticRoutingInstance`, `StaticRoute`, `Interface`, `Subinterface`, `BroadcastDomain` (whose `vni`/`rd`/`route_targets_import`/`route_targets_export`/`vtep_source`/`mac_redistribute`/`arp_redistribute`/`connected_redistribute` are the EVPN/VXLAN config `nos-fdbd` acts on: all require a `vni`, and `mac_redistribute` — the BGP instance named on `redistribute from mac to bgp <instance>` — also an `rd` and a `vtep_source`; `diff_broadcast_domains` emits every one, `vni` being the label the watchdog's `claim_label` keys on). Derived `garde::Validate` for commit-time validation. `BroadcastDomain.addresses`/`routing_table` are the same flat `Interface`-loopback shape (no tag concept applies to a domain's own bridge) making the domain's bridge device an SVI, independent of whatever `SwitchingProfile` members enslave into it — validated by the same `unique_addresses`/`routing_table_reference_valid` helpers `Interface`/`Subinterface` use, promoted to `validators` once a third schema type needed them. `BgpPeerGroup`/`BgpPeer` nest one level under `BgpInstance`, showing the pattern for a section nested under another section rather than directly under `Config`; `StaticRoute` nests one level under `StaticRoutingInstance` the same way. `RoutingTable` shows the pattern for a section that only *references* other top-level sections by name (`bgp_instance`, `static_routing_instance`) rather than owning them, with an ownership constraint (at most one table may claim a given instance); `Subinterface.routing_table` is the same by-name reference pattern but without that ownership constraint — many interfaces/subinterfaces may share one routing table (which doubles as a VRF). `Interface` has no "kind" field to mark a loopback interface: an `Interface.name` starting with `LOOPBACK_PREFIX` (`loopback-`, e.g. `loopback-rt1`) is a loopback for the routing table named by the rest of the string (`loopback_table_name`) — this is checked as part of `name`'s own validator (which also rejects a literal `.`, reserved for `nos-cli`'s `<interface>.<tag>` subinterface addressing), which also means `name`'s existing global uniqueness already guarantees at most one loopback per routing table, for free. A loopback interface keeps its L3 config flat on `Interface.addresses`/`routing_table` (unchanged from before subinterfaces existed — a loopback has no VLAN/dot1q concept); every other (physical) interface's L3 config lives entirely under `Interface.subinterfaces: Vec<Subinterface>` instead, `tag == 0` being the untagged/native case (what those same flat fields held before this split) and `1..=4094` a real 802.1q VLAN tag — `valid_addressing_split` (`schema::interface`) enforces the split (a loopback must have no `subinterfaces`; a physical interface must have empty flat `addresses` and no flat `routing_table`), and `valid_subinterface_and_switching_profile_tags` enforces that a `Subinterface`'s tag and a `switching_profile` member's tag (`Untagged`->0, `Dot1q(n)`->n) are disjoint on the same interface — Linux only allows one master device per link (physical or per-tag sub-link), and an L2 switching-profile member wants that link's master to be a bridge while an L3 subinterface wants it to be a VRF. `Interface.addresses`/`Subinterface.addresses` (`Vec<InterfaceAddress>`, `{ address: IpNet, label: Option<String> }`) is a list of small structs rather than `Vec<IpNet>` precisely because one field (`label`) needs to travel with each address rather than the whole list — `label` is stored from commit time onward but not yet applied to any kernel by any driver. `BgpInstance.routing_table` shows a different pattern: a **derived, read-only mirror** of `RoutingTable.bgp_instance` (the other direction of the same association), `#[garde(skip)]` and never touched by any `BgpInstanceOp` — see `crate::derive::sync_routing_table_refs`, called by `nos-config` on load and on every commit, never on a transaction's in-progress config. `BgpPeerGroup.auth: Option<BgpAuth>` is transport authentication (RFC 2385 TCP MD5 or RFC 5925 TCP-AO, `BgpAuth::Md5`/`BgpAuth::Ao{keys: Vec<BgpAoKey>}`, mutually exclusive) — stored clear-text like every other field, validated by a single `custom` closure (`valid_auth`) covering both variants (password/key length limits, unique `send_id`, exactly one `is_current` key) since garde has no per-enum-variant validation. `BgpAoKey.exclude_options` (`#[serde(default)]`) is RFC 5925 §5.2's MAC-coverage choice (`TCP_AO_KEYF_EXCLUDE_OPT`) — both peers must agree, or authentication fails; unvalidated by `valid_auth` (an unconstrained bool). `OspfProfile.auth: Option<OspfAuth>` (RFC 2328 Appendix D) and `Ospfv3Profile.auth: Option<Vec<OspfCryptoKey>>` (RFC 7166, crypto only so no enum) share `OspfCryptoKey`, whose `key_id: u16` is RFC 7166's 16-bit SA ID — `ospf_profile::valid_profile_timers` caps a classic (non-RFC 7474) OSPFv2 key at 255, the one-octet wire field, and `ospfv3_profile::valid_auth` rejects `Md5`. `OspfInstance.areas: Vec<OspfArea>` nests one level under `OspfInstance` (keyed by dotted-quad `area_id`, unique only within the owning instance — never referenced from outside `OspfInstance`, so plain per-parent uniqueness, unlike the next type); `OspfArea.profiles: Vec<OspfProfile>` nests a *second* level under that (keyed by `name`), the first two-level section nesting in this schema. `OspfProfile.name` is validated **globally** unique across every instance's every area (`ospf_profile::unique_name`, flattening `ospf_instances -> areas -> profiles`) rather than per-area, mirroring `BgpPeerGroup.name`'s own cross-instance uniqueness one level shallower — needed because `Interface`/`Subinterface`/`BroadcastDomain.ospf_profile` reference a profile by bare name with no instance/area qualifier, via the shared `ospf_profile_reference_valid` validator (same flattening lookup, the reference-side counterpart of `unique_name`). Each of those three `ospf_profile` fields also requires a `routing_table` set on that same attach point (`valid_addressing_split`'s loopback-`Interface` case, a `Subinterface`-list closure, and `broadcast_domain::valid_broadcast_domains` respectively) — OSPF has no meaning without an L3/VRF context, the same reasoning as `routing_table_reference_valid` itself. `PortAggregate` is a named Linux bonding device (`PortAggregateMode::Xor` static aggregation, or `Lacp` — membership negotiated by `nos-lacpd` via real IEEE 802.1AX, see `lacp/CLAUDE.md`; `lacp_rate: LacpRate::{Slow, Fast}` only meaningful for `Lacp`, `#[serde(default)]` so pre-existing on-disk config still loads; `esi: Option<String>` is the EVPN Ethernet Segment Identifier — ten colon-hex bytes, not all-zero, unique across aggregates (`valid_esi`/`valid_port_aggregates`, parsed by `evpn_id::parse_esi`), acted on by `nos-fdbd`; `redundancy_mode: EsRedundancy::{AllActive, SingleActive}` (`#[serde(default)]`, all-active) is how the PEs sharing the ESI divide the traffic — `valid_port_aggregates` rejects single-active without an `esi`; `lacp_system_id: Option<String>` overrides `nos-lacpd`'s derived Actor System ID with a unicast MAC) with the same config surface as a *physical* `Interface` (`switching_profile`/`mtu`/`subinterfaces` — no flat `addresses`/`routing_table`, since a bond is never a loopback; all its L3 config lives under `subinterfaces` exactly like a physical interface's does). `Interface.lldp_transmit`/`lldp_receive: bool` (both `#[serde(default)]` so pre-existing on-disk config still loads, `#[garde(skip)]` individually) enable `nos-lldpd`'s IEEE 802.1AB transmit/receive on that link independently; `valid_lldp_physical_only` (`schema::interface`, wired in `valid_interfaces`) rejects either flag on a `loopback-*` interface — a loopback has no wire to speak LLDP on. `InterfaceOp::SetLldpTransmit`/`SetLldpReceive` carry an `enabled: bool` rather than a `Set`/`Clear` pair, since a bool has no value to clear (`set` = `true`, `delete` = `false` in `nos-cli`). `Interface.port_aggregate: Option<String>` makes an interface a bonded member by naming an aggregate, the same reference-by-name shape as `switching_profile`; `valid_port_aggregate_membership` (`schema::interface`) rejects a member interface that also carries a `switching_profile` or any `subinterfaces` — the same "one Linux master per link" reasoning as `valid_subinterface_and_switching_profile_tags`. |
| `cli` | The CLI's view of the schema (#109): `#[derive(Cli)]` (the `nos-proto-derive` crate) on every schema struct/enum implements `CliValue`, a static tree of `Node`/`Field`/`Kind`/`Variant` built from the real Rust field types. Every struct field **must** carry `#[cli(...)]` — `topic = <Topic>` (its CLI help, text in `nos-config`'s `docs.rs`), `key` (a list element's key, agreeing with `config_path::ELEMENT_KEYS`), or `hidden` (derived state) — or the crate doesn't compile, so a field can't be added without its CLI documentation. The same attribute carries `words = "…"` (today's CLI spelling, shown; the REST segment `config_path::field_segment` is always accepted too), `alias = "…"` (accepted, never shown), `sugar(word, with, topic)` (a word handled by a `schema/sugar.rs` function returning the field's new value or the canonical words it stands for — `md5-password`, `ao-key`, `crypto-key`, `shutdown <message>`, `orlonger`/`upto`, and a physical interface's L3 words meaning its untagged subinterface) and `sugar = "{a}.{b} => {a} subinterface {b}"` (a list-key rewrite: `eth0.100`). A struct needs `Default` (the starting point of a new element — `Ensure`'s placeholders) unless marked `#[cli(no_default)]`; an enum's `#[default]` variant is what `delete` resets a non-optional field to. `nos-cli`'s `config_grammar` is the one consumer. |

| `validators` | Generic reusable validation helpers (e.g. `unique_in`, `unique_addresses`, `routing_table_reference_valid` — the latter two shared by `Interface`, `Subinterface`, and `BroadcastDomain`, each of which validates its own `addresses`/`routing_table` fields with them). Validators that need to search *across* a nested collection (e.g. peer-group name uniqueness scoped globally, not per-instance), or check a cross-reference specific to one schema type (e.g. `RoutingTable.bgp_instance` naming an existing instance claimed by at most one table), live next to their owning schema type instead. |
| `ops/` | Section-scoped edit types applied to a transaction's in-progress config (e.g. `BgpInstanceOp`, `BgpPeerGroupOp`, `RoutingTableOp`, `InterfaceOp`, `SubinterfaceOp`), wrapped by `ConfigOp`. Never validated — only `garde` at commit time is. A nested section's `Op` variants carry the owning parent's key too (e.g. `BgpPeerGroupOp::SetRemoteAs { instance, name, .. }`, `StaticRouteOp::Set { instance, subnet, .. }`, `SubinterfaceOp::AddAddress { interface, tag, .. }`). `InterfaceOp::AddAddress`/`RemoveAddress` (and `SubinterfaceOp`'s own address variants) show the pattern for a field that's a plain list of scalars (not a keyed sub-collection like `StaticRoute`) — no `Ensure`/`Set` split, just direct add/remove; `AddAddress` upserts by `address` (a repeat call replaces an existing entry's `label` rather than duplicating the address), which is how a label is set, changed, or cleared. There is no dedicated op for marking an interface as a loopback — that's just `Ensure`-ing (or `Edit`-ing) one whose name happens to start with `loopback-`, per `schema::interface::LOOPBACK_PREFIX`. `SubinterfaceOp::AddAddress`/`SetRoutingTable` (unlike `InterfaceOp`'s own address/routing-table ops) cascade-create both the subinterface entry *and* its parent `Interface` if either is missing — `nos-cli`'s `edit interface eth0.100` followed by `set address ...` must work in one step, with no separate "create the subinterface" op. `BgpPeerGroupOp`'s auth variants (`SetMd5Auth`, `SetAoKey`/`RemoveAoKey`, `SetAoCurrentKey`/`SetAoRnextKey`, `ClearAuth`) show a keyed sub-collection nested *inside* one field of an already-nested section (`Vec<BgpAoKey>` inside `BgpPeerGroup.auth`) — `SetAoKey` upserts by `send_id` and starts a fresh list if `auth` wasn't already `Ao`; `SetAoCurrentKey`/`SetAoRnextKey` eagerly clear the flag on every other key in the list at apply time (rather than deferring "at most one" to commit-time validation), since that's cheap and unambiguous. |
| `diff/` | Structural config comparison: `diff_configs(base, candidate) -> ConfigDiff`, plus one `diff_<section>` helper per section (e.g. `diff_bgp_instances`, `diff_bgp_peer_groups`, `diff_routing_tables`, `diff_interfaces`, `diff_subinterfaces`). Pure and synchronous, like `ops/`'s `apply` — only what changed is included, nothing unchanged. `SectionDiff.subsections` nests one section inside another for a nested config section (e.g. `diff_static_routing_instances` nesting `diff_static_routes`, `diff_interfaces` nesting `diff_subinterfaces`). Each `SectionDiff` carries both a display-only `header` (e.g. `"bgp instance r1"`, for `nos-cli`'s renderer) and a structured `name` (the section's identifying key as a plain string — an instance's `name`, a peer's `remote_address`, a route's `subnet`, a subinterface's `tag` — so a machine consumer never has to parse `header`). `DiffScope` names one top-level `ConfigDiff` section; `ConfigDiff::scoped(&self, scopes)` returns a copy keeping only the requested sections, used by `SubscribeDiff` subscribers to receive only what they asked for. |
| `ipc` | IPC message types: `Request` (client→server) and `Event` (server→client), plus `TransactionBase` and `TransactionSnapshot`. `Request::SubscribeDiff { scopes: Vec<DiffScope> }` streams `Event::Diff(ConfigDiff)` scoped to `scopes` — an initial diff against an empty config, then one per commit touching a requested scope — as an alternative to `Request::Subscribe`'s full-snapshot `Event::Config` stream. |

## Wire format

```
┌──────────────┬──────────────────────────┐
│ 4-byte LE u32│ postcard-encoded payload  │
│  (length)    │  (Request or Event enum)  │
└──────────────┴──────────────────────────┘
```

Use `IpcCodec<T>` with `tokio_util::codec::{FramedRead, FramedWrite}` to get typed async send/recv over a `UnixStream`.

## Adding a new config section

1. Add the new struct in `schema/` deriving `Serialize, Deserialize, garde::Validate, Default, Cli`, with a `#[cli(...)]` on every field — a new `Topic` in `docs.rs` (text in `nos-config`'s `docs.rs`) for each field that needs its own help. The shell's `edit`/`set`/`delete` then reach it with no CLI code.
2. Add `#[garde(context(Config as ctx))]` and use the context for any cross-references.
3. Add the field to `Config` in `schema/mod.rs` with `#[garde(dive)]`.
4. Add a sibling `<Section>Op` enum in `ops/<section>.rs` with a synchronous `apply(&self, config: &mut Config) -> Result<(), OpError>` (create/update/delete by name, no `garde` validation — that only runs at commit), then add a `ConfigOp` variant wrapping it in `ops/mod.rs`.
5. Re-export from `lib.rs` if it's part of the public API.

## Adding a scalar top-level field

For a single always-present scalar with exactly one possible edit (e.g. `hostname`), skip the dedicated `<Section>Op` enum and file — that convention exists to give named/keyed collections per-name create/update/delete semantics, which a lone scalar doesn't need:

1. Add the field directly to `Config` in `schema/mod.rs` with its own `#[garde(...)]` rule(s). If the desired default isn't the field type's own `Default::default()` (e.g. `hostname` defaults to `"nos"`, not `""`), add `#[serde(default = "some_fn")]` on the field — required so pre-existing on-disk config missing that key still deserializes — and give `Config` a manual `impl Default` instead of deriving it.
2. Add one `ConfigOp` variant directly in `ops/mod.rs`'s enum (e.g. `SetHostname(String)`), with an `apply` arm that sets the field. No new `OpError` variant needed unless the edit can fail structurally.

## Wire compatibility

`Request`/`Event` variants must always be **appended**, never inserted or reordered — `postcard` encodes enum variants by index, so reordering breaks compatibility with already-built binaries.
