# nos-proto — Shared Protocol Types

Single source of truth for all inter-process wire contracts in NOS.

## Why this crate exists

Component processes (`nos-bgp`, `nos-rib`, …) must not depend on `nos-config` internals — only on the shared types they exchange. By owning all shared types here, we get:
- **Protocol sync at compile time**: change a type → compiler breaks every consumer immediately.
- **Clean dependency graph**: components depend on `nos-proto`, not on each other.

## Contents

| Module | Purpose |
|--------|---------|
| `schema/` | Config tree types: `Config`, `BgpInstance`, `BgpPeerGroup`, `BgpPeer`, `RoutingTable`, `StaticRoutingInstance`, `StaticRoute`, `Interface`. Derived `garde::Validate` for commit-time validation. `BgpPeerGroup`/`BgpPeer` nest one level under `BgpInstance`, showing the pattern for a section nested under another section rather than directly under `Config`; `StaticRoute` nests one level under `StaticRoutingInstance` the same way. `RoutingTable` shows the pattern for a section that only *references* other top-level sections by name (`bgp_instance`, `static_routing_instance`) rather than owning them, with an ownership constraint (at most one table may claim a given instance); `Interface.routing_table` is the same by-name reference pattern but without that ownership constraint — many interfaces may share one routing table (which doubles as a VRF). `Interface` has no "kind" field to mark a loopback interface: an `Interface.name` starting with `LOOPBACK_PREFIX` (`loopback-`, e.g. `loopback-rt1`) is a loopback for the routing table named by the rest of the string (`loopback_table_name`) — this is checked as part of `name`'s own validator, which also means `name`'s existing global uniqueness already guarantees at most one loopback per routing table, for free. `Interface.addresses: Vec<InterfaceAddress>` (`{ address: IpNet, label: Option<String> }`) is a list of small structs rather than `Vec<IpNet>` precisely because one field (`label`) needs to travel with each address rather than the whole list — `label` is stored from commit time onward but not yet applied to any kernel by any driver. `BgpInstance.routing_table` shows a different pattern: a **derived, read-only mirror** of `RoutingTable.bgp_instance` (the other direction of the same association), `#[garde(skip)]` and never touched by any `BgpInstanceOp` — see `crate::derive::sync_routing_table_refs`, called by `nos-config` on load and on every commit, never on a transaction's in-progress config. `BgpPeerGroup.auth: Option<BgpAuth>` is transport authentication (RFC 2385 TCP MD5 or RFC 5925 TCP-AO, `BgpAuth::Md5`/`BgpAuth::Ao{keys: Vec<BgpAoKey>}`, mutually exclusive) — stored clear-text like every other field, validated by a single `custom` closure (`valid_auth`) covering both variants (password/key length limits, unique `send_id`, exactly one `is_current` key) since garde has no per-enum-variant validation. |
| `derive` | `sync_routing_table_refs(config: &mut Config)` — recomputes every `BgpInstance.routing_table` from the authoritative `RoutingTable.bgp_instance` references. Pure and synchronous, like `ops/`'s `apply`/`diff/`'s `diff_*`; called by `nos-config`, never by a client. |
| `validators` | Generic reusable validation helpers (e.g. `unique_in`). Validators that need to search *across* a nested collection (e.g. peer-group name uniqueness scoped globally, not per-instance), or check a cross-reference (e.g. `RoutingTable.bgp_instance` naming an existing instance claimed by at most one table), live next to their owning schema type instead, since they're not generic. |
| `ops/` | Section-scoped edit types applied to a transaction's in-progress config (e.g. `BgpInstanceOp`, `BgpPeerGroupOp`, `RoutingTableOp`, `InterfaceOp`), wrapped by `ConfigOp`. Never validated — only `garde` at commit time is. A nested section's `Op` variants carry the owning parent's key too (e.g. `BgpPeerGroupOp::SetRemoteAs { instance, name, .. }`, `StaticRouteOp::Set { instance, subnet, .. }`). `InterfaceOp::AddAddress`/`RemoveAddress` show the pattern for a field that's a plain list of scalars (not a keyed sub-collection like `StaticRoute`) — no `Ensure`/`Set` split, just direct add/remove; `AddAddress` upserts by `address` (a repeat call replaces an existing entry's `label` rather than duplicating the address), which is how a label is set, changed, or cleared. There is no dedicated op for marking an interface as a loopback — that's just `Ensure`-ing (or `Edit`-ing) one whose name happens to start with `loopback-`, per `schema::interface::LOOPBACK_PREFIX`. `BgpPeerGroupOp`'s auth variants (`SetMd5Auth`, `SetAoKey`/`RemoveAoKey`, `SetAoCurrentKey`/`SetAoRnextKey`, `ClearAuth`) show a keyed sub-collection nested *inside* one field of an already-nested section (`Vec<BgpAoKey>` inside `BgpPeerGroup.auth`) — `SetAoKey` upserts by `send_id` and starts a fresh list if `auth` wasn't already `Ao`; `SetAoCurrentKey`/`SetAoRnextKey` eagerly clear the flag on every other key in the list at apply time (rather than deferring "at most one" to commit-time validation), since that's cheap and unambiguous. |
| `diff/` | Structural config comparison: `diff_configs(base, candidate) -> ConfigDiff`, plus one `diff_<section>` helper per section (e.g. `diff_bgp_instances`, `diff_bgp_peer_groups`, `diff_routing_tables`, `diff_interfaces`). Pure and synchronous, like `ops/`'s `apply` — only what changed is included, nothing unchanged. `SectionDiff.subsections` nests one section inside another for a nested config section (e.g. `diff_static_routing_instances` nesting `diff_static_routes`). Each `SectionDiff` carries both a display-only `header` (e.g. `"bgp instance r1"`, for `nos-cli`'s renderer) and a structured `name` (the section's identifying key as a plain string — an instance's `name`, a peer's `remote_address`, a route's `subnet` — so a machine consumer never has to parse `header`). `DiffScope` names one top-level `ConfigDiff` section; `ConfigDiff::scoped(&self, scopes)` returns a copy keeping only the requested sections, used by `SubscribeDiff` subscribers to receive only what they asked for. |
| `ipc` | IPC message types: `Request` (client→server) and `Event` (server→client), plus `TransactionBase` and `TransactionSnapshot`. `Request::SubscribeDiff { scopes: Vec<DiffScope> }` streams `Event::Diff(ConfigDiff)` scoped to `scopes` — an initial diff against an empty config, then one per commit touching a requested scope — as an alternative to `Request::Subscribe`'s full-snapshot `Event::Config` stream. |
| `broker` | `ServiceRef` (`Config` / `RibTable(String)` / `Interfaces` / `Log` / `BgpInstance(String)`), `WatchdogRequest::ResolveEndpoint { service }`, `WatchdogEvent::Endpoint(PathBuf)` / `NotAvailable` — `nos-watchdogd`'s endpoint-resolution protocol, so no client needs to hardcode another daemon's socket path. `Interfaces`/`Log` (unlike `RibTable`/`BgpInstance`) carry no name — there's exactly one `nos-interfaced` and one `nos-logd` instance, each resolved directly like `Config` rather than through the registry. |
| `rib` | `RibRequest::GetRoutes` / `Lookup { addr }` / `GetVrfName` / `GetTableId`, `RibEvent::Routes(Vec<PrefixRoutes>)` / `Match(PrefixRoutes)` / `NoMatch` / `Error` / `VrfName(Option<String>)` / `TableId(Option<u32>)`, plus `PrefixRoutes` (a prefix + its candidates, best-to-worst) and the wire twins `RouteEntry`/`RouteSourceKind` of `nos-rib`'s internal `RibEntry`/`RouteSource` — `nos-ribd`'s route-query protocol. `GetVrfName`/`VrfName` is the first direct daemon-to-daemon link in the system: `nos-interfaced`'s Linux driver queries the owning `nos-ribd` instance (found via the broker's `ServiceRef::RibTable`) for its Linux VRF interface name, since that name is allocated and owned entirely by `nos-ribd`'s driver and can't be derived independently. `GetTableId`/`TableId` is symmetric — the same driver also needs the table's raw numeric kernel table id (not just its VRF name) to name the kernel device for a loopback interface (`lo<table_id>`, see `schema::interface::LOOPBACK_PREFIX`). |
| `interface` | `InterfaceRequest::GetInterfaces` / `GetInterface { name }`, `InterfaceEvent::Interfaces(Vec<InterfaceStatus>)` / `Interface(InterfaceStatus)` / `NotFound`, plus `InterfaceStatus` (the wire twin of `nos-interface`'s internal `InterfaceState`) — `nos-interfaced`'s interface-query protocol. |
| `bgp` | `BgpRequest::GetSummary`, `BgpEvent::Summary(Vec<PeerSummary>)`, plus `PeerSummary` (peer address, peer-group, remote AS/BGP ID once negotiated, `BgpSessionState`, uptime, negotiated hold-time/keepalive) — one `nos-bgpd` instance's session-summary protocol, backing `nos-cli`'s `show bgp brief`. `BgpSessionState::Idle` is a reporting-only value (`nos-bgp::fsm` itself only models `OpenSent`/`OpenConfirm`/`Established`) meaning no connection attempt has an OPEN in flight yet. |
| `log` | `LogRequest::Push(LogEntry)` / `GetLogs { source, limit }` / `Tail { source }`, `LogEvent::Logs(Vec<LogEntry>)` / `Line(LogEntry)` / `Error`, plus `LogEntry` (timestamp, level, source, target, message, fields) and `LogLevel` — `nos-logd`'s log-collection protocol. `Push` is the one request every other component process sends continuously over one long-lived connection rather than one-shot, and gets no reply; `GetLogs`/`Tail` are `nos-cli`'s one-shot snapshot and live-tail queries respectively, with `Tail` replying once with the current buffer before streaming further `Line`s. |
| `paths` | `DEFAULT_CONFIG_SOCKET`/`DEFAULT_WATCHDOG_SOCKET` — the two bootstrap socket defaults that stay fixed rather than being resolved via the broker. |
| `codec` | `IpcCodec<T>`: framing codec (4-byte LE length prefix + postcard payload). Generic over any `Serialize + DeserializeOwned` type, so it frames the config, broker, RIB, and interface protocols alike. |

## Wire format

```
┌──────────────┬──────────────────────────┐
│ 4-byte LE u32│ postcard-encoded payload  │
│  (length)    │  (Request or Event enum)  │
└──────────────┴──────────────────────────┘
```

Use `IpcCodec<T>` with `tokio_util::codec::{FramedRead, FramedWrite}` to get typed async send/recv over a `UnixStream`.

## Adding a new config section

1. Add the new struct in `schema/` deriving `Serialize, Deserialize, garde::Validate`.
2. Add `#[garde(context(Config as ctx))]` and use the context for any cross-references.
3. Add the field to `Config` in `schema/mod.rs` with `#[garde(dive)]`.
4. Add a sibling `<Section>Op` enum in `ops/<section>.rs` with a synchronous `apply(&self, config: &mut Config) -> Result<(), OpError>` (create/update/delete by name, no `garde` validation — that only runs at commit), then add a `ConfigOp` variant wrapping it in `ops/mod.rs`.
5. Re-export from `lib.rs` if it's part of the public API.

## Adding a scalar top-level field

For a single always-present scalar with exactly one possible edit (e.g. `hostname`), skip the dedicated `<Section>Op` enum and file — that convention exists to give named/keyed collections per-name create/update/delete semantics, which a lone scalar doesn't need:

1. Add the field directly to `Config` in `schema/mod.rs` with its own `#[garde(...)]` rule(s). If the desired default isn't the field type's own `Default::default()` (e.g. `hostname` defaults to `"nos"`, not `""`), add `#[serde(default = "some_fn")]` on the field — required so pre-existing on-disk config missing that key still deserializes — and give `Config` a manual `impl Default` instead of deriving it.
2. Add one `ConfigOp` variant directly in `ops/mod.rs`'s enum (e.g. `SetHostname(String)`), with an `apply` arm that sets the field. No new `OpError` variant needed unless the edit can fail structurally.

## Wire compatibility

`Request`/`Event` variants must always be **appended**, never inserted or reordered — `postcard` encodes enum variants by index, so reordering breaks compatibility with already-built binaries.
