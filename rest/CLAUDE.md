# nos-rest — REST API daemon (`nos-restd`)

An HTTP+JSON management API for the whole system: every `nos-cli` `show` query and the full transaction/config-editing surface. One process per `RoutingTable` that has `rest-api` pinned to it, listening on **one configured address inside that table's VRF**. **Every request needs a TLS client certificate** for a user in `Config.users` (see `auth.rs`, `login.rs` and root `CLAUDE.md`'s "User authentication"); the VRF and pinned address are a second boundary, so still pin it to a management address. The listener is HTTPS only — TLS 1.3 with post-quantum key exchange (hybrid `X25519MLKEM768`, nothing else), HTTP/2 or HTTP/1.1 by ALPN.

## Authentication (`auth.rs`, `login.rs`)

Mutual TLS replaces per-request credentials: the password crosses the network once, at login, and every later request carries only the client certificate.

- **Getting a certificate.** `POST /v1/login {user, password, csr}` — the only route reachable without one — sends the password and a base64 DER PKCS#10 request for an ECDSA P-256 key the client generated (`openssl req -new -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -keyout key.pem -outform DER | base64 -w0`). `nos-restd` forwards it to the watchdog (`WatchdogRequest::RestLogin`, allowed for `restd` only), which verifies it exactly as it does for `nos` (`nos_password::verify_or_dummy`) and returns a `user/<name>` certificate from the **REST CA** for the public key in the CSR — the client's private key never leaves it. `POST /v1/renew {csr}` trades the certificate the connection presented for a fresh one (`RestRenew`; refused once the user is deleted); lifetime is `--pki-user-lifetime`, renew at half of the `lifetime_secs` in the reply. Clients trust the REST CA from `rest-ca.crt` in the watchdog's `--pki-dir` (`/run/nos/pki`) — distribute it out of band; it is never served over the network, because fetching a trust anchor over an unauthenticated connection would let whoever intercepts that fetch also capture the login password.
- **Failed logins.** One attempt at a time *per username* (`LoginGate`), and a failed one costs 1s before the next may start — however many streams or connections the guesses arrive on. The broker's own per-connection throttle only covers a direct `Login`: `RestLogin` arrives over `nos-restd`'s shared connection, so the delay has to be here. ponytail: per-username only; many usernames in parallel are unthrottled (each still costs an argon2 verify). After 5 failures within 60s (counted from the first; a success resets it) further attempts on that username get `429` with `Retry-After` (RFC 6585) straight away — no watchdog call, no delay, even with the right password. This lets an attacker block one user's *login* for the window (not `renew`, not certificates already issued).
- **Every other route** (`client_auth`, the **last** `.layer(..)` in `api::router`, so it wraps the merged Swagger UI, `/openapi.json` and the SSE stream too): the TLS layer has already verified the certificate against the REST CA and `listen.rs` has attached the user its URI SAN names to every request of that connection (`PeerUser`, a request extension). Here the user must also **still exist in the running config** — one `Get` from `nos-configd` per request — so deleting a user locks their (still-valid) certificate out on the very next request, even on a connection that is already open. No verified user is `401` (with `WWW-Authenticate: Mutual realm="nos", login="/v1/login"` — a custom scheme name, since a client certificate has no registered one; it names the flow that gets one), an unreachable `nos-configd` is `503` (fail closed). An open SSE stream is authenticated at connect time only. ponytail: one config `Get` per request (a pooled IPC round trip, no handshake); add a short-TTL cache of the user list only if that is measured to matter.
- `ApiDoc` declares the `mtls` security scheme (`MutualTlsScheme`, `SecurityScheme::MutualTls`) and a global requirement; `login` is `security(())`. Browsers can present a REST certificate (it is ECDSA P-256 on purpose), so Swagger UI works once one is imported; `curl` needs `--cert/--key/--cacert` and a curl/OpenSSL new enough to offer `X25519MLKEM768`.
- Users appear in the generated config tree like any section (`/v1/transactions/{tx}/user/{name}`); a clear `password` in a `PUT` is hashed by `nos-configd`, and `GET /config` returns the hashes (behind auth).

## Transport (`listen.rs`, `tls.rs`, `ipc.rs`)

- **Listener.** After the VRF bind, `tls::start` asks the watchdog for a server certificate for the bound address (`IssueRestServerCert`, on a key generated here, IP SAN from the config — never from the CSR) and renews it at half its life. Each accepted connection gets its own task: TLS handshake (`nos_pki::rest::RestServer::accept`, 5s timeout — a slow peer never stalls accept), then hyper-util's `auto::Builder` (HTTP/1.1 + HTTP/2; 128 concurrent streams, 30s h2 keep-alive, 10s header-read timeout) with `Extension(PeerUser)` on every request. Shutdown is graceful, capped at 2s by `stop()` so a keep-alive client can't hold a rebind hostage. A client that offers only classical key exchange, or a certificate from another CA, never gets a request through.
- **One connection, many requests.** HTTP/2 multiplexes concurrent requests over one TLS handshake; a client should reuse its connection pool.
- **Behind it, IPC connections are pooled** (`Daemons::call` in `ipc.rs`). Every IPC connection is a mutual-TLS handshake, and a request used to cost three (config `Get` for auth, the broker to resolve, the daemon itself). Now a finished call parks its connection (up to 8 idle per daemon, discarded after 5 minutes) and the next call to that daemon reuses it, and broker answers are cached (socket paths are fixed per daemon name; a failed call drops the entry, and a "not running" answer is never cached). The one rule this leans on: **a plain request gets exactly one event back, and the server keeps reading requests on the same connection** — true of every daemon's server; streaming replies (`LogRequest::Tail`) use `open_stream` and a connection of their own. A parked connection whose daemon restarted shows up as "dead before any reply" and is retried once on a fresh connection; only that case is retried, so a request the daemon received is never sent twice.

## Pinning and supervision

`RoutingTable.rest_api: Option<RestApi { address, port }>` (`set routing-table <t> rest-api address <ip> [port <n>]`). `nos-watchdogd` runs `nos-restd --table <name>` for every table that has it set, via the same `instances::manage` as `nos-ribd`/`nos-bgpd`/`nos-ospfd`, with one addition: `Managed.claim_label`. The other families spawn a process per section; this one is *opt-in per table*, and a field flip on an existing table is a `Modified` diff (a no-op for the others), so the watchdog keys on the `rest-api` `FieldDiff` (`nos_proto::diff::routing_table::REST_API_LABEL`): a value other than `"unset"` spawns, `"unset"`/removal stops. It has no IPC query listener, so `Managed.endpoint` is `None` (no `--listen-socket`, no registry entry).

## Listening (`listen.rs`)

Every 1s tick — and immediately on a routing-table config diff — `Listener` compares what config *wants* (this table's `rest_api`) with what is *bound* and converges:

- the VRF name comes from the owning `nos-ribd` (`ServiceRef::RibTable` + `RibRequest::GetVrfName`), exactly like `nos-bgpd`; `None` means "not created yet" and is retried;
- the socket is bound to `address:port` (no wildcard) with `SO_BINDTODEVICE=<vrf>` (a per-crate copy of `nos-bgpd`'s `tcp::bind_listener`);
- an address that isn't configured on an interface in the VRF yet (`EADDRNOTAVAIL`) is a transient state, retried each tick and logged once per change (`rest api not listening yet: …`);
- a changed address/port, or a VRF that was deleted and recreated under the same name (its `nos-ribd` restarted — detected by the device's `ifindex` changing, since `SO_BINDTODEVICE` resolves the name once), drops and rebinds the listener;
- a `nos-configd` read failure keeps the current listener rather than tearing it down.

Log lines the e2e phase greps: `rest api listening table=… vrf=… address=… port=…`, `rest api stopped listening`, `rest api not listening yet: …`.

## Endpoints (`/v1`, see `api.rs`)

Auth (POST): `/login` (no certificate needed), `/renew`. Show (GET, the daemon's own reply payload as JSON): `/config`, `/fdb/{domain}` (a broadcast domain's `nos-fdbd` forwarding database), `/routes/{table}[/{addr}]`, `/interfaces[/{name}]`, `/port-aggregates[/{name}]`, `/lacp[/{name}]`, `/lldp/neighbors`, `/logs?source=&limit=`, `/logs/follow?source=&limit=` (`show log --follow` as Server-Sent Events: the backlog — trimmed to `limit` — then each new entry as an `event: log` whose data is the JSON `LogEntry`, until the client disconnects; the daemon-side `Tail` connection's write half is held open for the stream's lifetime), `/bgp/summary`, `/ospf/{neighbors,database}`, `/ospfv3/{neighbors,database}`. The router-wide ones (`bgp`/`ospf`/`ospfv3`) iterate the instances in the running config and report a per-instance `"not running"` instead of failing, like `nos-cli`. A daemon that isn't reachable is `503`. **Actions** (`clear.rs`, `POST`, change live state never config): `/bgp/{instance}/peer/{peer}/soft-in` = `clear bgp <instance> <peer> soft-in` — asks the live session for an RFC 2918 ROUTE-REFRESH; 404 if the peer isn't configured or has no `Established` session (the daemon doesn't distinguish the two), 503 if that instance's `nos-bgpd` isn't running.

**Transactions — the config tree is the URL tree:**

| | |
|---|---|
| `POST /transactions/<tx>?base=blank\|current` | open or resume (201 / 200) |
| `GET` / `PUT` / `DELETE /transactions/<tx>` | whole in-progress config / set the whole config / discard |
| `GET` / `PUT` / `DELETE /transactions/<tx>/<path>` | read / set / remove one subsection |
| `GET /transactions/<tx>/diff`, `POST …/commit` | diff vs running; validate + commit (422 on a validation error, transaction kept) |
| `ETag` / `If-Match` / `If-None-Match` | every transaction reply is tagged with its generation; `PUT`/`DELETE`/commit with a stale `If-Match` → 412, `GET` with a matching `If-None-Match` → 304 (see below) |

**Optimistic concurrency (RFC 9110 §8.8, §13.1).** Every reply that describes a transaction — `POST` (open/resume), `GET` (whole or subsection), a successful `PUT`, a subsection `DELETE`'s 204 — carries a strong `ETag`: the transaction's `generation` (`TransactionSnapshot.generation`, a per-transaction counter `nos-configd` bumps on every `ApplyOp`/`SetTransactionPath`) as a quoted decimal, `"17"`. It is per *transaction*, not per subsection, on purpose: the store serializes on one mutex entry per transaction, so that is the real conflict domain, and two clients editing disjoint paths of the same transaction still conflict. `PUT`, `DELETE` and `POST …/commit` honour an optional `If-Match` (`*`, or one `"<digits>"` tag — anything else is 400): it travels as `if_match: Option<u64>` on `SetTransactionPath`/`DiscardTransaction`/`CommitTransaction` and is checked by `nos-configd` under the same transactions lock as the edit (a real compare-and-set), a mismatch being `ConfigError::PreconditionFailed` → **412** with nothing changed (a refused commit keeps the transaction open, like a 422). `*` maps to no store-side precondition, since existence is already the 404 check. `GET` honours `If-None-Match` the same way (`*` or one tag) and answers **304** with the `ETag` and no body when it matches. Both are opt-in: a caller that sends neither (`nos-cli`'s `ApplyOp`, `nos-provision`) keeps last-write-wins. `nos-e2e`'s `Router::edit` sends `If-Match` on its `PUT` and commit, so every provisioning phase exercises the matching path; the `rest` phase (`rest_etag`) proves the 412/304 paths against the real daemon. The tags are `tx.rs`'s `etag`/`Condition`; a discarded transaction's 204 carries none.

`<path>` is e.g. `hostname`, `routing-table/rt1`, `bgp-instance/r1/peer-group/pg1`, `ospf-instance/o1/area/0.0.0.0/profile/p1`, `static-routing-instance/s1/route/10.1.0.0%2F16`. The grammar lives in `nos_proto::config_path` (segment = kebab-case field name, a list field is followed by the element's key; a `PUT` to a list element that doesn't exist appends it; the body's key must match the URL). `diff` and `commit` are static routes and therefore reserved first segments. The handlers split the **raw** URI path before percent-decoding, so a key containing `/` stays one segment. The server-side edit is one new `nos-configd` request, `Request::SetTransactionPath` — atomic under the transactions lock, all-or-nothing (the edited JSON must still deserialize as a `Config`), and, like every op, unvalidated until commit.

## Errors (`error.rs`)

Every error is an RFC 9457 problem document, `Content-Type: application/problem+json`: `{"type":"about:blank","title":<reason phrase>,"status":<HTTP status>,"detail":<message>}` (`ErrorBody`; `instance` is omitted, since a handler can't see the URI). Handlers return `ApiError`, whose variant picks the status (400/401/404/412/422/503/502). Errors the framework raises itself — unknown route 404, 405 (its `Allow` header is preserved), extractor rejections — are re-rendered by `problem_for_framework_errors`, the outermost layer in `api::router`; it leaves problems and non-error responses (SSE included) alone. `openapi::document` re-keys every `ErrorBody` response to `application/problem+json`, so the `#[utoipa::path]` annotations just say `body = ErrorBody`. Never build an error response by hand.

## OpenAPI (`openapi.rs`)

`GET /openapi.json`, browsable at `/swagger-ui/` (`utoipa-swagger-ui` with the `vendored` feature: assets are embedded in the binary, so there is no CDN dependency at runtime or GitHub download at build; it is pointed at the `/openapi.json` route rather than given a `utoipa` struct, so it shows the generated config-tree paths too). Show and transaction-root operations are `#[utoipa::path]`-annotated and registered with `routes!`, so the router and the spec can't disagree. The config-tree paths are **generated** by walking the `Config` schema (the router serves them all with one `{*path}` route) using `config_path::{field_segment, key_field}` — the same naming and key rules the server resolves paths with; the walker debug-asserts `field_matches` for every path it emits and tests check every parameter is declared and every `$ref` resolves. `nos-proto`'s `openapi` feature adds `ToSchema` derives (off unless `nos-rest` is built); `IpAddr`/`IpNet` fields carry `schema(value_type = String)`, and the recursive `SectionDiff.subsections` needs `schema(no_recursion)`. Adding a config section needs no OpenAPI work; adding a *show* endpoint needs a `#[utoipa::path]` and a `routes!` line. Any change to the document fails `tests/openapi_snapshot.rs` until `make docs-fix` rewrites the checked-in copy, `docs/openapi.json`, which the user docs (`docs/api.md`) link to.

## Testing

`tests/api.rs` drives the real router (via `tower::ServiceExt::oneshot`, with the `PeerUser` a verified certificate would produce injected as a request extension) against a **real** `nos-config` `ConfigStore` behind its own IPC server — so the path-set semantics tested are the shipped ones — plus a fake broker (which stands in for the CA on `RestLogin`/`RestRenew`) and fake `nos-ribd`. The pooling tests count the connections a fake daemon accepts (ten requests → one; a daemon that hangs up after every reply → retried, not an error). The `over_tls` module runs the real `listen::serve` on 127.0.0.1 with a real REST CA and a hyper HTTP/2 client: 20 concurrent requests over one connection, a certificate for an unknown user or none at all → 401, login without a certificate, a foreign CA's certificate refused. The VRF bind needs `CAP_NET_RAW`, so only `nos-e2e rest` covers that.
