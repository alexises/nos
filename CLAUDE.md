# NOS — Network Operating System

A network operating system built from scratch in Rust.

## Agent tooling requirements

Every agent working in this repo — the main session and any subagent spawned via the Agent tool (Explore, general-purpose, fork, etc.) — MUST always use:

- **`rtk`** for shell command output, per the "Command output" conventions at the bottom of this file. Subagents don't inherit the user's global CLAUDE.md, so this rule is restated here.
- **CodeGraph** (`codegraph_explore` MCP tool, or `codegraph explore "<query>"` from the shell) before grep/find or reading files, to locate or understand code — this repo has a `.codegraph/` index at its root.

The project's Claude tooling is tracked in `.claude/`, so every worktree (incl. `isolation: "worktree"` agents) gets it:

- `.claude/settings.json` wires the `PreToolUse` hook via `"$CLAUDE_PROJECT_DIR"`, never a relative path (a relative one exits 127 inside a worktree, #128).
- `.claude/hooks/codegraph-first.sh` denies `Grep` and `grep`/`rg` over the tree; append `# cg-ok` to a Bash command for a raw text scan (logs, non-code files).
- `.claude/commands/issue.md` is the `/issue` workflow.
- Machine-local files stay untracked: `.claude/settings.local.json`, `.claude/worktrees/`.

## Architecture

### Process model

Each component (BGP, RIB, OSPF, …) runs as a dedicated OS process. No component shares memory with another.

```
┌──────────────────────────────────────────────────────┐
│  nos-config process                                  │
│  ConfigStore (named transactions/running) + IPC      │
│  Listens on: /run/nos/config.sock                    │
└───────────────────────┬──────────────────────────────┘
                        │ Unix socket (nos-proto wire protocol)
          ┌─────────────┼─────────────┬─────────────┐
          ▼             ▼             ▼             ▼
    nos-bgp         nos-rib       nos-ospf       nos-cli
    process         process       process        (shell)
```

### IPC transport

**Transport:** Unix domain sockets carrying **mutually authenticated, post-quantum TLS 1.3** (`nos-pki`, `tokio-rustls` over `UnixStream`) — see "IPC security" below.  
**Serialization:** `postcard` (binary, compact, serde-based, no-alloc capable).  
**Framing:** 4-byte little-endian length prefix + postcard payload (see `nos-proto::codec::IpcCodec`).

This gives maximum performance for intra-host IPC with full Rust type safety — no HTTP overhead, no IDL outside the type system.

### Protocol spec sync

All wire types live in `nos-proto`. Since every component imports its message types from there, changing a type causes a **compile error in every consumer immediately** — stronger than protobuf's silent field-drop. This is the mechanism that keeps all processes in sync.

### Dependency graph

```
nos-proto   (no NOS dependencies)
    ↑               ↑
nos-config      nos-bgp, nos-rib, nos-ospf, nos-cli, …
(server)        (clients)
```

Component crates depend on `nos-proto` for types and `nos-proto::IpcCodec` for the framing codec. They do **not** depend on `nos-config` internals.

### Config subscription protocol

```
Client → Server:
  Request::Get                 one-shot read of the current running config
  Request::Subscribe           receive current snapshot + all future commits
  Request::Unsubscribe         stop receiving updates (connection stays open)
  Request::Save                persist the current running config to disk
  Request::OpenTransaction     open (or resume) a named transaction from blank/current
  Request::ApplyOp             apply one edit (e.g. a BgpInstanceOp) to a named transaction
  Request::GetTransaction      one-shot read of a named transaction's in-progress config
  Request::CommitTransaction   validate, promote to running, broadcast, and delete the transaction (if_match: optional generation precondition, RFC 9110 §13.1.1)
  Request::DiscardTransaction  delete a named transaction without touching running config (if_match as above)
  Request::Describe            one-shot fetch of one operation's documentation, by Topic
  Request::SetTransactionPath  set/remove one subsection of a named transaction by URL-style path (whole config for an empty path) — see nos_proto::config_path (if_match as above)

Server → Client:
  Event::Config(Config)             config snapshot (initial + on every commit, incl. via a transaction commit)
  Event::Error(String)              error from the daemon
  Event::Saved                      confirms the running config was persisted (reply to Save)
  Event::Transaction(Snapshot)      a named transaction's current state (reply to Open/Apply/Get/SetTransactionPath), incl. its generation (0 at open, +1 per edit — nos-restd's ETag)
  Event::Committed                  confirms a transaction was committed
  Event::Discarded                  confirms a transaction was discarded
  Event::Description(CommandDoc)    one operation's documentation (reply to Describe)
```

`Describe`/`Description` exist so that the shell's help text (what a command does, in human terms, for the CLI's user) is authored once in `nos-config` and shared by every client, rather than duplicated per-client. A `Topic` is one config-tree node or field — named by the mandatory `#[cli(topic = …)]` on every schema field (`nos-proto-derive`, see `proto/CLAUDE.md`'s `cli` row), so a field can't exist without its CLI help — or one show/shell command (`nos-cli`'s `spec.rs` rows). `nos-cli`'s config commands (`edit`/`set`/`delete`), their help, `?`, Tab and usage are all generated from that schema tree (`cli/src/config_grammar.rs`, #109) and sent as `SetTransactionPath`, the same generic write REST uses. The schema's `///` comments are the REST API's (Swagger) text, deliberately separate. It's scoped to a single `Topic` per request (not a bulk catalog fetch) so a client only ever fetches the docs it actually displays.

### Named transactions

Editing the config happens inside a **named transaction**, held server-side in `nos-config`, not tied to any one connection. `OpenTransaction` creates it from a blank config or a clone of the running config (`TransactionBase::Blank`/`Current`), or — if a transaction with that name already exists — resumes its current in-progress state unchanged. `CommitTransaction` validates the transaction and, if valid, atomically replaces the running config and broadcasts it to every `Subscribe`d connection (the same fan-out `Get`/`Subscribe` already use); on invalid input the transaction is left alive so the caller can keep editing. `DiscardTransaction` deletes it outright. Because transactions live only in the daemon and are addressed by name, a client can disconnect (crash, Ctrl-C, network drop) and resume the same transaction later from a fresh connection — see `nos-cli`'s `configure <name>` command.

### Config plane vs data plane

| Plane | Transport | Pattern |
|-------|-----------|---------|
| Config | Unix socket + postcard | Request/subscribe |
| Data (e.g. BGP→RIB routes) | Unix socket + postcard | Fire-and-forget push over a persistent connection |

Both planes use the same transport stack. In practice the data plane so far reuses each target daemon's existing per-instance socket and request/event enum (e.g. `nos-ribd`'s `RibRequest::PushBgpRoutes`, `nos-bgpd`'s `BgpRequest::RedistributeRoutes`) rather than a dedicated separate socket/message-type pair — a fire-and-forget variant appended to the same `Request`-style enum the config plane already frames with `IpcCodec`, sent over one long-lived connection (`Full` snapshot on connect, incremental `Add`/`Remove` after), same pattern as `nos-logd`'s `LogRequest::Push`. A future high-enough-volume feed could still justify a dedicated socket/message-type pair instead.

### Process supervision

`nos-watchdog` (binary `nos-watchdogd`) starts and supervises the other component processes as OS child processes, and is the container's entrypoint. It always runs exactly one supervised `nos-configd`. For BGP, rather than a single static `nos-bgpd`, the watchdog subscribes to `nos-configd` over its own `--config-socket` connection (`Request::SubscribeDiff`, independent of whatever address is forwarded to the `nos-configd` child via the opaque `--configd-arg` pass-through) and dynamically spawns one `nos-bgpd --instance <name>` per `BgpInstance` in the live config. It reconciles on every diff it receives: a fresh connection's first diff is synthesized against an empty config (so every currently-configured instance shows up as `Added`) and is treated as the authoritative full membership list — anything already running that isn't in it gets stopped, closing the gap where an instance removed while disconnected could otherwise leak as an orphan process — while every later diff on the same connection is applied incrementally (`Added`/`Removed` only — `Modified` is a no-op at this level, since `nos-bgpd`, like `nos-ribd`, independently subscribes to config and re-resolves its own peers/VRF on every relevant diff rather than needing a restart). The config subscription itself reconnects on a fixed 1s delay with no backoff if dropped (distinct from the exponential process-crash backoff below) — since `nos-configd` is supervised independently, its own crash/restart is transparent to already-running `nos-bgpd` instances. Every supervised process (`nos-configd` and each per-instance `nos-bgpd`) is respawned after an exponential backoff on unexpected exit (starting at 1s, doubling, capped at 30s, resetting to 1s once it's stayed up for 60s). On SIGTERM or SIGINT to the watchdog, or an instance's removal from config, its process is sent SIGINT (the signal `nos-configd`/`nos-bgpd` handle via `tokio::signal::ctrl_c()`), given up to 10s to exit cleanly, then force-killed — on watchdog shutdown this happens for every remaining process before it exits, so nothing is left orphaned.

RIB tables follow the identical dynamic-spawn pattern: the watchdog subscribes to `DiffScope::RoutingTables` and spawns one `nos-ribd --table <name>` per `RoutingTable` in the live config, with the same first-diff-is-authoritative reconciliation, fixed 1s reconnect delay, and exponential per-process crash backoff as BGP instances. `Modified` is likewise a no-op at this level — a table's `bgp_instance`/`static_routing_instance` association changing doesn't restart its `nos-ribd`, since that process independently subscribes to config (`RoutingTables` and `StaticRoutingInstances`) and re-resolves its own associations on every relevant diff, rebuilding its in-memory RIB from a fresh `Request::Get` rather than losing state to a restart.

OSPF instances follow the identical dynamic-spawn pattern too: the watchdog subscribes to `DiffScope::OspfInstances` and spawns one `nos-ospfd --instance <name>` per `OspfInstance` in the live config, with the same first-diff-is-authoritative reconciliation, fixed 1s reconnect delay, and exponential per-process crash backoff as BGP instances/RIB tables. `nos-ospfd` gets a real `--listen-socket` and an `EndpointRegistry`/broker registration (`EndpointKind::OspfInstance`) just like `nos-bgpd`/`nos-ribd` — see `ospf/CLAUDE.md`.

Broadcast domains follow the same dynamic-spawn pattern, but opt-in per object like `nos-restd`: the watchdog subscribes to `DiffScope::BroadcastDomains` and spawns one `nos-fdbd --domain <name>` per `BroadcastDomain` **while its `vni` is set** (`Managed.claim_label = Some(VNI_LABEL)`, so `SetVni`/`ClearVni` on an existing domain — a `Modified` diff — spawns or stops it, and the domain's removal stops it), with the same first-diff-is-authoritative reconciliation, fixed 1s reconnect and exponential crash backoff, and a real `--listen-socket` (`/run/nos/fdb-<name>.sock`) registered as `EndpointKind::FdbDomain`. It creates a VXLAN device, so its SIGINT (unset vni, domain removed, watchdog stopping) deletes that device, like `nos-ribd` deleting its VRF. See `fdb/CLAUDE.md`.

Interfaces are supervised differently: unlike `nos-bgpd`/`nos-ribd`, `nos-interfaced` is a single fixed process — the watchdog always runs exactly one, the same way it always runs exactly one `nos-configd` — rather than one instance per `Interface` in config. Every interface is an OS resource in the same network namespace, so there's no isolation benefit to a per-interface process, and a single process avoids spawn/teardown churn on every interface add/remove. `nos-interfaced` itself subscribes to `DiffScope::Interfaces` and reconciles every configured interface internally on each diff.

`nos-logd` is supervised the same way as `nos-interfaced` — one fixed process, spawned first among the watchdog's children so the window before it's reachable is as short as possible — since log collection has no per-config-object scope to spawn one instance per. It has no config subscription of its own at all: every other supervised process (`nos-configd`, each `nos-bgpd`/`nos-ribd` instance, `nos-interfaced`, and the watchdog itself) is simply handed `nos-logd`'s address directly via a constructed `--log-socket <path>` argument at spawn time — the same pattern already used for `--config-socket`, rather than a broker round trip, since (like `nos-configd`'s own address) it's needed unconditionally by every process from the moment it starts, not resolved lazily. See "Log collection" below.

`nos-lacpd` is supervised the same way too — one fixed process, since `PortAggregate` (unlike `BgpInstance`/`RoutingTable`/`OspfInstance`) has no per-VRF/per-instance multiplicity for a dynamic per-object spawn to key off: one `nos-lacpd` handles every currently-configured `Lacp`-mode aggregate's member ports itself, internally, the same way `nos-interfaced` handles every configured interface. It resolves both `nos-configd` (to learn which aggregates/members are `Lacp`-mode) and `nos-interfaced` (to push its negotiated active-member set, see "Endpoint broker" below) via the broker rather than a directly-handed address, since neither is needed unconditionally from the very first instant the way `nos-configd`'s/`nos-logd`'s own addresses are. See `lacp/CLAUDE.md`.

`nos-lldpd` is supervised the same way — one fixed process, since LLDP is per-interface with no per-instance multiplicity: one `nos-lldpd` handles every LLDP-enabled physical interface itself, internally. It resolves only `nos-configd` (via the broker) to learn which interfaces have `lldp transmit`/`lldp receive` set and what hostname to advertise; unlike `nos-lacpd` it pushes to no other daemon. It has `CAP_NET_RAW` only. See `lldp/CLAUDE.md`.

**Every** supervised process — including each dynamically spawned instance — is started with a fresh certificate identity on its stdin (`ProcessSpec::with_identity(pki, role, name)`, `supervise_one`), and a task pushing rotations until it exits; `--pki-dir`/`--pki-leaf-lifetime`/`--pki-rotate-every`/`--pki-user-lifetime` configure it. See "IPC security".

`nos-restd` is the one family that is **opt-in per object** rather than one per object: it runs for a `RoutingTable` only while that table's `rest_api` field is set, and pinning/unpinning happens on an already-existing table (a `Modified` diff, a no-op for every other family). `Managed.claim_label` (`Some("rest-api")`) makes `instances::manage` key on that `FieldDiff` — set (`new` other than `"unset"`) spawns, unset or the table's removal stops — instead of on section membership; it has no IPC query listener, so `Managed.endpoint` is `None`. See `rest/CLAUDE.md`.

`nos-config`'s IPC protocol supports this via `Request::SubscribeDiff { scopes }`: a subscriber names which `ConfigDiff` sections it cares about (`DiffScope::{Hostname,BgpInstances,RoutingTables,OspfInstances,StaticRoutingInstances,Interfaces}`) and only receives `Event::Diff` for commits that touch a requested scope — commits outside every requested scope are never sent. This is a separate, additive path alongside the original `Request::Subscribe`/`Event::Config` (full snapshot on every commit, used by `nos-cli`'s live hostname prompt), which is unchanged. Both paths rely on a documented but easy-to-miss connection-lifecycle rule in `server.rs`: a subscriber (of either kind) is expected to send its request and then never write to the connection again — "the caller owns its lifetime" — so the server must not treat EOF/an error on the *request* side of a subscribed connection as reason to close the whole connection; it only stops reading further requests; the connection stays open to keep pushing events until the client is actually gone (detected when writing to it fails).

### Endpoint broker

Because the watchdog is the one process that actually spawns every other daemon, it also acts as the directory for "how do I reach daemon X" — a small broker protocol (`nos_proto::broker`: `WatchdogRequest::ResolveEndpoint { service: ServiceRef }` → `WatchdogEvent::Endpoint(PathBuf)` or `NotAvailable`), served on its own socket (`--listen-socket`, default `/run/nos/watchdog.sock`) by `watchdog::broker` — TLS with an *optional* client certificate: `ResolveEndpoint` needs one, an unauthenticated peer may only `Login` (see "IPC security"). `ServiceRef::Config` always resolves to the watchdog's own `--config-socket` argument (tracked directly, not in the registry); `ServiceRef::RibTable(name)`/`ServiceRef::BgpInstance(name)` resolve via `watchdog::registry::EndpointRegistry`, populated when `watchdog::instances::manage` spawns/stops each `nos-ribd --table <name>`/`nos-bgpd --instance <name>` instance with its own assigned socket path (`/run/nos/rib-<name>.sock`/`/run/nos/bgp-<name>.sock`, passed to the child via `--listen-socket`, alongside `--watchdog-socket` so it can resolve `nos-configd` itself the same way). `ServiceRef::FdbDomain(name)` resolves via the registry like `RibTable`. `ServiceRef::Interfaces`/`ServiceRef::Log`/`ServiceRef::Lacp`/`ServiceRef::Lldp` resolve the same way as `ServiceRef::Config` — directly from the watchdog's own `--interfaced-listen-socket`/`--log-socket`/`--lacpd-listen-socket`/`--lldpd-listen-socket` arguments, tracked, not in the registry, since there's exactly one `nos-interfaced`, one `nos-logd`, one `nos-lacpd`, and one `nos-lldpd` instance rather than one per name. `nos-cli`, `nos-ribd`, `nos-interfaced`, `nos-lacpd`, and `nos-bgpd` all resolve `nos-configd`'s address through this broker at startup instead of assuming the hardcoded default (`nos-cli` falls back to the conventional default and warns if the broker is unreachable, preserving its existing "startup never blocks" resilience; `nos-ribd`/`nos-interfaced`/`nos-lacpd`/`nos-bgpd` retry indefinitely, since they're unattended daemons). `nos-bgpd` also resolves its own owning `nos-ribd` instance the same way (`ServiceRef::RibTable`, see below) to learn its VRF; `nos-lacpd` resolves `ServiceRef::Interfaces` the same way, to push its negotiated active-member set (see "Linux drivers" below). `nos-logd`'s own address, unlike every other `ServiceRef`, is never resolved by another *daemon* through this broker — the watchdog hands it out directly via `--log-socket` at spawn time instead (see "Process supervision" above); only `nos-cli` resolves `ServiceRef::Log`/`ServiceRef::BgpInstance`/`ServiceRef::Lacp`/`ServiceRef::Lldp` through the broker, since it isn't itself spawned by the watchdog.

Each `nos-ribd` instance also gains a real IPC listener for route queries (`nos_proto::rib`: `RibRequest::GetRoutes` / `RibRequest::Lookup { addr }` → `RibEvent::Routes(Vec<PrefixRoutes>)` / `Match(PrefixRoutes)` / `NoMatch`), backing `nos-cli`'s `show route <table>` (whole table) and `show route <table> <address>` (longest-prefix-match) commands — resolved via the broker, then queried directly, with every candidate route per prefix shown ordered best-to-worst rather than only the winner, since `Rib` is multi-source.

`nos-interfaced` similarly gains a real IPC listener for interface queries (`nos_proto::interface`: `InterfaceRequest::GetInterfaces` / `GetInterface { name }` → `InterfaceEvent::Interfaces(Vec<InterfaceStatus>)` / `Interface(InterfaceStatus)` / `NotFound`), backing `nos-cli`'s `show interface` (every interface) and `show interface <name>` (one) commands.

`nos-lacpd` similarly gains a real IPC listener (`--listen-socket`, default `/run/nos/lacp.sock`) for LACP state queries (`nos_proto::lacp`: `LacpRequest::GetSummary` → `LacpEvent::Summary(Vec<PortAggregateLacpSummary>)`), backing `nos-cli`'s `show lacp [<name>]` — each `Lacp`-mode aggregate's actor identity and configured `lacp-rate`, plus every member port's Receive/Mux state and partner identity. Resolved via `ServiceRef::Lacp` (a single fixed instance, so no per-name resolution).

`nos-lldpd` similarly gains a real IPC listener (`--listen-socket`, default `/run/nos/lldp.sock`) for neighbor queries (`nos_proto::lldp`: `LldpRequest::GetNeighbors` → `LldpEvent::Neighbors(Vec<LldpNeighbor>)`), backing `nos-cli`'s `show lldp neighbors` — every neighbor heard on any interface (local interface, chassis id, port id, system name, enabled capabilities, management addresses, seconds until it ages out). Resolved via `ServiceRef::Lldp` (a single fixed instance).

Each `nos-fdbd` instance similarly gains a real IPC listener (`nos_proto::fdb`: `FdbRequest::GetMacs` → `FdbEvent::Table(FdbTable)`), backing `nos-cli`'s `show fdb <domain>` and `GET /v1/fdb/{domain}` — the domain's local and EVPN-learned MACs (with the VTEP behind each remote one) and its flood list. It is also on both ends of the EVPN data-plane feed with `nos-bgpd`, mirroring `nos-ribd`: `nos-bgpd`'s `fdb_push_client` pushes every received EVPN route to the `nos-fdbd` of each domain that redistributes into that instance (`FdbRequest::PushEvpnRoutes`, `Full` on connect then `Add`/`Remove`, Route-Target filtering done by fdbd), and `nos-fdbd`'s `bgp_client` pushes the domain's local MACs into the instance (`BgpRequest::RedistributeMacs { domain, update }`, `Full` scoped to one domain since several feed one instance). It asks `nos-interfaced` for the domain's bridge (`GetBroadcastDomain`) and the VTEP address (`GetInterface`), and `nos-ribd` for a loopback's table id (`GetTableId`) — the same daemon-to-daemon pattern as `GetVrfName`.

Each `nos-bgpd` instance similarly gains a real IPC listener for session-summary queries (`nos_proto::bgp`: `BgpRequest::GetSummary` → `BgpEvent::Summary(Vec<PeerSummary>)`), backing `nos-cli`'s `show bgp brief` — a router-wide summary (no instance argument) that iterates every `BgpInstance` in the running config, resolves each one's `nos-bgpd` via `ServiceRef::BgpInstance(name)`, and queries each independently, printing a per-instance "not running" line rather than aborting when one instance's daemon isn't reachable. Each peer's summary reports its FSM state (`Idle`/`OpenSent`/`OpenConfirm`/`Established` — `Idle` is a reporting-only value meaning no connection attempt has an OPEN in flight yet, since `nos-bgp::fsm` itself only models the latter three), remote AS/BGP ID once negotiated, uptime since `Established`, and the negotiated hold-time/keepalive — sourced from a shared per-peer `nos_bgp::status::PeerStatus` (a `tokio::sync::watch` channel owned by `nos-bgp::collision::PeerSlot`, since a peer's active and passive connection attempts share one `PeerSlot` and only one becomes canonical) that `fsm::run` writes at the same transition points it already calls `PeerSlot::on_open`/`mark_established`.

### Linux drivers

Both `nos-ribd` and `nos-interfaced` apply their reconciled desired state to the real Linux network stack via `rtnetlink`, behind a swappable `Driver` trait per crate (`interface::driver::InterfaceDriver`, `rib::driver::RibDriver`) selected with `--driver linux|noop` (default `linux` on Linux, `noop` elsewhere — the `noop` driver is today's original log-only placeholder behavior, kept as a portability/test fallback). This is deliberately in-process rather than a separate privileged process, so a future non-Linux/hardware backend only needs a new `Driver` impl, not new IPC or supervision wiring. Both binaries run as the unprivileged `nos` user; the kernel access their Linux drivers need comes from `CAP_NET_ADMIN`/`CAP_NET_RAW` file capabilities baked onto the two binaries at image build time plus a matching `cap_add` on the `watchdog` container (see `Dockerfile`/`docker-compose.yml`).

`nos-ribd`'s Linux driver owns creating a Linux VRF device + kernel routing table for its `RoutingTable`, allocating a kernel table id on first use and persisting the name→id mapping to a local file (`--table-registry-path`, default `/var/lib/nos/linux-driver/table-ids.yaml`) purely so a crash/restart reuses the same id and VRF name — this file is never read by any other process. On shutdown (the same SIGINT used for both "watchdog is stopping" and "this table was removed from config") it deletes the kernel VRF and its routes, but never the registry entry, so an ordinary restart recreates the identically-named VRF.

Because `nos-interfaced` needs to enslave an interface into the VRF device that backs its configured `routing_table`, but has no way to derive that VRF's real Linux interface name on its own (it's allocated entirely inside `nos-ribd`'s driver), `nos-ribd`'s per-table socket gains one more request: `RibRequest::GetVrfName` → `RibEvent::VrfName(Option<String>)`. `nos-interfaced`'s Linux driver resolves the owning `nos-ribd` instance via the broker (`ServiceRef::RibTable(name)`) and queries it directly — **this is the first direct daemon-to-daemon IPC link in the system** (every other component only ever talks to `nos-configd` or the watchdog broker). A `None` answer (table not running yet, or running but hasn't created its VRF yet) is treated as an ordinary transient condition, not an error, and retried automatically by both daemons' periodic re-apply tick (in addition to their existing config-diff-triggered resync) — needed here specifically because "the other daemon became ready" isn't a config change either daemon would otherwise be notified of. The link also runs the other way: `nos-ribd` derives its table's **connected routes** (`RouteSource::Connected`, preference 0 — below `Static`) from what `nos-interfaced` actually applied, asking it on every resync (`rib/src/interface_client.rs`, `ServiceRef::Interfaces` via the broker) for `GetInterfaces` (every `Interface`/`Subinterface` address whose `routing_table` is this table — a loopback's is always the table in its name, whatever the field says), `GetPortAggregates` when some aggregate subinterface is in this table, plus `GetBroadcastDomain` per SVI-carrying domain of this table (there is no "list every domain" request). They show up in `show route`/`GET /v1/routes/{table}` as `connected` and in `RibRequest::IgpCosts` at cost 0, but are **never installed** (`Rib::best_routes_for_kernel` leaves a prefix whose winner is `Connected` to the kernel, so a `Static`/`Bgp`/`Ospf` route for a connected prefix is listed but not installed either, #139): the kernel adds its own on-link route the moment the address is applied, and `LinuxRibDriver`'s dump already ignores gateway-less routes as unmanaged, so a connected prefix never appears on either side of its diff. Their purpose is RFC 4271 §9.1.2 in `nos-bgpd` — see `bgp/CLAUDE.md`'s "Next-hop feasibility".

`nos-bgpd` resolves its VRF the same way: a `BgpInstance` carries a reflexive, read-only `routing_table` field (mirrored by `nos-config` from the owning `RoutingTable`'s `bgp_instance` reference on every commit — never independently editable, and never shown in `nos-cli`'s config rendering, since it exists purely for `nos-bgpd` to read over IPC), which it resolves to a VRF name via the same `ServiceRef::RibTable` + `GetVrfName` call `nos-interfaced` uses. A `BgpInstance` with no owning `RoutingTable` is treated as invalid operating state, not a "default VRF" fallback — `nos-bgpd` never opens a session for it, only logging an error and rechecking on every resync in case config is fixed. Once a VRF name is resolved, `nos-bgpd` opens raw, VRF-scoped TCP connectivity to its configured peers (both an active outbound connect per peer and a shared passive listener on port 179, scoped into the VRF via `SO_BINDTODEVICE` rather than `rtnetlink` since no interface/route is being programmed) — the foundation the BGP FSM (OPEN/KEEPALIVE message exchange) will be layered on top of later.

`nos-lacpd` (see `lacp/CLAUDE.md`) is a second, independent daemon-to-daemon link into `nos-interfaced`, but in the opposite direction from `GetVrfName`: instead of *querying* `nos-interfaced` for something only it knows, `nos-lacpd` *pushes* something only `nos-lacpd` knows — a `Lacp`-mode `PortAggregate`'s currently-negotiated active-member set (`InterfaceRequest::PushLacpMembers`, fire-and-forget, the same "data plane push" pattern as `nos-ribd`'s `RibRequest::PushBgpRoutes`) — over a persistent connection resolved via `ServiceRef::Interfaces`. `nos-interfaced`'s Linux driver still owns every actual `rtnetlink` call for the bond device (`ensure_port_aggregate`, member enslavement); `nos-lacpd` never touches rtnetlink at all, and the kernel bond is created identically for `Xor` and `Lacp` modes (`BondMode::BalanceXor` in both cases — **not** the kernel's own `Ieee8023Ad` bonding mode, which would silently steal every LACPDU from `nos-lacpd`'s own raw sockets before userspace ever saw them). The `PortAggregateMode` only changes which control plane decides *membership*: unconditional for `Xor`, gated on this push for `Lacp`.

`nos-interfaced`'s Linux driver owns L2 switching the same way `nos-ribd`'s owns VRFs: one real Linux bridge device per configured `BroadcastDomain`, named from a bridge id allocated on first use and persisted to its own private registry (`--bridge-registry-path`, default `/var/lib/nos/linux-driver/bridge-ids.yaml` — the same `linux-driver/` directory `nos-ribd`'s `table-ids.yaml` already lives in). Because a `BroadcastDomain` is one L2 domain but two different interfaces can tag it with two different local dot1q values (the tag is locally significant per interface, not global to the domain), there is deliberately no single shared 802.1Q-aware bridge with one global VID→domain mapping: an `Interface.switching_profile`'s `Untagged` member enslaves the physical link itself into its domain's bridge, and each `Dot1q(N)` member gets its own 802.1q sub-interface (`<interface>.<tag>`) enslaved into that domain's bridge instead — so two interfaces can use different tags for the same domain and still land on the same bridge. `routing_table` and an `Untagged` switching-profile member are mutually exclusive on the same interface (rejected at commit time), since the physical link has only one master; a `Dot1q` member never conflicts, since it lives on an independent sub-interface. `BroadcastDomain` itself also carries an optional `addresses`/`routing_table` — the same flat L3 shape as a loopback `Interface` — making the domain's own bridge device an SVI (switch virtual interface): `nos-interfaced` reconciles them directly onto the bridge with the identical `reconcile_addresses`/VRF-enslavement calls it already makes for an ordinary link, independent of whatever interfaces are enslaved into that bridge as L2 members (a separate Linux device, so no conflict with any member's own VRF assignment).

### User authentication

`Config.users` (`nos_proto::User { name, password }`) holds the local users — every user is a full administrator, there are no roles. `password` is an **argon2id PHC hash** at rest (`nos-password`); a garde check rejects anything else at commit, so a committed config never holds clear text. `set user <name> password <clear>` (`UserOp::SetPassword`, also `PUT …/user/<name>` over REST, or a clear password in a seeded `config.yaml`) is the clear-text entry point: `nos-configd` (`config/src/users.rs`, called from `ConfigStore::apply_op`/`set_transaction_path`/`new`) replaces a clear password with a hash right after applying the edit — and, if the clear text still verifies against the user's earlier hash (the transaction's previous value, then the running config's), **reuses that hash verbatim** instead of salting a new one, so re-setting the same password is not a diff. Hashing lives in `nos-config`, not `nos-proto` (`ConfigOp::apply` is pure and also runs client-side in `nos-e2e`; proto must not gain a crypto crate). `UserOp`'s `Debug` and `User`'s hide the password, since ops are logged and forwarded to `nos-logd`. A commit that would leave zero users is refused (`ConfigError::NoUsersLeft`); on startup `nos-configd` creates `admin`/`admin` when the config has no users (first boot, or a config saved before users existed) — change it.

`nos-cli` (and `nos-provision`) log in through `nos-watchdogd`, not `nos-configd`: it prompts `login:`/`password:` (no echo), sends them over a server-authenticated TLS connection to the broker socket (trusting only the published `ca.crt`), and the watchdog checks them against the running config's users with `nos-password`, then certifies a key the client generated — see "IPC security". The hashes never leave the daemons, and it fails closed if the watchdog is unreachable. `nos-restd` requires a **client certificate** on every route (incl. `/openapi.json`, `/swagger-ui/`, the SSE stream) except `POST /v1/login`, which trades a password for one: it forwards to the watchdog (`WatchdogRequest::RestLogin`, `restd` only), which verifies with `nos-password` and issues a `user/<name>` certificate from the **REST CA** for the public key the client sent. The password crosses the network once; every later request carries only the certificate, and the user must still exist in the running config (fetched from `nos-configd` per request, as its own `restd` identity) — a deleted user is refused on the next request, not when the certificate expires. REST, being network-reachable, is the boundary for network callers; see `rest/CLAUDE.md`.

### IPC security

Every daemon-to-daemon and client-to-daemon connection is mutually authenticated TLS (`nos-pki`), with `nos-watchdogd` as the CA:

- **Identity.** Each certificate carries one URI SAN `nos://<role>/<name>` (`nos_proto::Role`: `watchdog`, `configd`, `logd`, `bgpd`, `ribd`, `ospfd`, `ospfv3d`, `interfaced`, `lacpd`, `lldpd`, `fdbd`, `restd`, `user`). A client dialing `ServiceRef::RibTable("rt1")` requires the server to prove it is `ribd/rt1` (`ServiceRef::role()`/`instance()`); a client that only has a socket path checks the role (`connect_role`).
- **Post-quantum only.** No classical fallback anywhere: the only key-exchange group is hybrid `X25519MLKEM768`, the only cipher `TLS13_AES_256_GCM_SHA384`, and IPC certificates are ML-DSA-65 (a verifier that accepts nothing else, so an ECDSA leaf fails even when it chains to a trusted CA). One policy, in `pki/src/policy.rs`, on the aws-lc-rs provider. The REST listener has the same key exchange but **ECDSA P-256** certificates from a second CA, so browsers and stock clients can still present one; a REST certificate never opens an IPC socket, nor an IPC one the REST API.
- **Handoff.** The watchdog creates two ephemeral in-memory CAs at start (writing only the public `ca.crt` and `rest-ca.crt` to `--pki-dir`, default `/run/nos/pki`) and, for **every spawn** in `supervisor::supervise_one`, mints a fresh keypair + leaf and writes it to the child's piped **stdin** — never argv, environment or disk. Daemons have no plaintext fallback. The watchdog's own identity rotates in-process.
- **Rotation.** Leaves are valid `--pki-leaf-lifetime` (24h) and re-pushed down the same stdin every `--pki-rotate-every` (8h); daemons swap them in hot (`Identity::update`) — new connections use the new certificate, established ones are untouched, so a long-lived stream (e.g. `nos-bgpd`→`nos-ribd`'s route push) outlives its handshake certificate and only a *reconnect* needs the rotated one.
- **Revocation.** The IPC CA keeps an RFC 5280 CRL, pushed down every child's stdin with its identity and enforced on every new handshake (never on an open connection): a child's certificates are revoked when its process exits, a user's IPC certificates when the user is deleted or its password changes. No CA roll: a child can't outlive the watchdog. See `pki/CLAUDE.md`.
- **Login.** The broker socket is TLS with the client certificate **optional**. An unauthenticated peer may send only `WatchdogRequest::Login { user, password, csr_der }`: the watchdog reads the users from `nos-configd` (its own identity), verifies with `nos_password::verify_or_dummy` (1s delay per failure, dropped after 3), and returns a `user/<name>` certificate for the **public key in the CSR** (the subject/SANs the CSR asks for are discarded). `RenewCert` trades a still-valid user certificate for a fresh one without a password, refused once the user is deleted; `nos` renews at half-life (`--pki-user-lifetime`, 8h). `ResolveEndpoint` requires a certificate. `nos-restd` uses the same broker for its REST clients (`RestLogin`/`RestRenew`, REST-CA certificates, no per-connection throttle — `nos-restd` allows one guess per second per username itself) and for its listener certificate (`IssueRestServerCert`).
- **Authorization.** Each server has a pure, unit-tested `allowed(role, &request)` with **no wildcard arm** (a new request variant won't compile until classified); a refused request is logged with role+name and the connection is closed. Config *reads* are open to every authenticated daemon; edits/saves are `user`/`restd` only (`config/src/authz.rs`); the broker's `allowed` (`watchdog/src/broker.rs`) likewise: `Login` anyone, `ResolveEndpoint` any certificate, `RenewCert` `user`, the three `Rest*` requests `restd`; route pushes are each daemon family's alone (`ribd`: `bgpd` → `PushBgpRoutes`, `ospfd`/`ospfv3d` → `PushOspfRoutes`); `PushLacpMembers` is `lacpd`'s; `PushEvpnRoutes` is `bgpd`'s and `RedistributeMacs` is `fdbd`'s; queries are `user`/`restd`, except that `nos-interfaced`'s status queries are also open to the daemons that resolve addresses through it (`bgpd`, `ribd` — for its connected routes — `ospfd`, `ospfv3d`, `fdbd`); `nos-logd` accepts pushes from any daemon and reads from `user`/`restd`. Role-level only — see `pki/CLAUDE.md`'s ceilings.
- **`nos-configd --listen` is Unix-only**: the TCP variant was removed, since a network listener would bypass all of this.

### Session authentication

A `BgpPeerGroup` carries an optional `auth` field (RFC 2385 TCP MD5, or RFC 5925 TCP-AO with key rotation — see `bgp/CLAUDE.md`'s "Session authentication" for the wire-level detail). Neither mechanism has a maintained Rust binding, so the raw `setsockopt(TCP_MD5SIG)`/`setsockopt(TCP_AO_*)` calls live in their own crate, `tcp-auth/` (`nos-tcp-auth`) — no NOS dependencies, like `nos-proto`, and the one crate in the workspace whose whole purpose is `unsafe` FFI (every other crate stays within the workspace's `unsafe_code = "warn"` default). Secrets are stored **clear-text** in config, like every other field — this system has no encryption-at-rest anywhere, and `nos-cli` renders them in the clear too.

### Routing policy language (RPL)

A `BgpPeerGroup`'s `import_policy`/`export_policy` (each an `Option<String>` naming a `PolicyDefinition`, `None` defaulting to `deny-all` — this NOS never leaves a direction unfiltered) reference a small imperative script language, `nos-rpl` (`rpl/`), compiled once by `nos-config` at commit time (rejecting an invalid script before it can be referenced) and again — cached — by each `nos-bgpd` instance that uses it (`bgp/src/policy.rs`'s `PolicyCache`). `nos-rpl` has no NOS-internal dependencies, like `nos-proto`/`nos-tcp-auth`: it exposes a plain `Input`/`BgpInput` shape a consumer adapts its own route type into (`bgp/src/rib.rs`'s `to_policy_input`), and a `Verdict` the consumer applies back onto its own route.

**Language**: Python-style significant indentation, one statement per line. A script is a flat list of statements — `if`/`elif`/`else` (an `if` with no `else`, or any branch not itself terminating, is an ordinary non-terminating statement, not a self-contained policy), `set this.<field> = <expr>` (`local_pref`/`med` numeric; `origin` an `origin.*` literal; `next_hop` an address literal or `self`), `set this.<field> += <expr>`/`-= <expr>` (`local_pref`/`med`, saturating; an unset `med` counts as 0), `this.<field>.add(..)`/`.remove(..)`/`.clear()` (community-list fields only, see below), `this.bgp.as_path.prepend(<asn>[, <count>])` (count 1-16), and the two terminals `accept`/`reject`. `check.rs`'s `check_termination` rejects at compile time any script where some path never reaches a terminal statement, or where a statement follows one that already terminated its block — a policy can never silently fall through.

**Fields** (`this.prefix`, `this.bgp.*`) are a fixed table in `schema.rs` (`FieldId`/`FieldType`/`FIELDS`), each either a plain scalar (`this.bgp.origin`, compared with `==`; `this.bgp.local_pref`, settable), an optional scalar unreadable directly until set (`this.bgp.med`), or a list (`this.bgp.as_path`, `this.bgp.cluster_list`, `this.bgp.communities`/`extended_communities`/`large_communities`) exposing only `.length` and `.contains(..)` for matching — never read as a whole value. `this.prefix in 10.0.0.0/8` and `this.bgp.as_path.contains(65010)` are the basic prefix/as-path matching idioms, extended by `this.bgp.as_path.matches("^65001_")` and `this.bgp.as_path in NAME` (regex against the ASNs rendered space-separated, `_` = start/end/space boundary; a named `as-path-list` matches if ANY pattern does); neighbor context is `this.bgp.peer` (address, compared with `==`/`!=` against a literal — like `next_hop`/`router_id`, which are unreadable except that way) and `this.bgp.peer_as` (int; both are unset/0 for a locally-redistributed route); the three community fields extend the same `.contains(..)` idiom with `AA:NN` (standard, RFC 1997), `type:subtype:value` (extended, RFC 4360), and `ga:ld1:ld2` (large, RFC 8092) colon-separated literals — disambiguated by the target field's type, not the literal's own shape, and requiring no lexer support beyond the `:` token the block-syntax colon already uses (a colon literal's `Int` parts are only ever consumed by `parse_atom` when immediately followed by another `Int`, which a block-starting colon, always followed by a newline, never is). Community fields are the only list fields that are also mutable: `.add(65000:100)`/`.remove(65000:100)` add/remove one value, `.clear()` empties the list — real policy wants incremental edits, not whole-list literal replacement, so there's no list-value syntax at all.

**Execution model**: `codegen.rs` compiles the AST straight to bytecode (`vm::Op`) in one pass that doubles as type-checking — no separate type-check pass, since emission needs the same field-resolution work a type-checker would. `vm::run` executes against a fixed-size operand stack (`MAX_STACK_DEPTH`, compile-time-bounded, no heap allocation on the hot path — this runs once per route, per peer, per update) plus a handful of mutable locals seeded from the input and threaded through execution exactly like ordinary variables (`this.bgp.local_pref` read after a `set` sees the new value in the same pass) — `cur_local_pref`/`cur_med` for the two settable scalars, and `cur_communities`/`cur_extended_communities`/`cur_large_communities` (each a `Cow` over the input's borrowed slice — the one deliberate exception to "no heap allocation," since a script that actually calls `.add`/`.remove`/`.clear` needs to hand back an owned list through `Verdict::Accept`, but `Cow::to_mut()` only clones on that first actual write, and a `Reject` verdict never pays for it at all). `Verdict::Accept` always carries the current value of every mutable field, whether or not the script touched it — same guarantee for the three community lists as for `local_pref`/`med`.

**Built-in system policies**: `ACCEPT_ALL`/`DENY_ALL` (`accept-all`/`deny-all`) are compiled once (`LazyLock`) from `"accept\n"`/`"reject\n"` rather than stored as `PolicyDefinition` config entries — nothing to edit, nothing to delete, and every peer-group's unset `import_policy`/`export_policy` resolves to `deny-all`.

**Named community aliases, community groups, and prefix lists**: three more top-level config sections — `AsPathList` (a named set of as-path regexes, compiled into `Op::AsPathMatches`), `CommunityAlias` (one name → one community literal), `CommunityGroup` (a flat, named set of alias names and/or inline literals — `.contains(..)` matches if ANY member matches; `.add(..)`/`.remove(..)` apply to every member), and `PrefixList` (a named set of prefix entries, each either a bare CIDR — **exact match only**, deliberately diverging from `this.prefix in <cidr>`'s own containment/orlonger semantics — or `<cidr> range(<min>,<max>)`, matching any prefix contained within that CIDR whose own length falls in `[min, max]`) — referenced by bare identifier anywhere a literal is valid today (`this.bgp.communities.contains(NAME)`, `.add(NAME)`, `.remove(NAME)`, `this.prefix in NAME`). `nos-rpl` itself stays dependency-free: `nos_rpl::compile` takes a `Symbols` table (name → resolved value(s)) that the caller — `nos-config`'s commit-time validation and each `nos-bgpd`'s `PolicyCache` alike — builds from its own `community_aliases`/`community_groups`/`prefix_lists` config sections, the same adapter pattern as `Input`/`to_policy_input`. An undefined name surfaces as an ordinary `CompileError`, exactly like any other compile error — this is the entire cross-reference-validation story for the three sections, no separate reference-checking pass. `Verdict::Accept` additionally carries `edits: Edits` — `as_path` (`Some` only if the script prepended), `origin` and `next_hop: NextHopSet` — each "unchanged" by default so an untouched attribute costs nothing; `nos-bgpd`'s `apply_verdict` writes them back (import/redistribute) and `build_advertisement` lets a policy next hop override `next_hop`'s mode (export). `nos-bgpd` learns each peer's ASN via `BgpRib::set_peer_asn` (from the OPEN) for `peer_as`. Groups compile to N sequential existing ops (`ListContainsCommunity`×N OR'd together, or `CommunityAdd`/`CommunityRemove`×N) rather than a new opcode, since membership is flat and small; prefix-list matching is a new `Op::PrefixInList` opcode, since exact/range-within-CIDR matching has no existing equivalent.

**RPKI**: `this.bgp.validation_state` (read-only, compared with `==`/`!=` against `rpki.valid`/`rpki.invalid`/`rpki.not_found`, the same enum-literal form as `origin.*`) is RFC 6811 origin validation, computed by `nos-bgpd` before import policy runs against the VRPs its RTR client fetched (see `bgp/CLAUDE.md`'s "RPKI origin validation"); `CompiledPolicy::reads_validation_state()` tells `nos-bgpd` which peers to route-refresh when the VRPs change.

**Explicitly out of scope (v1)**: any capability beyond `bgp` (e.g. a future `this.static.*` for a different attach point) — `nos-rpl`'s two attach points (BGP import/export) both guarantee the exact same `Input` shape today, so there's no per-attach-point capability variation to model yet.

### Log collection

Every daemon (`nos-configd`, each `nos-bgpd`/`nos-ribd` instance, `nos-interfaced`, `nos-watchdogd`) already logs via `tracing`; `nos-log-client` provides a second `tracing_subscriber::Layer` (`ForwardingLayer`) that each process installs alongside its existing `fmt` layer. It is a leaf crate depending only on `nos-proto`, so sharing it keeps the star dependency graph intact — no daemon gains a dependency on another daemon (unlike `config_client.rs`/`watchdog_client.rs`, which stay reimplemented per crate). Installing it is purely additive, so stdout/`docker logs` output is unaffected. The layer converts every `tracing::Event` into a `nos_proto::log::LogEntry` (timestamp, level, source identity, target, message, structured fields), pushes it onto a small bounded channel (dropping the oldest on backpressure — logging must never block the caller), and a background task drains that channel into one long-lived `LogRequest::Push` connection to `nos-logd`, reconnecting on a fixed 1s delay like every other reconnect loop in this codebase.

`nos-logd` holds an in-memory, bounded ring buffer (`--capacity`, default 10,000 entries) behind `log::store::LogStore`, persisted to `--log-store-path` (default `/var/lib/nos/log/entries.jsonl`, one JSON line per entry, compacted back down to `--capacity` lines once the file grows past twice that) so recent history survives a restart — the one daemon in this system with disk-backed state purely for its own sake, rather than for cross-restart identity like `nos-ribd`'s table registry. `nos_proto::log`'s `LogRequest`/`LogEvent` serve three request shapes on one socket (`--listen-socket`, default `/run/nos/log.sock`): `Push` (fire-and-forget, no reply, from every other daemon), `GetLogs { source, limit }` (`nos-cli`'s one-shot `show log [<source>]`), and `Tail { source }` (`nos-cli`'s `show log --follow`, replying once with the current buffer before streaming further `Line`s from a `tokio::sync::broadcast` channel until the client disconnects).

## Development

```bash
make check   # build + fmt + clippy + test (matches CI's fast jobs)
make fix     # auto-fix formatting and clippy-fixable lints
make help    # list all available targets
make coverage  # line coverage, fails under COVERAGE_MIN (CI runs this) — excluded: tools/e2e, the Linux drivers, raw-socket FFI (see below)
```

`COVERAGE_MIN` in the `Makefile` is 90% (#104, #131): raise it when a change lifts the total, never lower it. The metric excludes code that only runs against the real kernel — `*/driver/linux.rs`, `rib/src/driver/route_channel.rs`, `l2-socket/`, `ospf{,v3}/src/socket.rs` (#131): a mock under them would only test the mock, and `nos-e2e` is their real test.

**Rust toolchain.** CI pins `RUST_TOOLCHAIN` in `.github/workflows/ci.yml` for fmt, clippy, test and coverage (#153); the `Clippy (stable canary)` job runs the newest stable and only warns, never fails, when it breaks the build. `rust-toolchain.toml` pins the same version and `make toolchain-check` (a prerequisite of build/fmt/clippy/test) fails when local `rustc` or the pin differs from CI's — an older local toolchain once let newer-lint failures (e.g. `assert_is_empty`) through twice; install the pin with `rustup toolchain install 1.99.0`. Still confirm `gh pr checks` is green after pushing. To bump: change `RUST_TOOLCHAIN` and `rust-toolchain.toml`, run `cargo +<new> clippy --workspace --all-targets` with `RUSTFLAGS=-D warnings` and `cargo +<new> nextest run --workspace`, and fix the new lints and deprecations in the same PR —  A lint the older toolchain doesn't know only prints an `unknown_lints` warning, which `-D warnings` doesn't promote. The `Dockerfile` floats on `rust:1-slim-bookworm`, harmless since release builds don't use `-D warnings`.

`watchdog/tests/system.rs` is the unprivileged whole-stack smoke test: the real `nos-watchdogd` supervising every real daemon (`--driver noop`, every socket and state file under a temp dir — `--run-dir` moves the per-instance `<prefix>-<name>.sock` sockets off `/run/nos`), provisioned by the real `nos-provision`, reconfigured, then stopped with SIGTERM. It needs every daemon binary built next to `nos-watchdogd`, which is why each daemon crate has at least one integration test (`tests/bin.rs` where nothing else existed); a single-package run without them skips.

Unlike `all` (which leaves containers running for a human to inspect via `logs`), `base`/`drivers`/`rpl`/`ospf-suite`/`multi`/`pki-suite` are self-contained: each bundles its own `up` and checks and tears itself down on exit (pass or fail), unless `VERIFY_E2E_KEEP=1` is set. They exist so `.github/workflows/verify-e2e.yml` can run all six as independent parallel CI matrix jobs, each on its own runner, instead of the phases only ever being run one at a time by hand.

**How the harness drives NOS.** `nos-cli`'s interactive shell (reedline) can't be scripted over a plain pipe, so `nos-e2e` uses the REST API (`nos-restd`, see `rest/CLAUDE.md`) for everything:

- **Bootstrap.** REST only exists once the config pins it (`rest-api` on `rt1`), so a router's *first* config is seeded rather than sent: `nos-e2e` builds it in memory, writes it as `/var/lib/nos/config.yaml` into the created-but-not-started container (`nos-configd` loads that path at startup), then starts it and polls `GET /v1/config` until the API answers. The pin stays in the config for every later provisioning, so REST stays up for the whole run.
- **Provisioning.** `nos-provision` (a lib plus a bin) owns the flag → `ConfigOp` mapping (`nos_provision::build_ops`). `nos-e2e` parses the same flags, opens a transaction over REST (`base=current`), applies the ops locally onto the returned `Config` (`ConfigOp::apply`), `PUT`s the whole config back and commits. The `nos-provision` *binary* (the same ops over `nos-configd`'s IPC socket) is still used by `tools/bench-bgp.sh`.
- **Assertions.** Each router's logs are collected by a background task holding `GET /v1/logs/follow` (SSE) open, de-duplicating across reconnects — so assertions never depend on the `nos-logd` ring buffer not wrapping. Patterns are the old `grep` (POSIX BRE) patterns, matched against `<message> k=v k=v` (`logs::bre` translates them). Containers run with `RUST_LOG=debug` (not the daemons' default `trace`): at trace, serving the log stream makes `nos-restd` log poller activity that is forwarded and streamed again.
- **The one place REST can't be used** is checking what happens when REST itself goes away: the `rest` phase's "address not on the VRF is retried" and "unpinning stops the process and closes the port" checks run on a throwaway `router-r` container and read its `docker logs` (through `bollard`), since the API and its log stream are exactly what those checks sever.
- The image is **not** built by the harness (BuildKit is required for this Dockerfile): run `make docker-build` first — CI already builds `nos:local`.
- `make e2e-preflight` (`tools/ci/e2e-preflight.sh`, the same script `verify-e2e.yml` runs before the harness) checks the host has the kernel modules the routers' drivers need (`vrf`, `dummy`, `bonding`, `vxlan`, `8021q`, `bridge`) and that the image's `nos-ribd` still carries its `cap_net_admin` file capability — run it when `up` fails with "REST API never came up".
- BGP sessions can sit Idle for the whole connect-retry timer after a fresh start or a config change (RFC 4271 §6.8 collision resolution), and the default is 120s. `nos-e2e` sets `connect-retry-time` to 3s on every peer-group it provisions (`nos-provision --connect-retry-time`), so "session established" waits are 60s at most; phases that change config still take a baseline first and wait for a *new* session rather than a stale log line.

### BGP performance benchmark

`tools/bench-bgp.sh` is the performance counterpart to `nos-e2e`: same docker-network-plus-subcommands shape, but measuring instead of asserting. It runs one daemon under test at a time against a fixed topology — `PEERS` `exabgp` injectors (default 4), the daemon under test, and a `gobgp` **monitor** counting what comes back out — and compares `nos-bgpd` against GoBGP, BIRD and FRR on the same load.

The load is deliberately shaped like a transit edge router rather than a clean lab table: every injector announces the *same* N prefixes, so the DUT holds one path per peer per prefix and has to run best-path selection over all of them, and injector k pads its AS_PATH with k-1 extra hops so peer 1 deterministically wins and the rest sit behind it as backups. With `POLICY=1` (the default) every injector session also carries an import policy — reject anything tagged `65000:666` (every 4th prefix), set local-pref on the rest — written natively per daemon: an RPL `PolicyDefinition` for nos (so `nos-rpl`'s VM runs once per route, per peer), a `filter` for BIRD, a `route-map` for FRR, a `policy-definition` for GoBGP. It is the same rule in four syntaxes, never a different rule per daemon, and the `kept_pfx` column (`held/expected`) proves each one actually applied it — a daemon whose filter silently did nothing would otherwise converge to more prefixes and still look like a pass, which is exactly what GoBGP did at first (it honours a per-neighbour `apply-policy` only for route-server clients, so its policy has to be attached globally).

Each injector also announces a small block only it has (`101.<k>.0.0/16`), on top of the common view. That is what makes convergence mean "every peer's view is in": the monitor only ever sees one best path per prefix, so a view announced by everyone is fully counted as soon as any single peer's copy lands, no matter what the other three are still sending.

The monitor is how all four are measured uniformly: `nos-cli` has no one-shot command mode (its whole CLI surface is `--watchdog-socket`) and `nos-bgpd`'s IPC surface only counts what each peer sent it (`nos_proto::bgp::PeerSummary.accepted_prefixes`), not what it selected or advertised, so there's no scriptable way to ask nos how many best routes it holds. Peering a GoBGP monitor to the DUT sidesteps every daemon's CLI, and measures the whole receive → best-path → re-advertise pipeline rather than just "bytes arrived". the `nos-provision` binary (the same flag → op mapping `nos-e2e` uses; it logs in as the seeded `admin` user first, like `nos`, since every daemon socket is mutually authenticated TLS) provisions the nos DUT with one peer-group per neighbour.

```bash
tools/bench-bgp.sh up                 # build/pull the nos, gobgp (+ its zebra sidecar image), bird, frr and exabgp images; create the network
tools/bench-bgp.sh run <dut> [N]      # one measurement cycle (N = prefixes per peer): dut = nos | nos-quiet | gobgp | bird | frr
tools/bench-bgp.sh all [N]            # run each daemon in turn, then print the comparison table
tools/bench-bgp.sh report             # reprint the table from target/bench-bgp/results.tsv
tools/bench-bgp.sh logs [n]           # tail the DUT / monitor / injector containers
tools/bench-bgp.sh down               # tear down containers, volumes, and the network
```

Each run records session-establishment time, convergence time to the surviving best paths, `updates_per_s` (prefixes × peers ÷ that — every path the DUT had to consider, including the quarter policy rejects, since those still cost a decode plus a policy evaluation), peak RSS and CPU-seconds of the DUT's BGP **process** (not its container — nos's runs five daemons), and reconvergence time after every injector is killed and restarted. Rows are appended to `target/bench-bgp/results.tsv`.

`PEERS=1 POLICY=0 tools/bench-bgp.sh run nos 1000` is the smoke-test shape — one clean view, no filtering — for checking the harness itself after editing it.

What makes the comparison fair rather than flattering, all enforced by the script and restated in its header: all five rows install their received best paths into a real kernel routing table — nos/nos-quiet via `nos-bgpd`'s `RibRequest::PushBgpRoutes` push into `nos-ribd` (see "Config plane vs data plane" above), GoBGP via a real zebra bundled into its own DUT image (`nos-bench-gobgp-zebra:local`, pinned to the specific FRR release its zapi v6 client was written against — newer FRR releases broke decoding), FRR via `zebra` enabled alongside `bgpd` (rather than `bgpd` run alone), and BIRD via its own `protocol kernel` — and `kernel_routes`/`kernel_deploy_s` in the results table prove it, capped independently of the convergence timeout (`KERNEL_DEPLOY_TIMEOUT`, default 180s) since a slow kernel-install phase shouldn't stall the whole comparison. Memory/CPU is still sampled per BGP-decision process via `/proc/<pid>/{status,stat}` (the runtime images have no `ps`, so the pid comes from the same `/proc/*/comm` scan `verify-e2e.sh` uses) — for nos/GoBGP/FRR the process actually doing the kernel work (`nos-ribd`/zebra) is a second, unsampled process, so its cost is excluded, while BIRD's kernel sync runs in-process and is already included, a real asymmetry the script documents rather than hides. nos is measured **twice** — `nos` exactly as it ships, and `nos-quiet` with `RUST_LOG=info,nos_bgp::rib=warn`, since `rib.rs` emits an `info!` per learned route and nothing else in the comparison logs per route. `nos-quiet` is the row comparable to the other three. Convergence is timed from the first prefix reaching the monitor (not from the injector container starting, which would charge each daemon ~1.5s of exabgp startup), polled at 0.2s — so N should be large enough to take seconds; the default is 100 000.

Every daemon in the stack now honours `RUST_LOG` (`EnvFilter` in each `main.rs`, defaulting to `trace`, i.e. exactly the unfiltered behavior they had before) — added for this benchmark, but generally useful: before it, the log level was fixed at "everything", including `rtnetlink`'s TRACE-level packet dumps.

### New features require an end-to-end Docker verification phase

`cargo test`/`clippy` only prove the pure logic (validators, ops, diffing, bytecode) is correct — they never touch a real kernel, a real `rtnetlink` call, or a real two-process IPC round trip, because every driver test in this codebase runs against `NoopInterfaceDriver`/`NoopRibDriver`, not `LinuxInterfaceDriver`/`LinuxRibDriver`. A feature that programs the kernel (a new `Driver` behavior), adds a new cross-daemon IPC call, or changes what gets advertised/learned over a real BGP session is **not done** until it's also proven against the real thing: add a new phase to `nos-e2e` (or extend an existing one if the feature is a variant of something already covered, e.g. a new RPL construct extends `policy`/`redistribute-policy`/`communities` rather than getting its own phase) and **run it** — don't just write it and assume it passes. A unit-test-only change here is only sufficient for pure logic with no OS/IPC surface (e.g. a new validator, a new bytecode op with no kernel effect).

How to add a phase, using `loopback` (`tools/e2e/src/phases/drivers.rs`) as the template:

1. **Provisioning**: if the feature needs new flags (a new op sequence to apply), add them to `tools/nos-provision/src/lib.rs`'s `Args` and push the ops in `build_ops` — one flag per independent toggle, matching the existing style (`--md5-password`, `--route-reflector-client`, etc.). Keep it a thin, mostly-linear list of `ConfigOp`s; it's a test fixture, not a general tool.
2. **A phase function** in `tools/e2e/src/phases/{bgp,drivers,ospf}.rs`: `async fn <thing>(w: &mut World) -> anyhow::Result<()>`. `w.a()?`/`w.b()?` are the routers; `a.provision(&["--flag", "value"])` applies the base flags plus yours over REST (`provision_flags` takes the complete list, for a phase whose base differs). Then assert on the log line the daemon itself already emits, never by inspecting kernel state directly — the runtime image has no `ip`/`iproute2`:
   - `a.wait(PATTERN)` — first-occurrence wait, for a pattern that can't have appeared earlier in this run.
   - `a.wait_new(PATTERN, BASELINE, SECS)` with `BASELINE = a.count(PATTERN)` taken **before** provisioning — for anything an earlier phase may already have logged (re-establishing after a config change). `a.established()` waits for a BGP session.
   - `a.assert_quiet(PATTERN, BASELINE, SECS)` — a negative check (no new match).
   - Find the exact text by reading the `info!`/`debug!`/`warn!` call in the code you wrote: the message string is the anchor, followed by `field=value` for each field in declaration order, so `info!(interface = %x, "did the thing")` matches `"did the thing interface=<value>"`. A quoted (`reason="shutdown"`) or `Debug` (`source=Some(Ospf)`) field renders that way too. Patterns are POSIX BRE (`.*` wildcards, `\[ \]` literals, `\|` alternation; a bare `(` is literal).
   - If a check needs a deterministic derived value (like a `nos-ribd`-allocated table id), work out *why* it's deterministic in this fixed topology (e.g. `rt1` is always the first and only routing table any scenario configures per container, so it always gets kernel table id 100) and say so in a comment next to the constant in `consts.rs`.
3. **Wire it in**: add the phase name to `phases::run`'s `match`, to `phases::ALL` and the relevant group in `phases::group` (in a sensible position relative to what it depends on), and to this file's "Two-router end-to-end verification" section (both the prose list and the command block).
4. **Run it**: `make docker-build && cargo run -p nos-e2e -- up && … -- established && … -- <new-phase>`, then `… -- established` again afterward to confirm the existing session wasn't disturbed, then `… -- down` to clean up. Fix forward until it passes — a phase that's never actually been run against real containers isn't verification, it's an unverified guess at what the logs will say.
